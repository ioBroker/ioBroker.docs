In September, that's `latest` -Repository grew from 798 to **812 adapters** , in `stable` There are now 667. **In this issue, we present 20 adapters** , plus 17 familiar ones that have made the leap to `stable` have succeeded.

This time the focus is on the garden and the garage: three robotic lawnmower adapters (Navimow, Anthbot, Sunseeker) and two for Škoda, which couldn't be more different. Plus a few adapters you'd never think of: one is connected to the alarm monitor of a fire department control center, one retrieves the timetable from the school software, and one monitors network devices via SNMP as thoroughly as a dedicated tool.

Essentially, it was a month of noticeable small changes. No migration like in August, but many places where the user interface now explains what it does. And one bigger change in the JavaScript adapter, which introduces a completely new way of building logic.

And one more note: Because October has already provided plenty of material, this issue will focus on September. October will have its own review.

## Core updates

### ioBroker.admin 8.0.11 → 8.0.21

The admin saw ten versions in September. The four you'll notice in everyday use are:

**A quick filter is available in the menu.** A magnifying glass appears next to the logo when eleven or more entries are found. Clicking it transforms the header into a text field and hides all entries that don't match the criteria. The search is performed using both the translated and English names, so the English name of a tab will find it in every language. Pressing Enter opens the first result, and Escape closes the filter.

<img src="de/blog/images/2026_10_08_schnellfilter.webp" width="800" style="border: 1px solid #205895"/>

**The login credentials now also show the scripts.** Previously, the " **Used by"** column in the central repository only listed instances. The administrator now also searches the source code of all scripts for... `SECRETS.<ID>` and `SECRETS['<ID>']` and shows which script reads which entry. Hovering over it displays the full script ID in the tooltip. The icon comes from the script engine. `script.js.*` and `script.py.*` They will therefore be treated equally. Anyone who wants to know what might break before replacing a key can now see it all in one place.

<img src="de/blog/images/2026_10_08_zugangsdaten.webp" width="800" style="border: 1px solid #205895"/>

**The log files are now searchable.** Previously, the input field in the log tab only filtered what was already displayed on the screen. Now, pressing Enter searches the log files of the selected host, including rotated and compressed files. The time column selects the range, from the most recent entries back 30 days. New lines are still displayed live, and multi-line entries like stack traces remain together. This is based on [ioBroker.logsearch](https://github.com/disaster123/ioBroker.logsearch) by @disaster123. A new button exports the displayed data as a text file.

**Small changes that speed up startup.** Previously, the start page read the entire object database just to count objects and states: on a system with 10,000 objects, this amounted to 32 MB, blocking the admin process for several seconds. Now, the server performs the counting and responds with two numbers. As a result, the entire startup process transfers 2.4 MB instead of half the database. Additionally, with HTTPS enabled, the admin now communicates via HTTP/2, and objects on an adapter can only be deleted in expert mode. When dragging an object from one room to another, it is now moved instead of copied. Copying only occurs when the Shift, Ctrl, or Alt key is held down. The pointer displays a preview of the action.

## Important adapter updates

### ioBroker.javascript 10.1.4 → 10.4.0

This is the biggest new feature in this edition: **function blocks** , or more precisely, function block diagrams in the style of CFC. Besides JavaScript, TypeScript, Blockly, and rules, there is now a fifth way to build logic. Anyone with a background in automation technology will recognize it immediately.

<img src="de/blog/images/2026_10_08_fbd.webp" width="800" style="border: 1px solid #205895"/>

You drag building blocks onto a surface and connect their inputs and outputs with lines. Included are timers, counters, flip-flops, edge detection, comparisons, arithmetic operations, conversions, sequence control, a calendar with cron and solar events, a log, and notifications. There's also a building block with its own JavaScript, in case something is missing. Everything is connected via the building blocks. `STATE_IN` and `STATE_OUT` directly to your objects.

A plan runs cyclically with an adjustable cycle time of 50 to 10,000 milliseconds. And a plan itself can become a building block: once created, it can be used any number of times in other plans. `FB_IN` and `FB_OUT` as connections. A detailed description can be found in the [adapter's documentation](https://github.com/ioBroker/ioBroker.javascript/blob/master/docs/en/fbd.md) .

**And every script now has a history.** A button in the editor's toolbar opens the list of all saved versions, including the time, line number, and user who saved it.

<img src="de/blog/images/2026_10_08_historie.webp" width="800" style="border: 1px solid #205895"/>

On the left, you select a version; on the right, the current version is displayed, and in between, the differences are shown line by line. **"Apply to editor"** restores the old version. Anyone who's ever spent half an hour tinkering and lost track of what they've actually changed will appreciate this.

You can configure how many versions are retained: 30 per script is the default, 0 disables the history. The new **"Script History"** tab in the instance settings shows how much space each script occupies. There you can delete individual histories, orphaned ones, or all at once.

Also in this series: Monaco, Blockly, and the rule blocks are only loaded when a script of this type is opened, resulting in noticeably faster editor startup. And the rules have been significantly cleaned up; an empty ampersand now collapses into its heading instead of occupying 292 pixels for nothing.

### ioBroker.snmp 3.x → 4.0.0

The SNMP adapter received a major new version on September 30th. This is no coincidence: it has been completely rebuilt using TypeScript and has gained three new features that transform it from a query tool into a true workhorse.

<img src="de/blog/images/2026_10_08_snmp.webp" width="800" style="border: 1px solid #205895"/>

##### MIB browser:

- MIB files can be uploaded and searched; SNMPv2-MIB, RFC1213-MIB and others are included.
- The device is read **live** , layer by layer, and the result is labelled with the names from the MIB files.
- Individual values or an entire folder can be included in the OID group, the folder in one pass.
- New option "Use MIB names": the OID field will then also accept symbolic names such as `IF-MIB::ifDescr.1` On. ⚠️ Switching changes the object IDs of existing OIDs.

##### Traps:

- The adapter can listen for SNMP traps and Informs of versions v1, v2c and v3.
- A received trap lands in `<Gerät>.trap.oid`, `.name`, `.json` and `.count` The counter is the data point that scripts reference.
- The sender's address determines which device a trap belongs to.

##### Templates and small items:

- OID groups can be saved as templates and imported again, either supplementing or replacing existing ones. Templates are included for the system group, the first port of a switch, a computer, a printer, and a UPS.
- New setup wizard on the Devices tab, with live queries before any settings are saved.
- New option to write each request and each response as JSON to the log, for support purposes.
- New value format "Hexdump" for binary data
- The roles of the data points now follow the ioBroker role list.

🔗 [GitHub page of the adapter](https://github.com/iobroker-community-adapters/ioBroker.snmp)

### ioBroker.tr-064 5.0.2 → 5.1.1

The FRITZ!Box adapter made one of its biggest leaps forward in September. The most noticeable change is a new tab: **Mesh** . It displays the topology of your network as a graphic, showing which device is connected to which access point, via LAN or which Wi-Fi band.

<img src="de/blog/images/2026_10_08_mesh.webp" width="800" style="border: 1px solid #205895"/>

This aligns with two new data points per device: `devices.xxx.accessPoint` names the FRITZ!Box or the repeater it is connected to, `devices.xxx.connection` The band. Both come from the same mesh query. Anyone who has ever wanted to understand why a sensor at the other end of the house keeps dropping out now has an answer in ioBroker for the first time, instead of just in the user interface of the box.

**Devices can be renamed directly.** Clicking on the name in the mesh view prompts for the new name and allows you to enter it. `X_AVM-DE_SetHostNameByMACAddress` into the FRITZ!Box, which then uses it everywhere. Firmware that can't do this will say so. Note: The objects below\... `devices` The names will follow the box name as long as the "Use configured names" option is disabled. The same applies to scripts, via the new message. `sendTo('tr-064.0', 'setHostName', { mac, name })`.

In addition, there are **new widgets** for vis-2 ("FRITZ!Box", "Mesh topology", "Presence") and for the device adapter, new states for the internet connection (`wanAccessType`, for example `LTE` It reports when the box switches to mobile network, including provider, maximum rates and 64-bit counter for the transferred volume) as well as statuses for the 6 GHz WLAN and a second 5 GHz band.

And a whole host of persistent bugs have been fixed: Call logs no longer stop updating after a few hours, and the call monitor no longer loses events when the box combines two of them into a single network packet. Device search now reads the list in a single request instead of one per device, which used to take longer than the button could hold for many devices.

⚠️ The Mesh tab requires **Admin 8** .

🔗 [GitHub page of the adapter](https://github.com/iobroker-community-adapters/ioBroker.tr-064)

### ioBroker.modbus 9.1.1 → 9.2.0

Modbus is powerful, and its timing parameters require explanation. Who knows offhand exactly what's between data query interval, read wait time, and wait time? **Version 9.1.2 explains it directly in the interface** : each timing setting now has a small diagram next to it. A click on it shows a detailed illustration of which part of the request and response process it refers to.

<img src="de/blog/images/2026_10_08_modbus.webp" width="800" style="border: 1px solid #205895"/>

Version **9.2.0** introduces something that you only truly appreciate once you've used it: The adapter now informs the JS controller which resources it is actually using, specifically the serial interface in RTU mode and the port of a TCP slave or proxy. Before a port is opened, the protocol now names the instance that has already registered it, instead of simply reporting "Resource temporarily unavailable" or EADDRINUSE.

### ioBroker.devices 4.2.0 → 4.2.2

The devices of this adapter are now accessible in the **ioBroker Device Manager** : each appears as a card with its name, icon, battery level, and availability. Only devices that can actually be switched have control buttons; a read-only device has no button at all. And a switch displays what the device is reporting, not what it was last told. Two new themes have also been added: **Clean Light** with white cards on a light gray background, and **Tech Blue** with almost black tiles and a blue outline.

### ioBroker.iot 7.0.1 → 7.1.2

Remote access now responds to **MCP requests from the cloud via MQTT** . Furthermore, the cloud connection is now properly closed upon restart, so the cloud no longer reports duplicate connections. Only one connection attempt can be made at a time.

### ioBroker.sql 4.1.5 → 4.2.0

Anyone who has been writing values to a database for years will almost certainly have data points that no longer exist. Previously, these had to be found using custom queries. Now there's a **"Statistics"** tab for this purpose.

<img src="de/blog/images/2026_10_08_sql.webp" width="800" style="border: 1px solid #205895"/>

Each logged ID is listed there with its type, number of values, estimated size, and oldest and newest entries. The **"Clean Up"** button deletes data that is no longer logged, and optionally also data points with logging disabled. Before deletion, a dialog box displays what would be affected.

The size is deliberately described as an estimate: the number of values multiplied by the average row width as reported by the database. No SQL dialect can specify the exact number of bytes of a single data point.

In addition, there are corrections that aren't visible but are noticeable. Buffered values were lost when the adapter was stopped. The **"Record changes only"** option compared the timestamp instead of the value, which is why an alias with read conversion wrote a line for every source change. The connection test reported an error even though the settings were correct. And a connection strand closed by the server crashed the adapter instead of being replaced. Furthermore, MySQL can connect via a Unix socket, and PostgreSQL can connect directly without going through the maintenance database.

## What we are currently working on

Three things are well advanced but not yet released. We'll mention them anyway so you know what's coming:

**Sections in vis-2.** A page in the grid layout will henceforth consist of sections, and sections are more than just a visual grouping: they have their own heading with title and icon, background, border, rounding, and spacing. A section can be collapsed, can start collapsed, and can open and close based on a condition. It can be shown only to specific user groups, only above a certain width, or only as long as a condition is met.

<img src="de/blog/images/2026_10_08_vis2.webp" width="800" style="border: 1px solid #205895"/>

In addition, there are two custom widget sets for the devices in a house. **Relative** is a tile that fills its cell in the section. **Absolute** is a marker on a floor plan, no larger than a coin. And a page can be generated from the devices in the installation, sorted by room or by trade.

**More security measures are being implemented in the admin area.** We're working on the permissions system for the AI assistant and log search. We'll let you know here as soon as it's released.

**Python adapter in the js-controller.** The controller is currently learning to start adapters written in Python (`common.platform: "Python"` Furthermore, the minimum version of Node.js is increasing to **22.19** ; versions 22.0 through 22.18 will be dropped. Neither of these changes is yet in the \[document/section/etc.]. `latest`, but plan for it.

### Garden: three robotic lawnmowers at once

#### ioBroker.navimow

<img width="100" height="100" src="https://raw.githubusercontent.com/TA2k/ioBroker.navimow/main/admin/navimow.png" />

**Category:** Garden **Developer:** TA2k

It controls and monitors the Segway Navimow robotic lawnmowers via the official Navimow SDK. With 244 installations, it's the most used new addition in this issue. It reached the top of the list in the same period. `stable` done.

##### Features:

- Login to the Navimow account via OAuth2; tokens are automatically renewed.
- Live status via MQTT, plus periodic polling as a fallback.
- `status.vehicleState` with values such as `isRunning`, `isDocked`, `isPaused`, `isDocking`, `isMapping`, `isLifted`, including battery level, signal strength and events
- Remote control via buttons: Start, Stop, Pause, Resume, Return to station, Update
- Position as `postureX`, `postureY` and `postureTheta` in meters, relative to the charging station, no GPS
- Optional **live mowing map** as PNG in the state `map`, with adjustable track color, opacity and width, plus a sample script for display in vis

##### Special features:

- The registration process takes a detour: after logging in, the browser displays "Page not reachable", and this address with the `?code=...` must be completely copied into the adapter
- The status data via HTTP comes from a cloud cache and can be one to two minutes behind.
- `remote.stop` It only pauses. An ongoing task cannot be terminated via the public API; this can still only be done within the app.
- The card is factory-installed and requires `@napi-rs/canvas` Without the appropriate package, everything else continues to run; there is only a warning. Each drawing action blocks the event loop for approximately 80 ms.

### Car: two Škoda, two completely different things

Two adapters with similar names that are easily confused. In short: one checks the ordering system, the other communicates with the finished car.

#### ioBroker.skoda-public-api

<img width="100" height="100" src="https://raw.githubusercontent.com/tmarthy/ioBroker.skoda-public-api/main/admin/skoda-public-api.png" />

**Category:** Vehicles **Developer:** tmarthy

It reads and controls approved Škoda vehicles via the **official** MyŠkoda Public API, using a key that you generate yourself within the app. The focus is on electric cars, especially the Enyaq.

##### Features:

- One object tree per VIN, which maps the interface response one-to-one. Objects are only created for what the vehicle actually delivers.
- Control per area via `enabled` as a target state, in addition `start` and `stop`
- Charging limit writable in increments of 50 to 100 percent, charging mode writable, charging profiles editable via their profile ID
- Parking position as `lat;lon` in a single data point, directly usable for maps in Vis
- Adaptive polling interval: 15 minutes as the base interval, 5 minutes during charging or climate control. If the timestamp remains unchanged, the interval doubles up to a maximum of 60 minutes.
- Diagnosis with remaining quota per VIN, data age, last command including result and key expiry date, with warnings 14, 7 and 2 days prior.

##### Special features:

- ⚠️ The interface is limited to **20 requests per hour per vehicle** . There are no push notifications and no status endpoint for commands. Therefore, real-time monitoring and continuous overcapacity control are not possible.
- The key is generated in the MyŠkoda app (from app version 8.16 onwards) and **expires** ; renewal is only possible manually.
- There is no vehicle list; each VIN must be entered manually.
- A confirmed message only means "accepted by the interface," not "the car did it." The result is only shown in the verification query approximately one minute later.
- An S-PIN only needs the auxiliary heater.

🔗 [Adapter's GitHub page](https://github.com/tmarthy/ioBroker.skoda-public-api) · [Test thread](https://forum.iobroker.net/topic/85433/test-adapter-skoda-public-api-v0-1-x)

<img width="100" height="100" src="https://raw.githubusercontent.com/SentiQ/ioBroker.skoda-order-status/main/admin/skoda-order-status.png" />

**Category:** Vehicles **Developer:** SentiQ

Tracks the status of an ongoing Škoda order, i.e., a new car that hasn't yet been delivered. An adapter for exactly one phase of its life cycle, but quite useful during that phase.

##### Features:

- Log in with your MyŠkoda account; all open orders will be automatically found.

- Raw status `orderStatus` with the values `ORDER_CONFIRMED`, `IN_PRODUCTION`, `IN_DELIVERY` and `TO_HANDOVER`, and a clear explanation in `orderStatusLabel`

- The dates of the four milestones, along with lists of those achieved and those still outstanding.

##### Special features:

- ⚠️ Uses an **unofficial, replicated** interface. No connection to Škoda.
- It works before a VIN exists, thus complementing adapters like `vw-connect`, which only apply from the VIN onwards

### Weather

#### ioBroker.meteonomiqs

<img width="100" height="100" src="https://raw.githubusercontent.com/Schimi1983/ioBroker.meteonomiqs/main/admin/meteonomiqs.png" />

**Category:** Weather **Developer:** Schimi1983

Weather forecast from wetter.com via the Meteonomiqs Public Weather API: 14-day forecast, hourly values, and weather warnings. Useful for anyone looking for a German-language source.

##### Features:

- Daily forecast for 1 to 14 days including temperature, precipitation, wind, clouds, humidity, hours of sunshine and pressure, plus the time periods morning, afternoon, evening and night.
- Hourly values in the location's time zone. The folder `current` It displays the current hour and is updated hourly without additional input.
- Weather warnings with group, text and numerical severity level from 0 to 4

##### Special features:

- ⚠️ Requires an **API key from Meteonomiqs** . According to the developer, the free plan includes **100 polling requests per month** . The adapter is specifically configured for this: three fixed polling times per day, staggered by up to 15 minutes per installation, resulting in 93 polling requests in a 31-day month. If the limit is approaching, the evening polling request is the first to be dropped.
- The counter in the adapter is an estimate; the interface does not report a remaining quota. Only the error message when the limit is exceeded is reliable.
- All data groups come from the same request, so additional data only costs objects: approximately 380 for daily values only, and approximately 2430 when everything is enabled. On a Raspberry Pi, the developer recommends hourly values for just one day.

Calculate the absolute humidity and dew point from the temperature and relative humidity. It sounds like physics class, but it's the basis for the question that arises every day in summer: Will ventilating now help, or will I just bring more moisture into the house?

##### Special features:

### energy

#### ioBroker.bluetti

<img width="100" height="100" src="https://raw.githubusercontent.com/Percy2Live/ioBroker.bluetti/main/admin/bluetti.png" />

**Category:** Energy **Developer:** Percy2Live

Reads the telemetry data from BLUETTI power stations from the manufacturer's cloud: charge level, solar, grid, load.

##### Features:

- Battery with charge level, estimated remaining runtime and estimated charging time
- Power in watts for PV input, grid input, AC output and DC output, plus the status of AC, DC and ECO modes.
- Device data including serial number, model, online status and operating mode
- Login via OAuth in the browser, device selected from a list, token stored encrypted and automatically renewed
- Personal health status: suspected network outage, consecutive failed queries, failed login

##### Special features:

- Read-only; the adapter never writes to the device.
- Only the Elite 30 V2 has been tested so far. According to the developer, other models are likely compatible, but have not been tested.
- ⚠️ Cloud dependency: The adapter is not suitable as proof of a power outage; the developer recommends a local signal such as a ping or a Shelly for this purpose.

### ioBroker.sigenergy

<img width="100" height="100" src="https://raw.githubusercontent.com/ssbingo/ioBroker.sigenergy/main/admin/sigenergy.png" />

**Category:** Energy **Developer:** ssbingo, with contributions from MMeinhardt1

Connect Sigenergy solar systems locally via Modbus, specifically SigenStor and Sigen Hybrid with inverters, batteries, and charging stations. No cloud, no intermediary. With version 3.3.4, this is no longer a new product, but a mature adapter.

##### Features:

- Modbus TCP and Modbus RTU over RS485, according to the Sigenergy protocol version 2.9
- Data points for the system (grid power, PV, battery charge level and power, operating status) and the inverter (battery health and temperature, phase voltage, grid frequency)
- Optional components: AC charging station, DC charging station, power station switch, PV insulation detection, battery preheating, and microinverters with search function.
- Write access to the control registers, protected against registers that the respective device does not even know about.
- Calculated values: Time until full, remaining battery life, self-consumption rate, degree of self-sufficiency and household consumption
- **Emergency shutdown:** If the system goes into island mode, the adapter shuts down up to four external devices, such as a balcony power plant via a Shelly relay. It will only switch back on after a grid stability period, preset to ten minutes, optionally with a notification via Telegram.

##### Special features:

- One instance per Modbus endpoint; a SigenStor with micro-inverters belongs in the same instance.
- Which registers a device provides depends on the model and protocol version. Anything the device reports as invalid will not appear as a measured value.
- The seven vis widgets are located in their own adapter. `vis-2-widgets-sigenergy`
- The emergency shutdown is intended as a safety measure and does not replace a professional electrical installation.
