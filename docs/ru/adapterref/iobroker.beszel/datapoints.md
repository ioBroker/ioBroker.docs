# Точки данных и переключения метрик
Каждый переключатель на вкладке «Метрики» применяется глобально, то есть ко всем отслеживаемым системам. Отключение не только останавливает обновление - связанные с ним точки данных удаляются при следующем запуске, а строка журнала `Object tree updated: removed N datapoint(s)` указывает, сколько их. Повторное включение восстанавливает их.

Переключатель категории также управляет переключателями детализации. При отключенном параметре _Использование ЦП_ отключаются также загрузка ресурсов, анализ распределения и использование ядер - эти параметры отображаются серым цветом в панели администратора и даже не создаются в дереве. Категория «Система» не имеет такого базового переключателя: среда выполнения, системная информация и службы systemd независимы; только сведения о службах связаны с переключателем «Службы».

Группы без уровня детализации - «Вентиляторы», «Батарея», «Контейнеры», «SMART», «Сетевые мониторы» - имеют отдельные переключатели.

## Система
| Переключатели | Точки данных | Примечание |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Время работы (включено) | `info.uptime` | Секунды с момента последнего запуска |
| Службы Systemd | `info.services_total`, `info.services_failed` | Только для Linux с systemd |
| Службы Systemd | `info.services_total`, `info.services_failed` | только Linux с systemd |

`info.os` обозначает семейство платформ (`Linux`, `macOS`, `Windows`, `FreeBSD`); `info.os_name` обозначает распределение или выходные данные, которые агент также сообщает, например, `Ubuntu 24.04.1 LTS`.

Время работы и версия агента отображаются сразу после первого подключения системы - система, находящаяся в состоянии `pending`, не имеет ни того, ни другого, и концентратор сохраняет оба параметра с последнего подключения, пока система не подключена. Пока система приостановлена, концентратор отправляет значения системы как нули; адаптер же сохраняет последние фактические значения.

`info.services_total` подсчитывает количество модулей systemd, которые отслеживает агент - по умолчанию, все службы, которые когда-либо были активны, - `info.services_failed` подсчитывает, сколько из них находятся в состоянии ошибки.

Всегда присутствуют, независимо от любого переключателя: `info.online` и `info.status`. `info.online` - это значение, которое символ устройства считывает в дереве объектов: истинно только до тех пор, пока концентратор сообщает `up`, и снова ложно, как только ничего не считывается. `info.status` содержит четыре значения концентратора (`up`, `down`, `paused`, `pending`) и пятое от адаптера, `unknown` - для времени, когда адаптер остановлен или не связывается с концентратором. Запись одного из четырех значений концентратора туда означала бы утверждение чего-то, что никто не измерял.

## ПРОЦЕССОР
| Переключатели | Точки данных |
| ------------------- | --------------------------------------------------------------- |
| Использование ЦП _(вкл)_ | `cpu.usage` |
| Анализ производительности ЦП | `cpu.user`, `cpu.system`, `cpu.iowait`, `cpu.steal`, `cpu.idle` |
| Использование каждого ядра | `cpu.cores.core0`, `core1`, … |
| Использование каждого ядра | `cpu.cores.core0`, `core1`, … |

Три значения средней загрузки не имеют единиц измерения: они подсчитывают процессы, использующие ЦП или ожидающие его загрузки - следовательно, их следует рассматривать в соотношении с количеством ядер: 4.0 соответствует полностью загруженной четырехъядерной машине и тихой 32-ядерной машине. Они существуют только для систем, агент которых сообщает значение: устаревший агент не получит никаких точек данных `load_*`, а данные, созданные для него более старой версией адаптера, будут удалены.

`cpu.steal` - это доля времени, выделенная гипервизором другим гостевым системам; на реальном оборудовании она остается равной нулю, а на перегруженной виртуальной машине это число объясняет, почему все работает медленно.

## БАРАН
| Переключатели | Точки данных |
| ------------------- | ----------------------------------------------- |
| Использование памяти _(an)_ | `memory.percent`, `memory.used`, `memory.total` |
| Обмен | `memory.swap_used`, `memory.swap_total` |
| Swap | `memory.swap_used`, `memory.swap_total` |

Буфер, файловый кэш и ZFS-ARC не являются частью `memory.used`: система может получить к ним доступ, и агент сообщает о них отдельно. `memory.zfs_arc` существует только на машинах, кэш ZFS которых занимает память, и два параметра подкачки указывают только там, где настроена подкачка - `swap_used` показывает 0, пока не используется.

## Жесткий диск
| Переключатели | Точки данных |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Использование диска _(an)_ | `disk.percent`, `disk.used`, `disk.total`, `disk.name` |
| Дополнительные файловые системы | `filesystems.<name>.disk_percent`, `.disk_used`, `.disk_total`, `.read_speed`, `.write_speed`, `.total_read`, `.total_write` |
| Загрузка ввода/вывода | `disk.io_util`, `disk.io_await_read`, `disk.io_await_write`, `disk.total_read`, `disk.total_write` |
| Загрузка ввода-вывода | `disk.io_util`, `disk.io_await_read`, `disk.io_await_write`, `disk.total_read`, `disk.total_write` |

Значения `disk.*` описывают файловую систему, которую агент использует в качестве корневой. Все остальные настройки, заданные в Beszel, находятся в разделе `filesystems.`, названном в честь устройства или имени самого агента (`EXTRA_FILESYSTEMS=device__name`). `io_util` - это процент времени, в течение которого был открыт хотя бы один запрос к диску; два значения `io_await` - это средняя продолжительность одной операции чтения и записи соответственно - те же значения, которые `iostat` выводит как `r_await` и `w_await`.

`disk.name` - это имя, которое можно присвоить системному диску на агенте (`FILESYSTEM=device__name`); точка данных создается только в том случае, если она там задана. Значения `total_read`/`total_write` - это количественные показатели, а не скорости: сколько данных устройство прочитало или записало с момента запуска. Вам потребуется Beszel 0.19.0 или более поздняя версия, и после перезагрузки счетчик также обнуляется.

## Сеть
| Переключатели | Точки данных |
| ---------------------- | ------------------------------------------------------------------- |
| Сетевой трафик _(an)_ | `network.sent`, `network.recv` |
| Через интерфейс | `network.interfaces.<name>.up`, `.down`, `.total_up`, `.total_down` |

`up`/`down` - это скорости в МБ/с; `total_up`/`total_down` - это суммарные счетчики операционной системы в ГБ с момента запуска интерфейса - обычно с момента загрузки, - поэтому они сбрасываются до нуля после перезагрузки компьютера, а не после перезагрузки агента.

`network.sent`/`network.recv` показывают 0, пока соединение находится в режиме ожидания - концентратор исключает скорость в режиме ожидания из набора данных, а режим ожидания - это значение, а не пропуск.

## Температура и вентилятор
| Переключатели | Точки данных |
| ------------------------------ | ---------------------------------------- |
| Температура _(an)_ | `temperature.average`, `temperature.max` |
| Скорость вращения вентилятора | `fans.<name>` |
| Скорость вращения вентиляторов | `fans.<name>` |

`temperature.average` усредняет показания трех самых горячих датчиков, а не всех сразу - в противном случае плата с двадцатью датчиками затопит горячий процессор холодными соседними датчиками. `temperature.max` - это самое горячее значение, и поэтому обычно именно оно вызывает предупреждение. Оба значения доступны только на машинах, агент которых сообщает показания датчиков - виртуальная машина или хост контейнера без данных hwmon не получает канал температуры, а машина, датчики которой перестали передавать данные, теряет две точки данных после двух запросов вместо сохранения пустого значения.

Для работы вентиляторов требуется Beszel 0.18.8 или более поздняя версия, и они доступны только под Linux, поскольку агент считывает их из hwmon. Они отображаются в отдельном канале, `fans`, а не в разделе «Температура»: другой источник, другое значение. Вентилятор с 0 об/мин находится в неподвижном состоянии - неподвижный вентилятор - это измеренное значение, а не пропущенное значение.

## Пулы хранения (ZFS и btrfs)
| Переключатели | Точки данных |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Пулы хранения | `zfs.<pool>.pool_type`, `.disk_percent`, `.disk_used`, `.disk_total`, `.raw`, `.read_speed`, `.write_speed`, `.health` |

Один канал на пул. Для пулов ZFS требуется Beszel 0.19.0 или более поздней версии, и они именуются так, как их обозначает `zpool list`; для файловых систем btrfs требуется Beszel 0.20.0, и они имеют имя, присвоенное им агентом (метка, иначе точка монтирования, иначе UUID), в то время как идентификатор канала остается UUID файловой системы - новая метка не перемещает канал. Внутренние имена (`zfs.`, переключатель) восходят к тому времени, когда существовала только ZFS. `pool_type` указывает, к какой из двух систем он относится.

Занятость - это то, что пул сообщает как занятое по отношению к своему размеру, а не то же число, что и `df` в наборе данных. Если `raw` истинно, размер и занятость представляют собой необработанные физические байты по всем устройствам-членам (файловая система btrfs, полезное пространство которой агент не смог прочитать) - тогда `disk_percent` отсутствует, поскольку это число ввело бы в заблуждение. Пропускная способность - это то, что пул переместил за последний интервал сбора данных; для неактивного пула отображается 0, а не «неизвестно». `health` содержит собственное слово пула (`ONLINE`, `DEGRADED`, `FAULTED`, ..., `UNKNOWN`); Адаптер передает данные без изменений, поэтому слово из более новой версии поступит, даже если его нет в списке выбора администратора.

Корневая файловая система btrfs также может отображаться в разделах «Диск» или «Дополнительные файловые системы» - агент сообщает о ней в обоих местах. Подробная информация о пуле (состояние очистки, vdev, наборы данных) хранится в отдельной коллекции на хабе - включите переключатель **Подробности пула**, чтобы просмотреть ее (см. ниже).

## GPU
| Переключатели | Точки данных |
| ----------- | ----------------------------------------------------------- |
| Метрики GPU | `gpu.<id>.usage`, `.memory_used`, `.memory_total`, `.power` |
| Подробности | `gpu.<id>.power_package`, `gpu.<id>.engines.<name>` |

Объем памяти графического процессора указывается в МБ и существует только для тех графических процессоров, которые его предоставляют - интегрированный графический процессор обычно этого не делает и, следовательно, не получает никаких данных о памяти. `power_package` (подробности о графическом процессоре) также существует только для графических процессоров с датчиком мощности пакетов, таких как графические процессоры Intel (`intel_gpu_top`); у видеокарт NVIDIA такого датчика нет.

## Контейнер
| Переключатели | Точки данных |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| Мониторинг контейнеров | `containers.<name>.status`, `.health`, `.cpu`, `.memory`, `.image`, `.network`, `.update_available` |

`health` - это результат проверки работоспособности образа, и он устанавливается в значение `none`, если образ его не определяет. `cpu` - это доля общего использования ЦП хоста; суммарная загрузка всех ядер составляет 100%. `docker stats`, однако, делится на одно ядро и показывает большее значение при той же нагрузке. `network` - это суммарное количество отправленных и полученных данных в байтах в секунду, и отображается только в том случае, если концентратор предоставляет это значение.

`update_available` (Beszel 0.20.0) имеет значение true, если в реестре под тегом контейнера находится более новый образ, чем тот, который используется в данный момент. Значение false означает: обновление неизвестно - даже если образ закреплен, исключен из проверки, проверка не удалась или она еще не выполнялась. Эта точка данных появляется только в том случае, если хаб поддерживает этот столбец.

## Батарея
| Переключатели | Точки данных |
| -------------- | ----------------------------------------------------------------- |
| Состояние батареи | `battery.percent`, `battery.charging`, `battery.batteries.<name>` |

`battery.charging` имеет значение только во время фактической зарядки батареи, а не когда она полностью заряжена, находится в режиме ожидания или разряжается. Значения для каждой батареи требуют Beszel версии 0.18.8 или более поздней; компьютер с одной батареей получает только эту запись, без порогового значения, которое удаляло бы дочерние элементы при извлечении второй батареи. Компьютер без батареи вообще не получает канал батареи.

## Умные устройства
| Переключатели | Точки данных | Примечания |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| SMART-устройства | `smart.<Gerät>.state`, `.model`, `.serial`, `.firmware`, `.interface`, `.temperature`, `.capacity`, `.power_on_hours`, `.power_cycles` | Требуется smartctl на хосте; чтение каждые 15 минут |

`state` - это общая оценка: самооценка накопителя по протоколу SMART (`PASSED` / `FAILED`) или, в случае хранилищ eMMC и RAID-массивов Linux md - которые агент считывает без smartctl - состояние износа или массива, которое также может указывать на `WARNING`. `UNKNOWN` означает, что агент не смог оценить накопитель. `power_on_hours` и `power_cycles` учитываются за весь срок службы накопителя, а не с момента последней загрузки. `temperature` и `capacity` существуют только для накопителей, которые их отображают, и текстовый столбец, который накопитель не заполнил, остается пустым вместо отображения чего-либо, похожего на измерение.

По умолчанию центральный узел обновляет данные SMART один раз в час (это можно изменить с помощью параметра агента `SMART_INTERVAL`); адаптер считывает их каждые 15 минут, поэтому новое заключение появляется в центральном узле не позднее чем через пятнадцать минут после обновления.

## Подробная информация о бассейне
| Переключатели | Точки данных | Примечания |
| ------------ | ------------------------------------------------------------------------------------ | ----------------------------------------------- |
| Сведения о пуле | `zfs.<Pool>.scrub_state`, `.scrub_progress`, `.scrub_errors` | требуется переключатель «Пулы хранения» |
| Подробная информация о бассейне | `zfs.<Pool>.datasets.<Dataset>.used`, `.avail`, `.mountpoint` | GB |
| Сведения о пуле | `zfs.<Pool>.datasets.<Dataset>.used`, `.avail`, `.mountpoint` | ГБ |

Данные проверки существуют только после того, как пул был проверен хотя бы один раз - пул ZFS, который никогда не проверялся, и любая файловая система btrfs (агент не читает данные проверки btrfs) не будут иметь никаких данных.

`scrub_state` представляет собой часть данных, завершенную во время проверки (например, `SCANNING`, `FINISHED`, `CANCELED`, `scrub_progress`). `scrub_errors` представляет собой то, что не удалось исправить при последней проверке или восстановлении; это значение сохраняется до конца следующего запуска - поэтому нулевое значение в этом месте относится только к последней проверке.

Файловая система btrfs управляет своими устройствами-членами как vdev и не содержит наборов данных. Обозначение vdev-`state` `MISSING` означает, что устройство-член отсутствует.

Центр управления обновляет эти данные примерно ежечасно, поэтому адаптер считывает их не чаще, чем каждые 15 минут - информация о занятости и статусе пула, обновляемая ежеминутно, отображается выше в разделе пулов хранения. Подробная информация доступна только для пулов, которые в данный момент отображаются в группе пулов хранения.

## Сведения о службе systemd
| Переключатели | Точки данных | Примечания |
| -------------- | ------------------------------------------------------------------------------------- | ------------------------------------ |
| Подробная информация о службе | `services.<Unit>.state`, `.sub_state`, `.cpu`, `.cpu_peak`, `.memory`, `.memory_peak` | требует включения параметра служб systemd |

Один канал на устройство - на сильно загруженном хосте это очень много точек данных. `state` и `sub_state` содержат слово systemd (`active`, `running`, …), а не номер хаба. Агент считывает данные с устройств каждые 10 минут: `cpu` - это среднее значение за эти 10 минут в процентах от всего хоста; все ядра вместе представляют 100%. `cpu_peak` и `memory_peak` - это максимальные значения с момента начала мониторинга устройства агентом; для оценки использования памяти также учитывается пиковое значение systemd с момента запуска устройства.

## Сетевые мониторы
| Переключатели | Точки данных | Примечания |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| Сетевые мониторы | `monitors.<id>.protocol`, `.target`, `.port`, `.interval`, `.enabled`, `.response`, `.response_avg_1h`, `.response_min_1h`, `.response_max_1h`, `.loss_1h`, `.last_probe_loss`, `.last_probe`, `.last_update` | Беззель 0.20.0 или новее |

Для каждого монитора, настроенного для системы на хабе, используется один канал - агент проверяет целевой объект с помощью команды ping (`icmp`), `tcp`, `http` или `dns`) с заданным интервалом. Идентификатор канала состоит из протокола и целевого объекта (порта для TCP); если целевой объект монитора изменяется, он переходит на новый канал, а старый деактивируется. `port` используется только для TCP-мониторов.

`response` - это время последнего ответа в миллисекундах. `response_avg_1h`, `response_min_1h` и `response_max_1h` охватывают последний час; все четыре поля остаются пустыми, пока не было успешных тестов. `loss_1h` - это процент неудачных тестов за последний час. `last_probe_loss` и `last_probe` берутся из самого последнего набора данных тестирования: его потери и времени - при большом интервале этот набор данных может быть старше одного интервала, поэтому он не называется «последней минутой». `last_update` - это время, когда концентратор в последний раз обновлял монитор; для монитора, который никогда не измерялся, он остается пустым, и его значения также остаются неизменными. Монитор, выключенный на хабе, некорректно сохраняет свои последние значения, как показано в `enabled`.
