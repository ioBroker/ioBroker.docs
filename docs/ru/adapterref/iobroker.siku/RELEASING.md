# Выпуск и официальное включение в список ioBroker.

В этом документе кратко изложены практические шаги, необходимые для переезда.`ioBroker.siku` от бета-версии репозитория до официально зарегистрированного адаптера ioBroker.

## Что требуется от ioBroker для включения в`latest`

Исходя из текущих условий`ioBroker.repositories` Согласно требованиям, адаптер должен соответствовать как минимум следующим условиям:

- имя репозитория`ioBroker.<adaptername>`
- Настроены темы GitHub
- Файл README на английском языке с описанием, списком изменений и ссылкой на описание производителя или устройства.
- предопределенная лицензия
- Тесты адаптера на основе GitHub Actions
- действительный`type` ,`connectionType` и роли государства в`io-package.json`
- Обработка зашифрованных/защищенных паролей при хранении учетных данных
- пакет опубликован на npm
- `iobroker` организация добавлена в качестве владельца npm (`bluefox` (это документально подтвержденный контакт)
- Диалоговое окно конфигурации Admin 3 / JSON config

Основные источники:

- [ioBroker.repositories README](https://github.com/ioBroker/ioBroker.repositories)
- [создатель адаптера ioBroker](https://github.com/ioBroker/create-adapter)
- [npm доверенное издательство](https://docs.npmjs.com/trusted-publishers)

## Одноразовая настройка npm для непрерывной доставки (CD).

1. Для публикации должны существовать права на публикацию.`iobroker.siku` на npm.
2. Настройте **доверенную публикацию** для этого пакета на npmjs.com:
   - Поставщик: GitHub Actions
   - владелец:`ChrMaass`
   - репозиторий:`ioBroker.siku`
   - рабочий процесс:`test-and-release.yml`
3. Добавить владельца документа, подтверждающего право на действия в чрезвычайной ситуации:
   - `npm owner add bluefox iobroker.siku`
4. Включите переменную репозитория`ENABLE_NPM_RELEASE=true` в GitHub.

После этого помеченные тегами релизы можно публиковать из GitHub Actions без необходимости сохранять долгосрочный токен npm.

## Автоматическое определение версий патчей

Если каждая успешная попытка`main` Следующую версию патча следует получать автоматически, включите переменную репозитория.`ENABLE_AUTO_PATCH_RELEASE=true` .

Рабочий процесс`.github/workflows/auto-patch-release.yml` затем:

1. ждёт успешного`Test and Release` бежать на`main`
2. классифицирует проверяемое изменение с помощью`.github/scripts/auto-release-policy.cjs`
3. запускает существующий`release-script` в качестве выпуска патча
4. отправляет сгенерированный коммит релиза и тег Git обратно в`main`
5. вручную отправляет доверенное лицо`test-and-release.yml` рабочий процесс для нового тега, поскольку добавление тега, созданное`GITHUB_TOKEN` не запускает отдельный рабочий процесс push-уведомлений самостоятельно

Рекомендуемая стратегия версионирования для этого репозитория:

- использовать **минорные версии** (`0.2.0` ,`0.3.0` …) для видимых наборов функций или этапов публикации
- использовать **версии патчей** (`0.1.1` ,`0.1.2` …) для исправления ошибок и последующего контроля за ходом проверки.
- используйте первый npm /`latest` отправка как **`0.1.x`публичная бета-версия** , а не как`0.0.x`

Автоматический классификатор создает патч-релиз для изменений исходного кода среды выполнения, административных ресурсов, метаданных адаптера среды выполнения или зависимостей производственной среды. Он намеренно пропускает коммиты релизов, изменения версий, внесенные вручную, и изменения, ограниченные документацией, тестами, рабочими процессами, файлами блокировки или зависимостями разработки.

## стратегия CI

- Регулярные запросы на слияние: проверка синтаксиса + проверка типов + покрытие кода + один дымовой тест Ubuntu для быстрой обратной связи.
- Запросы на слияние Dependabot: полная матрица поддерживаемых ОС/Node.js перед автоматическим слиянием.
- `main` : матрица, соответствующая релизу Linux/macOS/Windows
- Windows: отдельный плановый/ручной рабочий процесс регрессионного тестирования, поскольку загрузка контроллера происходит значительно медленнее на средах выполнения Windows.
- Теги / отправка релизов: стандартное действие развертывания ioBroker с доверенной публикацией в npm и автоматическими примечаниями к релизу GitHub.

Это позволяет быстро вносить ежедневные изменения, не отказываясь при этом полностью от кроссплатформенного покрытия.

## Процесс выпуска для этого репозитория

1. Убедитесь, что запрос на слияние для релиза получил положительный результат (зеленый) и был проверен.
2. При необходимости проведите пробный запуск:
   - `npm run release -- patch --dry --branchPattern '*'`
3. В ветке релиза создайте реальный коммит релиза и локальный тег, не отправляя их автоматически:
   - `npm run release -- patch --noPush --branchPattern '*'`
4. Отправьте коммит релиза в ветку pull-request, но сохраните тег локально до слияния запроса на слияние.
5. Объедините проверенный запрос на слияние и дождитесь завершения процесса.`main` тестовая матрица. Внесение изменений в версию вручную приводит к тому, что автоматический классификатор патчей пропускает это слияние.
6. После того, как протестированный коммит релиза будет выполнен, добавьте уже подготовленный тег.`main` .
7. GitHub Actions запускает рабочий процесс создания помеченных релизов.
8. Если настроена доверенная публикация и`ENABLE_NPM_RELEASE=true` , тег build публикует файл в npm.
9. В рамках той же задачи по выпуску создается также релиз на GitHub с автоматическими примечаниями, классифицированными по категориям.`.github/release.yml` .

## После первого релиза npm

Добавьте адаптер в ioBroker.`latest` Репозиторий, используя один из следующих путей:

- с помощью`iobroker.dev` → управлять → **добавить в список последних обновлений**
- или посредством PR против`ioBroker/ioBroker.repositories`

Важное примечание к рабочему процессу проверки для`ioBroker/ioBroker.repositories` Запросы на слияние:

- почта`RE-CHECK!` **в виде отдельного комментария без дополнительного текста.**
- При необходимости добавьте пояснительный контекст в отдельный комментарий.
- Бот автоматически удаляет комментарий-триггер после завершения проверки.

После получения реальных отзывов пользователей и достаточной проверки адаптер можно будет предложить для дальнейшего использования.`stable` .
