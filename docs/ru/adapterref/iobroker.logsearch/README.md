# ioBroker.logsearch

Ищите файлы журналов ioBroker непосредственно в административном интерфейсе по временному диапазону, уровню и тексту.

## Функции

- Определяет каталог логов и имя файла лога из конфигурации js-контроллера.
- Проводит поиск в активном журнале ioBroker и в ротированном журнале. `<name>.YYYY-MM-DD.log` файлы.
- Прозрачно считывает сжатые с помощью gzip исторические журналы.
- Фильтрация по фрагменту текста без учета регистра и уровням `error`, `warn`, `info`, `debug`, или `silly`.
- Ограничивает количество результатов и четко указывает на усеченные результаты.
- После выполнения поиска журнал активных действий обновляется каждые пять секунд.
- Синхронизация возобновляется после открытия вкладки браузера, восстановления сетевого соединения или подключения администратора.
- Сохраняет дублирующиеся строки физического журнала в виде отдельных результатов.
- Переключает отображение раздела « **С настоящего момента»** для показа только новых соответствующих записей или возврата к истории изменений.
- Экспортирует отображаемые строки журнала в формате UTF-8. `.txt` файл.
- Извлекает десять последних уникальных поисковых запросов из постоянно отображаемого выпадающего списка.

Текстовый фильтр представляет собой простой поиск подстроки без учета регистра по всей строке лога. Это не регулярное выражение.

## Требования

- Node.js 22 или новее
- js-controller 6.0.11 или новее
- Администратор 7.6.20 или более поздняя версия

## Установка

Адаптер опубликован на [npm](https://www.npmjs.com/package/iobroker.logsearch) . Включение в официальный каталог адаптеров ioBroker находится в процессе рассмотрения.

После добавления выберите **«Поиск логов»** в каталоге адаптеров в административной панели ioBroker и добавьте экземпляр.

## Вкладка «Администратор» и экземпляры

Адаптер намеренно ограничен одним экземпляром на каждую установку ioBroker. Его единственная вкладка «Администрирование» предоставляет интерактивное рабочее пространство для поиска по логам с таблицами результатов, инкрементальными обновлениями, фильтрацией в реальном времени, историей поиска и экспортом. Отдельное представление конфигурации управляет только местоположением логов и параметрами поиска по умолчанию; стандартная форма конфигурации jsonConfig не подходит для этого интерактивного рабочего пространства.

В многохостовых установках файлы журналов хранятся локально на хосте, где запущен адаптер. Вкладка «Администрирование» выполняет поиск в журналах, доступных этому экземпляру; она не объединяет журналы с других хостов.

## Конфигурация

| Параметр                                   | По умолчанию | Описание                                                                                      |
| ------------------------------------------ | -----------: | --------------------------------------------------------------------------------------------- |
| Каталог журналов                           |   _(пустой)_ | Каталог, содержащий файлы журналов ioBroker. Оставьте пустым для автоматического определения. |
| Часы по умолчанию                          |         `72` | Начальный временной диапазон, используемый вкладкой «Поиск в журнале».                        |
| Максимальное количество строк по умолчанию |        `500` | Начальное максимальное количество возвращаемых строк.                                         |

Адаптер устанавливает абсолютный максимум в 5000 строк на запрос. Настроенный каталог логов используется на стороне сервера; клиент не может переопределить его в поисковом запросе.

### Автоматическое определение каталога журналов

При пустом **каталоге Log** адаптер считывает `iobroker.json` и оценивает первый включенный `log.transport` типа `file`, точно так же, как это делает js-controller:

- `filename` по умолчанию `log/iobroker` Относительные имена файлов определяются с помощью js-контроллера. `logger.ts` Правило: путь указывается в корневом каталоге установки для npm-инсталляций или в каталоге контроллера для репозитория разработки. Это место назначения используется, даже если оно пустое или еще не существует; журналы в других каталогах не должны переопределять указанный путь.
- Абсолют `filename` (`/var/log/iobroker/iob` а также `D:\logs\iobroker`) используется без изменений.
- `fileext` Определяет расширение ротируемых файлов; символическая ссылка на активный журнал всегда одинакова. `<name>.current.log`.
- Сначала проверяется каталог данных, определяемый контроллером. `iobroker.json` Это обеспечивает сохранность. `IOBROKER_DATA_DIR` поддержка через adapter-core без доступа к среде выполнения процесса в адаптере.

Если чтение пригодного для использования файла невозможно, адаптер ищет подходящие варианты. `log/` плюс соседний каталог данных и `/opt/iobroker/log` Обнаруженный каталог регистрируется при запуске и отображается на странице конфигурации. Устаревшее значение по умолчанию. `/opt/iobroker/log` Тот факт, что более ранние версии, записанные в каждый экземпляр, игнорируются, если они не существуют, позволяет и существующим экземплярам извлечь выгоду из этого обнаружения.

## Использование

1. Откройте вкладку **«Поиск по журналам»** в административной панели ioBroker.
2. Введите необязательный фрагмент текста и выберите временной диапазон, уровень и ограничение по количеству строк.
3. Выберите **«Поиск»** . Изменение фильтра автоматически запускает новый поиск через небольшую задержку.
4. Оставьте вкладку открытой, чтобы автоматически получать новые соответствующие записи.

Результаты упорядочены по дате добавления (сначала самые новые) и отображают метку времени, уровень, источник и сообщение. **Кнопка «Очистить фильтр»** снимает текстовый фильтр.

Эта кнопка **немедленно** очищает таблицу и начинает отслеживать новые записи. В этом режиме кнопка остается выделенной. Она сохраняет текущие фильтры и не удаляет файлы журналов. Начальная точка устанавливается с помощью часов адаптера и остается активной при повторном поиске, изменении фильтров или переподключении. Нажмите выделенную кнопку **«Сейчас»** еще раз, чтобы включить более старые записи в выбранном временном диапазоне. Перезагрузка страницы также возвращает к обычному виду истории.

**Экспорт в формат .txt** загружает только отображаемые в данный момент строки, начиная с самых новых, включая повторяющиеся строки. Файл в формате UTF-8 содержит исходный текст журнала без цветовых кодов терминала. Применяются активные фильтры и ограничение на количество строк; в случае усечения результата экспортируются только отображаемые строки.

Щелкните **текстовое поле «Поиск»** , чтобы открыть последние десять поисковых запросов, начиная с самых новых. Ввод текста фильтрует выпадающий список по началу поискового запроса (регистр нечувствителен); он исчезает, когда ничего не совпадает. Пустое поле отображает полную историю. Выберите запись с помощью мыши или клавиш со стрелками и нажмите Enter, чтобы повторить поиск, не изменяя другие фильтры или **поле «С настоящего момента»** . Непустой запрос запоминается при нажатии Enter, щелчке **«Поиск»** или выходе из редактируемого поля; автоматическое обновление и промежуточные нажатия клавиш не заполняют историю. Повторное использование запроса перемещает его вверх (регистр нечувствителен). При открытии вкладки последнее состояние поиска восстанавливается и используется для первоначального поиска. Очистка фильтра также запоминается, в то время как предыдущие непустые термины остаются доступными в выпадающем списке. Адаптер хранит историю и последнее состояние поиска в формате JSON. `logsearch.<instance>.searchHistory`, например `logsearch.0.searchHistory` Он сохраняется после перезапуска адаптера/браузера и используется пользователями этого экземпляра. Текст поиска сохраняется дословно, включая пробелы; пропускаются только пустые записи или записи, состоящие только из пробелов.

## Разработка

Сам адаптер написан на TypeScript. `src/` и компилируется в `build/` Административный интерфейс пользователя (Admin GUI) — это отдельный проект npm. `src-admin/` создано с помощью [Vite](https://vite.dev/) и[`@iobroker/gui-components`](https://github.com/ioBroker/adapter-react-v5) ; `npm run build` записывает это в `admin/`.

```bash
npm ci            # adapter dependencies
npm run 1-npm     # GUI dependencies from src-admin/package-lock.json (npm ci)
npm run lint      # eslint for src/ (npm run lint-frontend for src-admin/)
npm run check     # tsc for src/ and test/
npm test          # unit tests and package validation
npm run build     # build/ (tsc) and admin/ (vite)
```

Полная сборка графического интерфейса пользователя запускается. `npm ci` в `src-admin/` даже когда `node_modules` уже существует. Он использует зафиксированный файл блокировки без `--force` и останавливается, если установка зависимостей завершается неудачей. При повторных сборках графического интерфейса после однократной установки зависимостей, отдельный процесс завершается неудачей. `2-build`, `3-copy`, и `4-patch` Задания остаются доступными.

Для работы с графическим интерфейсом запустите сервер разработки Vite и направьте его на работающий экземпляр административной панели через порт 8081:

```bash
cd src-admin
npm start
```

Затем откройте `http://localhost:3000/?instance=0` для диалогового окна настроек или `http://localhost:3000/?instance=0&tab=true` для вкладки «Поиск в журнале».

Система непрерывной интеграции (CI) проверяет код адаптера и графический интерфейс пользователя (GUI) на Node.js 24, собирает оба проекта из чистой репозитории, а затем запускает тесты адаптера на Node.js 22, 24 и 26 под Linux. При отправке тегов релизов тесты адаптера также запускаются на Windows и macOS.

### Подготовка к выпуску

Используйте Node.js 24 и `npm ci` для релизов. Обновите версию в `package.json`, `src-admin/package.json`, `io-package.json` и оба поля корневой версии в каждом `package-lock.json` (корень и `src-admin/`), вместе с журналом изменений и переведенными примечаниями к выпуску. Запросы на добавление новых функций не обновляют сгенерированные файлы в `build/` и `admin/`.

Отправьте полный коммит исходного кода и дождитесь завершения процесса **тестирования и выпуска** . CI пересобирает адаптер и административный интерфейс для каждого запроса на слияние. После этого выполняется проверка наличия отправки изменений. `main` При успешном прохождении проверки CI фиксирует сгенерированные данные. `build/` и `admin/` файлы в `main` Таким образом, при установке непосредственно из GitHub включаются скомпилированный адаптер и интерфейс администратора. Обновления зависимостей фиксируют только обновленный блок пакета; последующий процесс тестирования публикует соответствующую сборку интерфейса администратора.

Дождитесь сгенерированного коммита сборки, затем создайте аннотированный коммит. `v<version>` метка на полученном `main` Используйте команду HEAD и отправляйте только этот тег. Избегайте инструкций CI-skip в сообщениях коммитов релиза. Проверка тегов подтверждает соответствие тега и всех полей версии пакета. Задача публикации собирает адаптер и административный интерфейс непосредственно перед публикацией через npm Trusted Publishing и созданием релиза GitHub. Никогда не перемещайте существующий опубликованный тег релиза.
