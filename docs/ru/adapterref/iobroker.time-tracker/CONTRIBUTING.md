# Вклад

Немецкий оригинал этого документа находится в[`docs/de/CONTRIBUTING.md`](https://github.com/sadam6752-tech/ioBroker.time-tracker/blob/main/docs/de/CONTRIBUTING.md) .

## 1. Основное правило: чистая комната (связывание)

Этот проект представляет собой **самостоятельную реализацию** , а **не** производную версию другой системы учета рабочего времени. В основе лежит **внутренняя спецификация** : она находится вне этого репозитория и **не публикуется** . Только описание адаптера (`README.md`), эти правила внесения вклада и исходный код опубликованы (см. раздел 6).

**Запрещено**

- Заимствование кода, комментариев, текстов сообщений, имен классов или переменных из других проектов — даже не «копирование и переименование».
- Автоматический перенос или перевод иностранного кода (транспайлер, преобразование LLM).
- Перестройка файловой или классовой структуры других проектов в виде собственной модульной структуры.

**Допустимый**

- Технические характеристики, необходимые для дальнейшего использования существующих данных: форматы файлов и данных, индексы полей и единицы измерения. `users.txt`, `userdaten.txt` индекс 0–17, `Timetable/<year>.<month>`, `A<year>`, `absenz.txt`).
- Правила вычислений, поведение и правила округления (документированы во внутренней спецификации).
- Краткие технические идентификаторы в документации для обеспечения отслеживаемости.

**Собственные идентификаторы в коде** (на английском языке, согласованные): `_Vorholzeit_pro_Jahr` →`vorholzeit_per_year`, `_zuschlag` →`shift_rules`, `Timetable` →`time_entries`, `_modell` →`overtimeModel`, `absenz.txt` →`absenceTypes`.

## 2. Способ работы

1. **Сначала спецификация:** сначала опишите поведение во **внутренней спецификации** (она находится вне этого репозитория и не публикуется).
2. **Тестирование перед внедрением:** создавайте эталонные файлы и фикстуры на основе **наблюдаемых выходных данных** эталонной установки или существующих данных — никогда не заимствуйте их из стороннего кода.
3. **Внедряйте** и адаптируйте спецификацию там, где она отклоняется от неё — не используйте сторонний код в качестве образца, чтобы «подстроить» реализацию под себя.
4. Изменения в спецификации вносятся на том же этапе, что и в код, и кратко упоминаются в тексте запроса на слияние (сама спецификация не публикуется).

## 3. Контрольный список для связей с общественностью

- [ ] Никакой код, комментарии или идентификаторы не были заимствованы из стороннего проекта (сравнение со спецификацией, результат указан в запросе на слияние).
- [ ] Внутренняя спецификация обновляется, если она затрагивает поведение или формат (указано в тексте запроса на слияние).
- [ ] Добавлены или адаптированы тесты (модульные/интеграционные; эталонный файл для логики вычислений).
- [ ] i18n: добавлены новые тексты в `en.json` только, `npm run translate` бегать, `npm run check:i18n` зеленый (все 11 языков доступны).
- [ ] Информация о лицензии и происхождении по-прежнему верна. `LICENSE`, раздел «Происхождение» в `README.md`).
- [ ] В коммите отсутствуют сторонние файлы, архивы или копии данных. `*.zip` (иностранные справочники).
- [ ] Новые/измененные состояния: `common.role`, `common.type`, `common.read`, `common.write` подходят друг другу — нет общей роли `state`, `button` →`boolean` с `read:false` /`write:true` роль `json` →`common.type = "string"`.
- [ ] Новые тексты в `common.news` В текущей версии добавлены **все 11 языков** (проверка адаптера сообщает об отсутствии переводов в новейшей версии как об ошибке).
- [ ] Секреты можно получить только через `encryptedNative` /`protectedNative`; нет четкого текста в `native` или в бревнах.
- [ ] Результат проверки адаптера, указанной в запросе на слияние, как только будет готов шаблон адаптера. `npx @iobroker/repochecker <repo-url> --local`).

## 4. Соглашения по кодированию

- **TypeScript** (строгий режим), ESLint с `@iobroker/eslint-config` Prettier; в коде отсутствуют немецкие идентификаторы (исключение: термины предметной области, которые документированы целенаправленно, например...). `vorholzeit_per_year`).
- **Тесты адаптера:** `@iobroker/testing` —`tests.packageFiles` (проверки) `package.json` /`io-package.json`) и `tests.integration` Для контроллера JavaScript; предоставленные заглушки модулей устарели.
- **Собственная логика:** Mocha с ts-node и chai для вычислений и учета часовых поясов. `test/mocharc.custom.json`), драматург, проводивший сквозное тестирование PWA, `npm run coverage` (`nyc`) для покрытия — проверка покрытия намеренно пропускает проверку типов (`test/mocharc.coverage.json`), потому что узел проверки типов ts-node находится в `nyc` Не работает с адаптерами разных типов; `npm run check` остается ограничением по типу; названия тестов описывают сценарий и ожидание («формирует пары по (ts\_utc, id)», а не «test1»).
- **Веб-приложение (`src-www/`):** самостоятельный проект со своими собственными `package.json` /`tsconfig.json` (React 18, MUI 5, Vite). Схема работы: `npm run install:pwa` →`npm run build:pwa` (проверка типа + встроить в `www/`) →`npm run lint:pwa`; в процессе развития `npm run dev:pwa` (впереди) `/api` (к запущенному экземпляру). Приложение взаимодействует с адаптером только через префикс API. `/api` поддерживает сессию в `localStorage` и очереди, отметки о прохождении контроля в автономном режиме (`idempotencyKey` (за каждый удар). Права доступа **всегда** определяются сервером; пользовательский интерфейс лишь скрывает то, что и так было бы запрещено. Новые тексты должны находиться в `src-www/src/i18n/en.json`.
- **Сгенерированные файлы:** `build/` и `www/` Они генерируются и никогда не редактируются напрямую.
- **Состояния:** создавать объекты с `setObjectNotExistsAsync` /`extendObject`; `common.name` (по меньшей мере `en` +`de`), `common.type`, `common.role`, `common.read`, `common.write` являются обязательными и должны соответствовать правилам роли (см. контрольный список PR).
- **Конфигурация:** секреты должны находиться в `encryptedNative` /`protectedNative`; `native` блокировать, `admin/jsonConfig.json` и `src/lib/adapter-config.d.ts` поддерживаются в синхронизированном состоянии.
- **Время:** внутри системы всегда отображается в формате UTC (время начала временной эпохи) **и** в целых минутах; отображение осуществляется с учетом часового пояса пользователя.
- **База данных:** изменения вносятся только посредством версионированных миграций (`schema_migrations`).
- **Ошибки:** ошибки API, такие как `application/problem+json` со стабильными кодами ошибок (в соответствии с внутренней спецификацией).
- **Языки (i18n):** отображать тексты только из языковых файлов; добавлять новые тексты **только** в базовый английский файл, а затем запускать `npm run translate`. Подробности:[`docs/en/i18n.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/i18n.md) .
- **Коммиты:** краткое, фактическое описание в повелительном наклонении; один коммит на каждое логическое изменение.
- **Интеграционный тест:** он выполняется для **собранного** пакета (`npm pack` от `build/` Всегда бегите. `npm run build` до `npm run test:integration` — В противном случае тест молча проверяет предыдущее состояние (что видно по отсутствующим в тестовом запуске новым сообщениям в логах).
- **Символы конца строки и форматирование:** символами конца строки являются **LF** (`.gitattributes`, `.editorconfig`, Prettier); CRLF делает `npm run lint` терпят неудачу с сотнями `prettier/prettier` ошибки. Поэтому исправьте форматирование с помощью `npx prettier --write "src/**/*.ts"` а **не** с `eslint --fix`: `--fix` добавляет пустые блоки JSDoc для недокументированных членов и тем самым создает ошибки (`jsdoc/no-blank-blocks`).

## 5. Изменения, имеющие отношение к безопасности.

Это касается, в частности, аутентификации, обработки сессий/токенов, управления доступом на основе ролей (RBAC), аудита и конечных точек терминалов. Такие изменения требуют: описания риска, тестирования негативных сценариев (права доступа, CSRF, идемпотентность, `409`) и обновление контрольного списка безопасности во внутренней спецификации.

Правила для этого:

- Внутренняя спецификация **никогда не** копируется в репозиторий; `.gitignore` содержит для него страховочную сетку (`PROJECT_PROMPT.md`, `docs/PROJECT_PROMPT.md`).
- Ссылки на номера разделов спецификации не должны содержаться в опубликованных файлах, таких как... `README.md` Внутренние файлы README модулей описывают требования своими словами.
- Информация о происхождении кода хранится вне этого репозитория и содержит указание на основу реализации, а также утверждение «исходный код не был скопирован извне».

### Процедура выпуска

1. `npm run version:bump patch` устанавливает версию в `package.json`, `io-package.json` а также в списке изменений файла README. Добавьте записи новостей на **всех 11 языках** — при обновлении копируется только первая строка.
2. `npm run version:check`(Также проверяется, что списки не увеличиваются в размере: максимум семь) `common.news` (и пять версий в файле README), `npm run check:i18n`, `npm test`, `npm run check:adapter` и `npm run e2e` (последнее **после** `npm run build && npm run build:pwa` (в противном случае проверяется старое состояние) должно быть зеленым — только тогда фиксация. После внесения изменений с помощью скрипта всегда выполняется. `npm run lint` eslint рассматривает правила Prettier как ошибки, и даже слишком длинное выражение приводит к сбою в работе CI. `check-and-lint` неудача. `lint` и `lint:pwa` бежать с `--max-warnings 0` Таким образом, предупреждение — это в той же мере ошибка, что и предупреждение.
3. **Перед коммитом и отправкой изменений необходимо получить подтверждение.** Коммит версии и тег отправляются только после того, как владелец (Алекс) даст «ок»: непосредственно перед релизом вопрос заключается в том, разрешена ли отправка изменений или есть какие-либо замечания. Только после этого «ок» коммит создается, помечается тегом и отправляется.
4. Коммит, **аннотированный** тег (`git tag -a vX.Y.Z -m 'X.Y.Z'`) и настаивать с одобрения (`npm run push:approve` Сообщение коммита версии становится **примечанием к релизу** — рабочий процесс записывает его содержимое на страницу релиза. Таким образом, оно написано **на английском языке** (как и записи в журнале изменений в файле README), чтобы страница релиза была понятна всем.
5. **Подождите, пока рабочий процесс «Тестирование и релиз» не станет зеленым для соответствующего тега, а затем еще 5-10 минут:** публикация в npm запустится в конце выполнения, а затем последует индексация в реестре (измерено: зеленый результат выполнения 17:37). `npm view … dist-tags` (показывает версию 17:42). Только после этого проверяйте.
6. Тег опубликованной версии **никогда не удаляется и не отправляется повторно** . Это удаляет соответствующий релиз на GitHub, создает ошибку (npm отклоняет вторую публикацию той же версии) и ничего не меняет в опубликованном пакете. Если тег отсутствует, устанавливается только сам тег, и релиз создается на его основе в интерфейсе GitHub.

## 7. Локальный сервер разработки (ioBroker dev-server)

Экземпляр для разработки находится в `.dev-server/`: администратор `http://127.0.0.1:8081`, адаптер с веб-интерфейсом на `http://127.0.0.1:8092` Начинается это с

```powershell
npm run dev-server watch
```

Сервер разработки собирает адаптер и устанавливает его в экземпляр разработки. `npm pack` +`npm install`) и запускает его самостоятельно; при каждом изменении источников он перезапускается примерно через две секунды.

Правила, важные в следующем порядке:

1. **Экземпляр остается отключенным в контроллере.** Сервер разработки запускает адаптер самостоятельно, и контроллер не должен запускать его дополнительно — иначе каждый запрос на запуск контроллера будет приводить к ошибке. `ADAPTER_ALREADY_RUNNING` (код 7) и повторяется каждые 30 секунд. Проверить и установить (из `.dev-server/default`):

   ```powershell
   node node_modules/iobroker.js-controller/iobroker.js list instances
   node node_modules/iobroker.js-controller/iobroker.js object set system.adapter.time-tracker.0 common.enabled=false
   ```

   Затем в журнале говорится следующее: `Do not restart adapter system.adapter.time-tracker.0 because disabled or deleted` И адаптер продолжает работать, потому что его удерживает сервер разработки.

2. **Никогда не включайте и не перезапускайте адаптер в `ioBroker.admin` ** пока `dev-server watch` запущен — запуск через интерфейс снова активирует экземпляр и воспроизводит в точности цикл правила 1. В логе это выглядит так: `"system.adapter.time-tracker.0" enabled` →`started with pid …` →`terminated with code 7 (ADAPTER_ALREADY_RUNNING)` →`Restart adapter … because enabled` Перезапуск происходит каждые 30 секунд. В документации к серверу разработки это прямо указано. Перезапуск принудительно осуществляется путем сохранения исходного файла (управление переходит к наблюдателю) или путем перезапуска всей цепочки.

3. Тот, кто хочет запускать и останавливать адаптер **из административного интерфейса,** выбирает один из двух режимов — в этом случае адаптер удерживается только с одной стороны, и запуск/остановка через интерфейс не вызывает проблем.
   - `npm run dev-server run` — Сервер разработки не запускает адаптер, его удерживает контроллер. Горячая перезагрузка существует только для административного интерфейса; для внесения изменений в код требуется... `npm run build` и (при остановленном сервере разработки) `npm run dev-server upload`.
   - `npm run dev-server watch --noStart` — Сервер разработки по-прежнему автоматически выполняет сборку и синхронизацию, но не запускает адаптер. Он отключает экземпляр при каждом собственном запуске. `adapter.common.enabled = false` в журнале `Stop <adapter>.0`), поэтому запустите адаптер **еще раз** после этого — в административном интерфейсе или с помощью `node .dev-server/default/node_modules/iobroker.js-controller/iobroker.js start time-tracker.0` После этого контроллер удерживает его; запуск, остановка и перезапуск в интерфейсе не вызывают проблем. После изменения кода перезапустите адаптер там, чтобы загрузить синхронизированную версию.

4. **Одновременно можно использовать только один сервер разработки** , **дополнительные серверы не допускаются. `npm run build` ** Кроме того: сервер разработки выполняет сборку самостоятельно, параллельные сборки приводят к состояниям гонки и последующим перезапускам.

5. Если экземпляр всё равно зависает в цикле, завершите все процессы, в командной строке которых указан репозиторий или `.dev-server` и перезапустить `npm run dev-server watch --noStart`.

6. Сюита драматурга (`npm run e2e`) запускает собственный сервер на порту `8099` с базой данных в оперативной памяти и не затрагивает сервер разработки; он загружает адаптер из `build/`, поэтому `npm run build` необходимо сделать заранее.

7. Для вызова передайте `--no-browser-sync` BrowserSync однажды дал сбой на старте в соревновании с администратором, который еще не начал работу (`ECONNREFUSED 127.0.0.1:20426`) и потянул за собой вниз сервер разработки. Цена заключается лишь в том, что изменения в административном интерфейсе ioBroker больше не перезагружаются автоматически.

Данные экземпляра для разработки находятся в папке `.dev-server/default/iobroker-data/time-tracker.0/` (база данных, `session-secret`, `backups/`) и не имеет версий.

## 8. Версионирование и выпуск

Версия адаптера находится в **двух** местах и должна быть одинаковой: `package.json` (`version`) и `io-package.json` (`common.version` Проверка на это выполняется в `npm run test:package` и дополнительно посредством `npm run version:check`.

Правила:

1. **Никакая информация не будет опубликована или распространена без вашего разрешения.** Перед публикацией `git push` и перед каждым шагом версии (`npm run release …`), сопровождающему задается вопрос, и ожидается ответ. Тот, кто хочет заблокировать отправку изменений, включает обязанность подтверждения в своей рабочей копии (локальная настройка, не версионированная):

   ```powershell
   git config zt.requirePushApproval true   # works only together with core.hooksPath = .githooks
   npm run push:approve                     # shows the open commits and approves exactly this commit
   git push                                 # now allowed — the next commit needs an OK again
   ```

   Без подтверждения предварительный крючок прерывает работу; отключите его навсегда с помощью `git config zt.requirePushApproval false`.

2. **Перед каждым рывком, `npm run version:bump -- patch` повышает версию** (или `minor` /`major` Инструмент устанавливает оба поля версии, переименовывает блок «В РАЗРАБОТКЕ» в файле README в новую версию, создает новый заполнитель и добавляет `common.news` для новой версии. Затем переведите новости (`npm run translate` или вручную) и бежать `npm run version:check`, `npm run check:i18n` и тесты. Аргументы должны остаться позади. `--` В противном случае npm их проглотит. `npm run version:bump -- patch --dry` (показывает процедуру без текста).

3. **Каждое изменение вносится в список изменений файла README перед отправкой** (changelog). `## Changelog`, новейший раздел `### **WORK IN PROGRESS**` Этот блок **не должен быть пустым** — инструмент выпуска его не принимает. Версия для него **не** изменяется вручную.

4. **Список изменений находится в файле README, а не в отдельном файле.** Инструмент выпуска читается следующим образом: `CHANGELOG.md` только если он существует, и тогда раздел README больше не будет поддерживаться. В README хранятся последние **пять** версий (`--numChangelogEntries` по умолчанию 5); более старые версии перемещаются на `CHANGELOG_OLD.md` как только этот файл будет создан. Затем ссылка в нижнем колонтитуле на `CHANGELOG_OLD.md` Этот текст должен оставаться в файле README (это требование инструмента).

5. **Публикация осуществляется с помощью тега.** Тег указывает версию, которая была собрана в CI и опубликована через **доверенную публикацию npm** (без этого подтверждения в npm задача развертывания завершится с ошибкой):

   ```powershell
   git tag v0.0.2                   # mark the approved version
   npm run push:approve             # approval for the tag push
   git push --follow-tags           # push the tag — the CI publishes the package
   ```

   `npm run release <patch|minor|major>` остается доступным в качестве альтернативы: он повышает версию, записывает список изменений и `common.news` и теги за один раз (см. `.releaseconfig.json`, который работает `npm run build` первый).

   **Оба результата сборки должны быть включены в пакет.** Сборка выполняется в рамках задания развертывания. `build/` **и** `www/` перед публикацией (собственной) `build-command`, потому что `build/` и `www/` отсутствуют в репозитории); `npm run check:package` — автоматически перед `npm pack` и `npm publish` через `prepack` — Если один из них отсутствует, релиз завершается с ошибкой. В публикациях до версии 0.0.6 не было никаких данных. `www/` и ответил `/` с `404 not_found`.

6. После каждого этапа проверки версии проверяйте `common.news` тексты на всех 11 языках или запустите `npm run translate` — Проверяющий адаптеры требует их наличия (правило E510). `npm run check:i18n` в отчётах отсутствуют пробелы.

7. **Предварительная проверка (pre-push hook)** автоматически проверяет пункты 1 и 2. Активируйте её один раз для каждой рабочей копии:

   ```powershell
   npm run hooks:install
   ```

   Отправка изменений прерывается, если нет подтверждения для коммита, поля версии различаются, отсутствует список изменений в файле README или его раздел "новый" не содержит ни "В РАЗРАБОТКЕ", ни текущей версии. Пропустите его намеренно. `git push --no-verify`.
