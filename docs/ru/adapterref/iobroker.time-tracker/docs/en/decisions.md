# Решения и отклонения
В этом документе фиксируются решения, отклоняющиеся от первоначальной сферы действия, чтобы их можно было отследить в дальнейшем. Как и другие документы в разделе `docs/`, он также существует на немецком языке ([`../de/entscheidungen.md`](https://github.com/sadam6752-tech/ioBroker.time-tracker/blob/main/docs/de/entscheidungen.md), оригинальный текст); `README.md` - на английском языке (требование программы проверки адаптера).

## D1 - Импорт старых данных из предыдущей системы невозможен (16.09.2026)
**Решение:** Адаптер **не** считывает существующие данные предыдущей системы. Отсутствует импортер, нет пробного запуска и нет отчетов об импорте.

**Что было удалено в результате коммита `184414c` ** (65 файлов, 41 строка добавлена, 3861 удалена):

| Часть | Область применения |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Парсер (`src/lib/legacy/parsers.ts`) | `Data/users.txt`, `Data/group.txt`, `<login>/userdaten.txt` (18 строк на основе индекса), `<login>/absenz.txt`, `Timetable/<year>` (12 строк целевого/балансового значения в часах), `Timetable/<year>.<month>` (время отметки времени прихода/ухода), `Timetable/A<year>` (отсутствия), `Timetable/auszahlungen`, `Timetable/total.txt`, `include/Settings/pausen.txt`, `include/Settings/settings.txt` |
| Импорт (`import.ts`) | сопоставление и нормализация, пробный запуск и реальный запуск, идемпотентность, дубликаты, отчет |
| Интерфейс | вкладка администрирования, команда адаптера (`sendTo`), REST-маршруты, поля `native` (каталог, пробный запуск, повтор) |
| Тестовые данные | `fixtures/smalltime/**` и `tools/make-legacy-fixture.mjs` |
| Происхождение | `docs/provenance.md`, `tools/cleanroom-check.ps1` (см. D3) |
| Происхождение | `docs/provenance.md`, `tools/cleanroom-check.ps1` (см. D3) |

**Последствия**

- Миграции очищают промежуточные состояния: `users.legacy_sha1`, `work_profiles.legacy_source` и

`rfid_tags.legacy_code` вместе с индексом `idx_rfid_legacy` удаляются, если они существуют (`src/lib/db/migrations.ts`).

- **Ни один пользователь не пострадал:** удаление было выполнено 16.09.2026 в 08:18, первая публикация `0.0.4` появилась на npm по адресу

16:32 - В опубликованной версии **ни один** импортер не был указан.

- `time_entries.source` и `EntrySource` по-прежнему знают значение `import`; просто оно больше не создается.
- Таким образом, допустимый уровень импорта «старые данные можно импортировать с помощью пробного запуска» во внутренней спецификации определяется следующим образом:

**намеренно открыто**; проверка принятия в [`test-plan.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/test-plan.md) теперь проверяет только поведение самого адаптера.

**Обоснование:** Импортеру пришлось бы корректировать значение каждого столбца существующих данных; без реальной копии данных эталонной установки это сопоставление было бы лишь предположением - а правила в [`CONTRIBUTING.md`](/#/docs/adapterref/iobroker.time-tracker/CONTRIBUTING.md), раздел 1, запрещают выводить его из стороннего программного кода или его интерфейса. В этом не было необходимости: адаптер начинает работу с пустыми основными данными, администрация сама создает пользователей, рабочие профили и отсутствия. Удаление затронуло 65 файлов и 3861 строку; предыдущее состояние остается доступным через историю (`184414c`).

**Если импорт должен быть восстановлен:** Полное состояние находится в истории Git (`git show 184414c^:src/lib/legacy/import.ts`).
Что потребуется: тестовые данные в `fixtures/smalltime/**` (из реальной установки, **не** полученные из стороннего программного кода), четыре столбца базы данных через новую миграцию, вкладка администрирования, команда адаптера и REST-маршруты.

## D2 - `common.compact: true` (изменено 20.11.2026, ранее: `false`)
**До версии 0.8.1** адаптер работал как отдельный процесс (`common.compact: false`), поскольку он привязывается к собственному HTTP-порту и поддерживает файл SQLite в режиме WAL открытым на протяжении всего времени работы.

**С 20.11.2026** поддерживается компактный режим (рекомендация `S1039` средства проверки репозитория). Проверка кода не выявила ничего, что требовало бы отдельного процесса: каждый таймер является собственным таймером адаптера (`this.setTimeout`/`this.setInterval`, включая пинг WebSocket и ограничение времени SFTP), `onUnload` закрывает HTTP-сервер со всеми его соединениями, а затем и базу данных, отсутствуют `process.env`/`process.exit`/`process.on`, и единственным состоянием на уровне модуля является кэш хешей паролей-приманок, который могут совместно использовать два экземпляра. Адаптеры `web` и `admin` также связывают порты в компактном режиме.

**Стоимость совместного процесса:** better-sqlite3 и хеширование паролей (`scryptSync`) выполняются синхронно. Пока выполняется резервное копирование (`VACUUM INTO`), перерасчет, создание PDF/Excel-отчета или вход в систему, другие адаптеры компактной группы ожидают; сбой собственного модуля завершает работу всей группы. `compact: true` предлагает только выбор: **компактная группа** экземпляра принимает решение - группа `0` поддерживает адаптер в собственном процессе, как и прежде. В файле README рекомендуется группа `0` для слабого хоста или загруженной установки.

Правило «в исходном коде нет `process.env`/`process.exit`» остается в силе (в совместно используемом процессе выход из программы также завершит работу других адаптеров); см. [`adapter-check.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/adapter-check.md).

## D3 - Запись о происхождении данных вне репозитория (16.09.2026)
До 16.09.2026 в репозитории находились `docs/provenance.md` (источник и дата эталонной системы, процедура записи) и `tools/cleanroom-check.ps1` (сравнение текста с эталонной установкой). Оба были удалены коммитом `184414c`, поскольку при использовании импортера (D1) удалялась только та часть, которая затрагивала форматы и идентификаторы предшествующей системы.

**Что остаётся:** В разделе [«Происхождение»](/#/adapters/time-tracker#provenance) документа `README.md` указывается источник, а правила для чистых помещений являются обязательными в [`CONTRIBUTING.md`](/#/docs/adapterref/iobroker.time-tracker/CONTRIBUTING.md) (раздел 1). Сама запись хранится **вне** этого хранилища.

**Если автоматическое сравнение должно завершиться успешно:** Скрипт находится в истории (`git show 184414c^:tools/cleanroom-check.ps1`); он ожидает в качестве параметра пути ссылку на установку (`-LegacyPath`) и сообщает о результатах в виде списка.

## D4 - Резервное копирование из браузера: загрузка через необработанное тело запроса, ограничение на маршрут (17.09.2026)
Администрация могла загрузить резервную копию и восстановить **указанную**. Функции **удаления** и **восстановления загруженного файла** отсутствовали - для обеих требуется одно и то же решение на транспортном уровне: API считывает каждое тело запроса с учетом **общемаршрутизационного** ограничения (2 МиБ), и маршрут пока не мог установить собственное ограничение. Резервная копия превышает это ограничение.

**Решение:** `RouteDefinition` получает необязательный параметр `maxBodyBytes`. Только `POST /backup/restore` устанавливает его (64 МиБ), все остальные маршруты остаются на уровне 2 МиБ - тесты подтверждают оба параметра (большое тело запроса к другому маршруту по-прежнему заканчивается на `413 payload_too_large`).
Веб-сервер читает с тем же ограничением (`MAX_BACKUP_UPLOAD_BYTES`), поскольку транспорт отклоняет тело запроса до того, как маршрут его вообще увидит. _(Изменено в D18: теперь транспорт запрашивает у маршрутизатора ограничение маршрута и предоставляет увеличенное ограничение только авторизованному вызывающему абоненту, который может восстановить маршрут.)_

Загрузка поступает в виде **сырого тела** (`application/octet-stream`), а не в формате Base64 в JSON: браузер отправляет выбранный файл напрямую (`body: file`), сервер сохраняет его для этого типа контента в виде **байтов** вместо текста. Декодирование в UTF-8 привело бы к повреждению двоичных данных; существует проверка с последовательностью байтов, которая не является допустимой UTF-8 (должны быть переданы размер **и** SHA-256). Имя и причина передаются в качестве параметров запроса; имя является лишь меткой для отображения и логирования и очищается до `[A-Za-z0-9._-]` перед сохранением.

**Сигнал безопасности:** Новый файл заменяет ожидающий только **после** его проверки - сначала он записывается как `<…>.part`, проверяется, а затем переименовывается. Таким образом, отклоненный файл оставляет уже поставленный в очередь файл восстановления нетронутым, и наполовину записанный файл никогда не сможет стать базой данных при следующем запуске.

**Удаление:** `DELETE /api/backup/:name` удаляет только файлы, находящиеся в списке (имя извне никогда не попадает в файловую систему), записывает `backup.remove` в аудит и запрашивает подтверждение через интерфейс. Автоматическая ротация остается неизменной и продолжает работать в фоновом режиме.

## D5 - Шкала разрыва от удара или от перелома (17.09.2026)
В учётной записи времени есть столбец «Перерыв», и вычисление было `balance = sum(pairs) − scale − target`. Две вещи в этом были неверными или вводящими в заблуждение:

1. **В столбце не указан фактический перерыв.** Тот, кто отмечает время прихода/ухода/..., образует пары; время между двумя парами составляет

Перерыв. Он отсутствовал в сумме пар («брутто»), но столбец «Перерыв» был заполнен только по шкале перерывов. Результат: тот, кто отмечался полчаса, видел `Break 0:00`.

2. **Дважды был вычтен пробитый разрыв** сразу после применения правила шкалы, кроме того: в общей сумме отсутствовал пробел.

И вот, правило снова было отменено (07:00/13:30/14:00/17:00 дало 9:00 вместо 9:30).

**Решение:** Теперь расчет начинается с **наличия** (от первого удара до последнего завершенного удара) и вычитается ровно один разрыв:

| Режим (`pause_mode`) | Разрыв столбца | Время работы |
| `auto` (по умолчанию) | перфорированный разрыв, в противном случае масштаб | наличие − разрыв |
| `punched` | только пробитый разрыв (`0:00` если ничего не было пробито) | наличие − разрыв |
| `staffel` | только правила шкалы | присутствие − нарушение |
| `staffel` | только правила гаммы | присутствие − перерыв |

Весы остаются тем, для чего предназначены: фиксированным перерывом в дни, когда никто не отмечается на работе. День с **открытой** отметкой еще не имеет окончательного перерыва - весы применяются и в этот день.

**Оплачиваемый перерыв:** Новое поле `work_profiles.pause_paid_minutes` (миграция 13) с числовым полем в рабочем профиле каждого сотрудника: **оплачивается именно столько минут перерыва в день** (`0` = не оплачивается вовсе). Значение `1440` означает оплату перерыва любой продолжительности; компания, оплачивающая только четверть часа, вводит `15`. Оплаченные минуты добавляются к рабочему времени, остальная часть перерыва остается вычетом - в столбце «Перерыв» по-прежнему отображается **весь** перерыв, чтобы отчет оставался понятным. (Первоначально это был переключатель «да/нет»; миграция 13 меняет его: «оплачивается» становится `1440`.)

**Примечание:** Изначально не было возможности поддерживать шкалу перерывов - в таблице `pause_rules` не осталось записей (импорт данных был прерван с D1), поэтому правила в новой установке были пустыми, и «перерыв» всегда был `0:00`. С последнего раунда появились `GET`/`PUT /api/pause-rules` (справа `settings.edit`) и редактор на вкладке **Настройки**: правила с параметрами «с минут / до минут / минуты перерыва» и переключатель для каждого правила; вызов заменяет всю таблицу, отсутствующие правила удаляются.

**Доказательство:** В ведомости учета рабочего времени рядом с пунктом «Перерыв» указана колонка **«из которых оплачено»** (`day_aggregates.paid_break_min`, миграция 14) с суммой - таким образом, в PDF-файле и файле Excel показано, какая часть перерыва была оплачена.

## D6 - Только администрация меняет время, отмечает сотрудник в этот день (24.09.2026)
Тот, кто может изменить время, может и придумать рабочее время. До этого момента пользователь `employee` мог изменять и добавлять **собственные** отметки времени в окне редактирования (`edit_window_days`, по умолчанию 7 дней); в режиме просмотра месяца карандаш открывал именно это диалоговое окно. Две вещи здесь были неверны:

1. **Диалог выбора месяца не был привязан к сотруднику.** `DayCorrectionsDialog` запрашивал отметки времени **без** `userId`.

(`api.entries(date, date)`), поэтому сервер использовал собственную учетную запись - и `createEntry` записал данные с помощью `userId: session.user.id`. В месяце сотрудника (`/month?userId=…`) администрация, следовательно, отобразила и изменила его **собственные** отметки времени; функция «Добавить отметку времени» создала отметку времени в собственной учетной записи.

2. **Время - это не дело сотрудника.** Забытое отметка времени - это **сообщение**, а не исправление: сотрудник

Зная, что они забыли, администрация оформляет бронирование.

**Решение:** Время принадлежит администрации, **отмечает** сотрудник.

| Роль | Карандаш в этом месяце | Содержание диалога |
| ----------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `admin`, `manager` (`time.edit_other`) | собственный месяц и месяц сотрудника | отметки времени: добавить, изменить время, удалить (`time.delete`), **причина** для журнала - привязана к сотруднику, чей месяц открыт |
| `сотрудник` | только за свой месяц | **заметка за день** («забыл отметить время прихода/ухода»), больше ничего |

На сервере, расположенном за ним: `POST /api/entries` (ручной ввод) и каждая настройка `tsUtc` в `PATCH /api/entries/:id` требует `time.edit_other`; собственная отметка теперь может быть только **закомментирована** (`note`). `DELETE` остается `time.delete`. Отметка продолжается до `time.punch` (`/punch`, `/punch/quick`, офлайн-очередь `/entries/sync`).

**Примечанию** нужно отдельное место, потому что именно для дня, **не** отмеченного**, оно и предназначено: таблица `day_notes` (миграция 25, одна запись на сотрудника и день) с `GET`/`PUT /api/day-notes` (собственные дни с `time.edit_own`, другие дни с `time.edit_other`; пустой текст удаляет) и `POST /api/day-notes/handled` - администрация отмечает примечание как **выполненное**, оно остается видимым. Месяц отмечает день с примечанием (символ рядом с балансом): открыто = желтый, выполнено = серый.

**Административная учетная запись не выполняет функцию отметки времени:** Она создается при установке и никому не принадлежит, она управляет сотрудниками. Поэтому роль `admin` теряет `time.punch` (начальная и миграционная версия 26); тот, кто также работает, получает права обратно через роль `employee` (права доступа являются объединением ролей). `manager` продолжает отмечать время и исправлять ошибки. На стартовой странице учетной записи без права отметки времени объясняется, для чего она нужна.

**Влияние на окно редактирования:** Осталась проверка, к которой больше никто не мог получить доступ: `requireInsideEditWindow` отклонял собственные отметки вне `edit_window_days` - но после этого решения изменить свое время мог только тот, у кого есть `time.edit_other`, и для него проверка завершалась преждевременно. Поэтому она удаляется (вместе с проблемой `edit_window_closed`). Настройка остается и работает ровно в одном месте: в **офлайн-очереди** - отметка, поступившая старше `edit_window_days`, сохраняется как конфликт `too_old` и учитывается только тогда, когда администрация ее принимает.
`GET /entries/conflicts` принимает `?userId=` за это, так что администрация видит очередь сотрудника.

## D7 - Всегда присутствует активный администратор (24.09.2026)
Администратор может лишить себя права администрирования. К этому ведут два пути: **деактивация** собственной учетной записи (специальное правило уже помогало предотвратить это - `PATCH /users/:id` и `DELETE /users/:id` отклоняют это, поскольку запущенная сессия сразу же завершится) и **удаление роли `admin` ** через диалоговое окно ролей. Второй способ был незащищенным: тот, кто является последним активным администратором и забирает роль, впоследствии ничего не может управлять - сотрудники, роли, терминалы, настройки и резервные копии зависят исключительно от этой роли. Восстановить права можно было только путем перезапуска экземпляра с **свободным** `adminLogin` (`ensureAdministrator` создает администратора только в том случае, если нет **активного**, и завершается ошибкой `LoginExistsError`, если занят настроенный логин).

**Решение:** Изменение, которое приведет к отсутствию активного администратора в системе, отклонено - проблема `last_administrator`, статус 409. Правило проверяет **оба** поля одновременно (`isActive` и `roleKeys`), поскольку запрос может установить оба поля, и учитывает только **активные** учетные записи: деактивированный администратор никому не поможет.

| Ситуация | Результат |
| ---------------------------------------------------------------------- | ------------------------------------------------ |
| Последний активный администратор деактивирован | 409 `last_administrator` |
| Последний активный администратор теряет роль / `roleKeys: []` | 409 `last_administrator` |
| деактивировать собственный аккаунт | 400 `ValidationError` (правило собственное, без изменений) |
| деактивировать собственную учетную запись | 400 `ValidationError` (собственное правило, без изменений) |

`DELETE /users/:id` также деактивирует учетные записи, но требует `user.deactivate` - это требование действует только для роли `admin`, поэтому вызывающая сторона сама является активным администратором, и целевая сторона никогда не является последней. Таким образом, правило присутствует только в `PATCH`; комментарий в этом месте это подтверждает.

**Интерфейс предупреждает перед этим:** При переключении **собственной** учетной записи в диалоговом окне объясняется, почему ее нельзя деактивировать, вместо отправки запроса, который будет отклонен. Для последнего активного администратора в диалоговом окне ролей сообщается, что роль нельзя отозвать, и отключается кнопка «Сохранить», пока отсутствует галочка; для любой другой собственной учетной записи отображается только предупреждение о том, что все права администратора исчезают одновременно. Сообщение сервера отображается как `error.last_administrator` на всех одиннадцати языках.

**Доказательство:** `src/lib/web/routes/users.test.ts` («сохраняет последнего активного администратора на месте»: второй администратор, отказ для последнего, успех, как только другой администратор займет эту роль), `test/e2e/users.spec.ts` (предупреждение в собственном аккаунте, отключенное сохранение, неизмененное состояние).

## D8 - Календарь передается в ioBroker в виде ленты и состояния (24.09.2026)
Персональная ссылка ICS из версии 0.5.0 (`POST /calendar/token` → `GET /calendar.ics?token=…`) предназначена для сотрудников: она отображает **одного** человека и вносится в календарное приложение. | Данные | `calendar.absences` (JSON) и `calendar.updatedAt` | скрипты, Blockly, VIS |
| Данные | `calendar.absences` (JSON) и `calendar.updatedAt` | скрипты, Blockly, VIS |

Файл намеренно находится в `files/`, а не в соседней папке экземпляра: прочитать его может только адаптер, тогда как экземпляр `web` предоставляет `files/` для скачивания (`http://<host>:8081/files/time-tracker.0/calendar.ics`). **Ссылка** должна находиться ниже префикса `/api` - без него браузер получает веб-интерфейс со своим логином вместо календаря (`companyFeedUrl` в `src/lib/services/calendar.ts` это фиксирует, процедура проверяется).

_(Дополнение от 25.09.2026: вариант с файловым сервером оказался нежизнеспособным - см. **D11**. В корпоративном календаре имя сотрудника стоит первым (`Anna Muster: Vacation (F)`), чтобы день оставался читаемым в корпоративном календаре; `UID` остается `absence-<id>@time-tracker`, чтобы календарное приложение **обновляло** событие, а не дублировало его.

## D9 - Исходный код веб-приложения называется `src-www/` (24.09.2026)
Программа проверки репозитория считывает исходный код репозитория и проверяет импортированные пакеты на соответствие корневому каталогу `package.json` (`W5042`). Пропускаются только папки из **фиксированного** списка (`excludedSourceDirs` в `lib/M5000_Code.js`): `/admin`, `/build`, `/docs`, `/test`, `/tools`, `/www`, `/widgets`, `/src-admin`, `/src-www`, `/src-vis`, `/src-widgets` и другие.

`src-pwa/` **не** был в этом списке, поэтому в запросе на слияние для ПОСЛЕДНЕГО репозитория было указано пять `W5042` (react, MUI, i18next, `@tanstack/react-query`, `react-i18next`) и требовалось принять решение до проверки: учитываются только `dependencies` - `@types/*` и `@iobroker/types` являются единственным исключением, которое может находиться в `devDependencies`.

**Решение:** Исходный код веб-приложения находится в ** `src-www/` ** (перед `src-pwa/`). Папка есть в списке проверяющей программы, по имени соответствует доставке из `www/`, а зависимости приложения остаются в `src-www/package.json`: они не должны входить в установку адаптера, поскольку ничего не загружается из исходного кода во время выполнения - `npm run build:pwa` помещает готовый пакет в `www/`. Другой вариант (перемещение react, MUI и i18next в корневой каталог `package.json`) обеспечил бы каждую установку ioBroker вторым стеком фронтенда и был бы по существу неправильным. С точки зрения функциональности преобразование ничего не меняет: адаптер по-прежнему предоставляет `www/`, все скрипты и рабочие процессы просто указывают на новый путь.

**Доказательство:** `npm run check`, `npm run lint`, `npm run build`, `npm run build:pwa`, `npm run test:ts`, `npm run test:package`, `npm run check:adapter`, `npm run check:i18n` и `npm run version:check` отмечены зеленым цветом; подтверждение - **T22** в [`test-plan.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/test-plan.md).

## D10 - Автоматическое правило может иметь период действия (24.09.2026)
Раньше правило действовало до тех пор, пока кто-нибудь его не выключил. Для постоянного правила это правильно - но для замены на время отпуска, сезонного работника или на период проекта это не так: в этом случае правило начинается и заканчивается само собой, и никому не нужно об этом помнить.

**Решение:** Каждое правило содержит два необязательных поля даты `active_from` и `active_until` (миграция 27). Оба поля представляют собой **простые даты** (`YYYY-MM-DD`), намеренно без указания времени суток: само время в правиле уже указано как минута местного дня, а окно с указанием времени суток вызвало бы вопрос о часовом поясе (правило применяется *для каждого сотрудника* локально). Поэтому сравнивается **местная календарная дата сотрудника** (`local.date` в `runAutomationRules`) - именно тот день, с которым работают будние дни и маркер в `automation_runs`. Ничего не нужно конвертировать: «действительно до 15.10.» означает для каждого сотрудника 15 октября по месту его работы, и изменение дня в полночь не приводит к сбоям.

Оба конца **включают** друг друга; пустое поле - это открытая сторона: «действительно с пустого» = с настоящего момента, «действительно до пустого» = неограниченно. Значение выбора «с настоящего момента» не могло быть сохранено: его пришлось бы преобразовывать в фиксированную дату при сохранении, и тогда оно выглядело бы как намеренно установленное ограничение. Интерфейс по-прежнему отображает значение: поля содержат «Пусто = с настоящего момента» и «Пусто = неограниченно», а в списке правил для ограниченного правила отображается «действительно с…», «действительно до…» или «действительно … - …».

Проверка окна производится в `evaluateAutomation` (чистая функция, сразу после проверки дня недели) - поэтому решение и его причина находятся в журнале отладки и могут быть проверены без адаптера. Истекшее окно **не** является ошибкой; сохранение остается разрешенным, иначе старые правила больше нельзя было бы изменить. Окно **не** сбрасывает маркер в `automation_runs`: правило по-прежнему срабатывает не более одного раза за период (день или ISO-неделя), и если время действия правила за первый день находится до «действительно с», этот день пропускается и не компенсируется.

**Доказательство:** `src/lib/adapter/automation.test.ts` (день до, точно «с», точно «до», день после, оба конца пустые), `src/lib/db/repositories/automations.test.ts` (сохранить и прочитать, «опустить сохраняет», «пусто очищает», 30.02. отклоняется, «до перед с» отклоняется), `src/lib/web/routes/settings.test.ts` (даты перемещаются в соответствии с правилом, 400 для недействительной даты) и принятие **T23** в [`test-plan.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/test-plan.md). Список под таблицей был **удален** (ранее он был ограничен пятью записями): `GET /automation-rules/runs` предоставляет одну строку **на каждое правило** (самое новое, вплоть до `latestRuns`), и строка правила записывает ее в отдельную строку - см. **D12** в этом документе и **T25** в [`test-plan.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/test-plan.md).

## D12 - В обзоре правил указан последний запуск каждого правила (26.09.2026)
**Примечание:** Список «Последние запуски» под таблицей правил представлял собой журнал, не имеющий отношения к правилам: в нем отображались пять самых новых строк всех правил, и правило, которое не запускалось в течение недели, в нем больше не появлялось.

**Решение:** Список удален. `GET /automation-rules/runs` предоставляет **одну строку на правило** вместо самых новых строк (самый новый запуск; `latestRuns()` в репозитории использует правило SQLite, согласно которому при наличии ровно одной агрегатной функции (`MAX`) остальные столбцы берутся из соответствующей строки), и строка правила указывает это в отдельной строке (`Last run: … · employee`, в противном случае `never run`). Кроме того, рядом с «Сохранить правила» отображается подсказка о том, что таблица сохраняется **всё целиком** - до этого момента изменения будут внесены только в форму.

**Кстати:** Правило, работающее **все семь** дней, дважды записывало одно и то же в свою строку («один раз в день» - из-за будних дней и из-за повторения). Теперь поле для будних дней остается пустым, когда нет никаких ограничений - так же, как и поле для проверки действительности, которое также появляется только тогда, когда оно установлено.

**Доказательство:** `src/lib/db/repositories/automations.test.ts` («сообщает об одном запуске на каждое правило - самое новое»), `src/lib/web/routes/settings.test.ts` (ответ содержит одну строку на каждое правило) и **T25** в [`test-plan.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/test-plan.md).

## D13 - Запрос на отмену, а не бронирование без подтверждения (26.09.2026)
**Ситуация:** Утвержденный отпуск сотрудник не мог изменить или отменить самостоятельно; удалить его могла только администрация, а в приложении такой возможности не было. Случаи, например, «отпуск все-таки перенесен на другую неделю», оставались на уровне ручной обработки.

**Решение:** Удаление утвержденного отгула - решение администрации. Сотрудник **запрашивает** аннулирование (`POST /absences/:id/cancellation`, причина необязательна в `cancel_note`); отгул **продолжает учитываться**, поскольку `isApproved` зависит только от `approval`. Администрация отвечает существующим `DELETE /absences/:id` - то есть «да», и удаление влечет за собой `cancelRequested: true` в деталях аудита - или `POST /absences/:id/cancellation/decline` («нет», причина в аудите). Сотрудник отзывает **открытый** запрос самостоятельно (`DELETE /absences/:id/cancellation`); он может удалить свою строку в любом случае. Если сотрудник меняет утвержденное отсутствие, продолжает действовать прежний порядок: возвращается к `requested`, и ожидающая отмена прекращается вместе со старым решением (`setApproval` ее подтверждает).

Две причины для этой модели: `approval` содержит `CHECK` из миграции 21, другое состояние (`cancelled`) потребовало бы перестроения таблицы в соответствии с правилами SQLite - столбцов `cancel_requested_at` и `cancel_note` (миграция 28) достаточно, и `isApproved` остается неизменным. И отмена, исчезающая без ответа, больше не могла бы быть отличима от ошибки данных в аудите.

**Доказательство:** `src/lib/db/repositories/absences.test.ts` (запрос продолжает подсчитываться, отзываться и отклоняться, записывать действия аудита `absence.cancel_request`/`_withdraw`/`_decline`, отменять можно только утвержденные отсутствия, решение разрешает ожидающую отмену), `src/lib/web/routes/absences.test.ts` (запрос, разрешения, отзыв, отказ, 400 для отсутствия, которое еще не утверждено) и принятие **T26** в [`test-plan.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/test-plan.md).

## D11 - Файловый сервер недоступен для просмотра календаря (25.09.2026)
При повторной проверке T21 выяснилось, что загрузка через экземпляр `web`, обещанный в D8 и в README, **не** работает: `http://<host>:8081/files/time-tracker.0/calendar.ics` не доставляет файл, а очевидный способ без номера экземпляра (`…/files/time-tracker/calendar.ics`) доставляет **пустой ZIP-архив** (22 байта, `PK\x05\x06`). Таким образом, запрос попадает в общедоступную веб-область, а не в папку экземпляра; то есть, календаря нет.

**Решение:** Файловый способ **больше не** предлагается для скачивания. `calendar.feedFile` остается тем, чем он является - **абсолютным путем** к записанному файлу, который адаптер `ical` считывает как локальный файл (проверено в тесте, все в порядке). Для браузеров, календарных приложений и скриптов используется `calendar.feedUrl`: ссылка адаптера на токен экземпляра, которая предоставляет тот же самый, полный файл. Теперь это указано в файле README, плане тестирования и строке таблицы состояний (последняя явно называет `feedFile` *путем*).

Два вопроса остаются открытыми, и мы намеренно не стали их решать:

- **Запись:** Файл перезаписывается с помощью `writeFileSync` при каждом изменении и каждые пять минут - сначала пустым, затем записывается.

Читатель, считывающий данные именно в этот момент, может обработать половину файла. Атомарная запись была бы надежной (сначала `calendar.ics.tmp`, затем `rename`); острой проблемы нет, поскольку адаптер `ical` считывает данные с интервалом в несколько минут.

- **Видимость:** Все, что находится ниже `<iobroker-data>/files/…`, доступно через веб-экземпляр **без авторизации**.

Таким образом, корпоративный календарь находится в общедоступной папке, хотя для доступа через API требуется токен. Тот, кто этого не хочет, может переместить файл обратно в папку экземпляра (`<iobroker-data>/time-tracker.<n>/`) - адаптер `ical` всё равно будет считывать его оттуда.

**Доказательство:** **T24** в [`test-plan.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/test-plan.md) (ссылка предоставляет полный файл ICS, адаптер `ical` считывает `calendar.feedFile`, в README и документации больше не указана ссылка на файловый сервер) и измененный раздел *Календарь для ioBroker* в README.

Файловому менеджеру известно только то, что создано через файловый API (вызов также создает папку); папка, созданная с помощью `fs`, остается для него внешней папкой. Абсолютный путь для `calendar.feedFile` остается прежним; адаптер `ical` по-прежнему читает локальный файл.

До тех пор ссылка не будет упоминаться в README и документации, а `calendar.feedUrl` используется для браузеров, календарных приложений и скриптов. Вторая открытая точка - **атомарная запись** - остается открытой: `writeFileAsync` также сначала записывает пустой файл, а затем полный.

**Дополнение (27.09.2026, 0.7.12):** Путь 0.7.11 был **направлен неправильно**, и это выявилось при приемке. В журнале реальной установки было указано:

```
error Cannot write file INFO.txt: time-tracker.0 is not an object of type "meta"
warn  the folder 'files/time-tracker.0' could not be prepared: time-tracker.0 is not an object of type "meta"
error Cannot write file calendar.ics: time-tracker.0 is not an object of type "meta"
```

`writeFileAsync(<namespace>, …)` отклоняется базой данных объектов. В документации ioBroker *Сохранение файлов* в руководстве разработчика объясняется причина: файлы **всегда** зависают на объекте типа `meta` - **точке монтирования** - и запись происходит **ниже** него (`writeFileAsync(mountPoint, "file", …)`). Пространство имен экземпляра не является точкой монтирования; оно принадлежит объекту экземпляра `system.adapter.time-tracker.0`. Проверка `validateMetaObject` в `objectsInRedisClient` выдает ошибку не только при наличии объекта неправильного типа, но и в случае отсутствия объекта вообще - папка, созданная вручную в файловом менеджере, все равно заняла бы это имя.

**Решение:** Теперь файл зависает на `<namespace>.storage` (`type: "meta"`, `common.type: "meta.folder"`), путь - `files/time-tracker.<n>/storage/calendar.ics`. Имя - `storage`, а не `calendar`, потому что `calendar` в дереве объектов уже является каналом состояний календаря (`calendar.feedUrl` и его аналоги), а объект не может быть одновременно каналом и точкой монтирования. `meta.folder` вместо `meta.user`: адаптер перезаписывает файл при каждом запуске и каждом изменении, поэтому он **не** должен находиться в резервной копии данных. Точка монтирования создается в начале (идемпотентно через `setObjectNotExists`, как и остальная часть дерева объектов) - намеренно **не** через `instanceObjects` в `io-package.json`, потому что его одноязычное имя открыло бы второе место для тех же одиннадцати текстов. Файл подсказок `INFO.txt` удаляется: теперь открыта не папка, а сам объект. А календарь теперь публикуется в собственном блоке `try` (`the calendar could not be written: …`) - в версии 0.7.11 он работал в блоке состояния, поэтому в журнале появилась ошибка файла `states could not be published`, скрывающая истинную причину.

**Доказательство:** `src/lib/adapter/calendarFile.test.ts` (файл зависает в точке монтирования и **никогда** не в самом пространстве имен, объект создается ровно один раз как `meta.folder` с одиннадцатью языками, абсолютный путь заканчивается на `files/time-tracker.0/storage/calendar.ics`), `src/lib/adapter/states.test.ts` (каждое имя объекта на одиннадцати языках) и два места в `src/main.ts` (`onReady`, `publishCalendar`).

**Доказательство установки (27.09.2026, T28):** В версии 0.7.12 лог не содержит ошибок, файловый менеджер отображает папку `time-tracker.0` → `storage` с `calendar.ics` внутри, а загрузка выдает файл с корректным содержимым - проверка пройдена. **Файловый сервер** теперь тоже доставляет файл: прямая ссылка `http://<host>:8081/files/time-tracker.0/storage/calendar.ics` (то есть, **ниже** точки монтирования) проверена, загруженный файл без ошибок. Старый путь без `storage` (`…/files/time-tracker/calendar.ics`) остается недоступен - по нему по-прежнему приходит пустой ZIP-архив. Это также объясняет, почему ссылка исчезла из документации и из T21 в версиях 0.7.7/0.7.8: неправильным был не файловый сервер, а сам путь.

## D17 - HTTPS в самом адаптере с использованием сертификатов ioBroker (01.10.2026)
**Повод:** Приложению на телефоне требуется HTTPS (сервис-воркер, установка). До сих пор существовал только способ через обратный прокси (`trustProxy`). Адаптер `web` от ioBroker **не** может помочь в этом случае: он не перенаправляет сторонний порт, а лишь предоставляет адаптеры, которые подключаются к нему как веб-расширение - у системы отслеживания времени есть собственный сервер (`http.createServer`). Работа: локальная установка без доступа из интернета.

**Решение:** Сервер может использовать HTTPS самостоятельно (`https.createServer`). Новые настройки экземпляра: `secure` (переключатель) и **имена** `certPublic`, `certPrivate`, `certChained` из коллекции сертификатов ioBroker (`getCertificatesAsync`, в виде типа `certificate`). Собственного управления сертификатами нет, и пути к файлам отсутствуют. Ключ намеренно называется `secure`: администратор извлекает из него заполнитель `%protocol%` для ссылки в списке экземпляров (`common.localLinks`), поэтому ссылка без лишних сложностей становится `https://…`. Это чистое изменение транспортного протокола: маршруты, разрешения, CSRF и ограничения остаются неизменными.

**Последствия**

## D18 - Правило может срабатывать при каждой записи, а карта значений указывает имя сотрудника (07.10.2026)
**Повод:** Проверка адаптера на соответствие адаптеру `ioBroker.fingerprint` (пункты A1/A2 внутреннего анализа кода): Правило срабатывает только при изменении **значения** состояния. Адаптер отпечатков пальцев записывает одно и то же имя при каждом совпадении (`lastMatch.name`) и оставляет `lastMatch.matched` равным `true` - тот, кто сканировал отпечаток в одиночку утром и вечером, **не** отмечался как уволенный вечером. А `lastMatch.id` - это **номер слота** отпечатка пальца (1-200), а не идентификатор сотрудника; режим «Значение - это сотрудник» сначала считывал числа как идентификатор сотрудника.

**Решение:** (1) Новое свойство правила `fireOnRepeat` («срабатывает при каждой записи»): по умолчанию **включено** для режима `user`, **выключено** для фиксированного значения; миграция 29 включает его для существующих правил режима `user`. Время ожидания и защита от двойных нажатий (30 секунд) остаются неизменными и позволяют обнаружить устройство, активно использующее голосовую связь. (2) Новое свойство правила `valueMap` (значение → employee, JSON в `value_map`). Если правило имеет карту, срабатывает только значение из нее; все остальное не срабатывает - даже если число случайно является идентификатором сотрудника. Без карты сохраняется старое поведение (идентификатор, логин или отображаемое имя).

**Преднамеренно не реализовано:** Разрешение «номер = идентификатор сотрудника» остается без сопоставления, поэтому скрипты, записывающие идентификатор, продолжают выполняться; форма и файл README называют это ловушкой.

**Связанные моменты (B1/B2 того же обзора):** Транспорт считывает тело запроса с ограничением **маршрута** и только после проверки сессии, если маршрут содержит более высокое ограничение (восстановление резервной копии); тело запроса, содержащее больше информации, чем лимит, отклоняется без прочтения. Для ввода данных, который может отправить любой пользователь без авторизации, действуют ограничения по длине; имя пользователя и пользовательский агент хранятся в сокращенном виде; строки аудита неудачных и заблокированных входов в систему удаляются через 90 дней (все остальные сохраняются).

**Доказательство:** `src/lib/adapter/triggers.test.ts`, `src/lib/db/repositories/triggers.test.ts`, `src/lib/web/server.test.ts`, `src/lib/services/auth.test.ts`, браузерный тест `test/e2e/triggers.spec.ts`.

### Дополнение D18 (07.10.2026): A3, B3, B4, B5, C1 того же обзора
- **B3 - Источник прямой трансляции:** Соединение браузера с cookie отклоняется (403 `origin_not_allowed`), если `Origin`

не соответствует `Host` запроса (за доверенным прокси-сервером также учитывается `x-forwarded-host`). Токен в URL и клиенты без `Origin` (интеграции) не затрагиваются. Причина: `SameSite=Lax` разделяет страницы разных *сайтов*, а не сервисы одного и того же хоста на другом порту.

- **B4 - Заголовки безопасности веб-приложения:** `Content-Security-Policy` (собственные скрипты, без встроенных скриптов,

`frame-ancestors 'none'` (встроенные стили разрешены, поскольку библиотека компонентов записывает их во время выполнения), `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`; с собственным TLS дополнительно `Strict-Transport-Security` (180 дней, без `includeSubDomains`). За прокси-сервером прокси отправляет заголовок HSTS.

- **B5 - Блокировка входа в систему:** подсчитывается по **имя и адресу** (ограничение как и раньше) и по имени по **всем** адресам (пять)

(в раз больше). Тот, кто вводит имя администратора, блокирует только свой собственный адрес; тот, кто угадывает имя из множества адресов, блокирует учетную запись. Неизвестное имя вычисляется по ложному хешу той же стоимости, так что время ответа не позволяет его выдать. **Не изменено:** `scryptSync` блокирует процесс примерно на 50 мс за попытку; ограничение на адрес (20 попыток в минуту) поддерживает это значение на низком уровне.

- **A3 - Обратная связь с устройством:** Адаптер не взаимодействует с устройством чтения; каждый перфорированный фрагмент линейки отображается сразу же

`events.*` (`lastUser`, `lastDirection`, `lastSource`). В файле README это описано с примером скрипта и указанием того, что отображается в журнале при сканировании без ввода данных.

- **C1 - Пример README:** `fingerprint.0.lastMatch` не существует; в README указаны `lastMatch.name`, `lastMatch.id` (с

карта значений) и причина, по которой `lastMatch.matched` не подходит.

## D21 - Каждая резервная копия копируется на внешний сервер по протоколу SFTP (13.10.2026)
**Ситуация:** Резервная копия базы данных была потеряна вместе с хостом. Вкладка «Миграция и резервное копирование» в настройках экземпляра не позволяла получить копию с машины. Аналогичный адаптер `e-invoices` решил эту проблему накануне; здесь используется та же схема.

**Решение:**

1. **SFTP с использованием `ssh2` ** (чистый JavaScript, без системных инструментов, без монтирования, без `sudo`). Файл загружается как `<name>.part`, его

Размер файла сравнивается, и только после этого он переименовывается, поэтому файл, размер которого неполный, никогда не будет выглядеть как резервная копия (`src/lib/services/remoteBackup.ts`, реальное соединение в `sftpSsh2.ts`).

2. **Один хук для каждого способа создания резервной копии.** `BackupDeps.onCreated` запускается после каждой резервной копии (приложения, `commands.backup`, `sendTo`,

ежедневное расписание); сбой в обработчике никогда не превратит хорошую локальную резервную копию в ошибку. Адаптер копирует оттуда.

3. **Ключ хоста может быть зафиксирован** (`SHA256:…`): другой отпечаток будет отклонен до отправки пароля. Пустое поле означает

Не подтверждено; в журнале и на кнопке проверки отображается отпечаток пальца для ввода.

4. **Удаление на сервере ограничено.** Удаляются только файлы с именем `time-tracker-<time>.sqlite` (самые старые из которых превышают _количество копий для сохранения_).

Остатки `0` = все) и `….sqlite.part` удаляются. Другие имена (включая `time-tracker-prerestore-…`) остаются нетронутыми.

5. **Неудачное копирование видимо и безвредно**: оно регистрируется в журнале аудита (`backup.remote_copy`,

`backup.remote_copy_failed`) и показан в `info.remoteBackupError`; `info.lastRemoteBackup` содержит последний работоспособный файл. Копии выполняются одна за другой и имеют ограничение по времени.

6. **Пароль: `encryptedNative` и `protectedNative`.** Для проверки соединения используются значения из несохраненной формы и

Функция использует сохраненный пароль только для того же сервера, пользователя и порта, поэтому кнопку нельзя использовать для отправки сохраненного пароля на другой сервер.

**Доказательство:** `src/lib/services/remoteBackup.test.ts` (копирование, проверка размера, срок хранения, остатки, ограничение по времени, настройки теста), `src/lib/services/sftpSsh2.test.ts` (проверка на реальном SFTP-сервере в процессе, отпечаток), тест на перехват в `src/lib/services/backup.test.ts`.

## D22 - Тела запросов проверяются с помощью zod (18.10.2026)
**Случай:** Каждый маршрут считывал своё тело с помощью небольших рукописных полей (`requireString`, `optionalNumber`, …) и проверял остальное вручную. Это работало, но маршрут с первого взгляда не показывал, какие поля он принимает, и останавливался на первом же недопустимом поле.

**Решение:**

1. **zod 4** проверяет тело каждого маршрута на границе. Маршрут объявляет свое тело как объект правил поля.

(`bodySchema({ login: requiredText(128), … })` в `src/lib/web/routes/validate.ts`) и считывает введенные значения с помощью `parseBody`.

2. **Сообщения остаются прежними.** Каждое правило формулирует свое сообщение так же, как и сообщение в замененном им ридере («требуется вход в систему»).

`direction must be in, out or auto (got x)`, …), поэтому веб-приложение и клиенты не видят никаких изменений. Тест закрепляет формулировку.

3. **Каждое недопустимое поле сообщается** в массиве `errors[]` (RFC 9457); сообщение о проблеме - это сообщение, относящееся к первому полю.
4. **Что означает отсутствующее поле, остается неизменным:** необязательное поле становится `null`, полем изменения, которое не отправляется.

остается `undefined` (`keepMissing`, запись сохраняет свое значение), число в тексте по-прежнему берет то место, где оно было раньше (`employeeRef`, `year`). zod отклоняет отсутствующий ключ для некоторых типов схем; каждое правило проверяется с отсутствующим полем.

5. **Проверки, требующие доступа к базе данных, остаются в маршруте** (существует ли сотрудник, может ли вызывающий абонент это сделать). Два места сохраняют

Их собственное толкование, сделанное намеренно: `PUT /settings` - это свободное хранилище ключ/значение с правилом для каждого ключа, а сессия терминала берется из тела запроса.

6. zod привязан к версии, которая старше, чем время ожидания Dependabot (7 дней) на момент его добавления.

**Доказательство:** `src/lib/web/routes/validate.test.ts` (сообщения, все недопустимые поля, отсутствующие поля, вложенные пути) и тесты API в `src/lib/web/routes/*.test.ts`, которые выполняются без изменений.
