#<img src="../../admin/senec.png" width="36" align="top" alt=""> ioBroker.senec
## Адаптер SENEC для ioBroker
Контролируйте и управляйте вашей домашней системой хранения данных SENEC. Адаптер поддерживает четыре независимых разъема, которые можно использовать по отдельности или в комбинации:

- **Локальный** (lala.cgi) — Прямой запрос к локальной сети с данными в реальном времени с интервалом в 10 секунд. Предоставляет полные данные BMS, показания сетевых счетчиков, данные настенного блока и управление устройствами.
- **API приложения SENEC** — Запросы через API приложения SENEC на основе облачных технологий. Данные панели мониторинга, история измерений, сведения о системе и информация о настенном блоке.
- **mein-senec.de** — Запрос через веб-портал. Обзор состояния, история измерений, автономность, аварийное электропитание, сглаживание пиковых нагрузок, готовность к использованию энергосберегающих устройств (SG-Ready) и управление переключаемыми розетками.
- **SENEC.Connect** — API на базе Azure. Данные о батарее и счетчиках передаются по ключу подписки.

Не все коннекторы обязательно должны быть активированы. Выбирайте в соответствии с вашими потребностями — чисто локальные настройки работают так же хорошо, как и чисто облачные конфигурации для систем без локального веб-интерфейса.

### Поддерживаемые системы
Практически все системы хранения данных SENEC совместимы: серия Home, начиная с ранних моделей на свинцовом и литиевом топливе, включая V2, V2.1 и V3, и заканчивая текущим поколением V4 | P4 | E4, а также бизнес-модели и варианты от партнеров ADS Tec, OEM LG и Solarinvert.

Системы с локальным веб-интерфейсом могут использовать все четыре коннектора. Системы без него, включая поколение V4, работают через API приложения SENEC, mein-senec.de и SENEC.Connect. Доступные точки данных зависят от модели.

[полный список моделей](../SUPPORTED_SYSTEMS.md) помогает снова найти свою систему.

## Требования
- ioBroker с Node.js >= 22
- Система хранения данных SENEC в локальной сети (для локального коннектора)
- Аккаунт my-senec.de (для API и веб-коннектора)
- Установлен адаптер ioBroker.web (для интегрированной панели управления)

## Установка
Установите адаптер через репозиторий адаптеров ioBroker. После установки создайте экземпляр адаптера и настройте как минимум один коннектор.

#### Двухфакторная аутентификация (2FA)
Если для учетной записи mein-senec.de активирована двухфакторная аутентификация, адаптер все равно сможет автоматически входить в систему — никому не нужно будет сидеть рядом с ним и вводить код.

В процессе настройки отобразится QR-код приложения-аутентификатора, а также тот же секретный ключ в текстовом виде. Этот текст следует записать в поле **Секретный ключ TOTP**. Запишите его, пока открыта страница настройки: После активации секретный ключ больше не будет отображаться; новый будет сгенерирован только при повторной настройке. Пробелы и дефисы в тексте не имеют значения.

Речь идёт о постоянном секретном ключе, а не о шестизначном коде из приложения — он меняется каждые тридцать секунд и истек бы задолго до того, как адаптер смог бы его использовать.

Для обоих облачных коннекторов достаточно одного секретного ключа, поскольку они оба авторизуются в одной и той же учетной записи. Если запись отсутствует, даже если требуется двухфакторная аутентификация, адаптер явно указывает на это в журнале, вместо того чтобы просто сообщать о неудачной попытке входа.

#### Проверка TLS-сертификата
Адаптер проверяет HTTPS-сертификат устройства SENEC с помощью многоэтапного процесса:

1. **Сертификат CA пользователя** — Загрузите сертификат SenecGui-Root CA через панель управления (вкладка «Система» → «Сертификат TLS»). Скачайте его с сайта mein-senec.de (Документы / Общие документы / SenecGui-Root), затем загрузите файл .pem или .zip. SENEC распространяет этот сертификат за авторизацией, поэтому адаптер не может его включить.
2. **Кэшированный сертификат центра сертификации** — Если пользовательский сертификат отсутствует, адаптер может автоматически загрузить сертификат центра сертификации с сайта mein-senec.de (при условии, что коннектор mein-senec.de включен). Загруженный сертификат сохраняется в состоянии адаптера и остается активным после перезапуска.
3. **TOFU (Trust On First Use)** — Если сертификат центра сертификации не подтвержден, адаптер запоминает отпечаток сертификата устройства при первом контакте и сравнивает с ним каждое последующее соединение. Если происходят изменения (например, после обновления прошивки), регистрируется предупреждение, и автоматически применяется новый отпечаток.

Адаптер последовательно проверяет каждый этап и использует тот, который проходит проверку.

TOFU — это проверка целостности, а не привязка сертификата: она уведомляет вас об изменении сертификата устройства, но не отклоняет новый и не проверяет цепочку сертификатов. Это преднамеренный компромисс для устройства в вашей собственной сети — законное изменение сертификата не должно отключать адаптер на такое длительное время, чтобы кто-то заметил запись в журнале. Для полной проверки вы указываете центр сертификации (CA): загрузка CA необязательна, но является более надежным вариантом.

Если автоматическая загрузка сертификата CA не удалась и вы хотите повторить попытку, установите значение `_local.tls.certFetchFailed` в `false` — адаптер попытается загрузить сертификат при следующем перезапуске или немедленно, если он запущен.

**Важно**: Частые запросы или слишком большое количество точек данных могут перегрузить устройство SENEC. Это может привести к перезапускам, недоступности или отсутствию синхронизации с облаком. В случае возникновения проблем уменьшите частоту запросов или остановите адаптер.

### Прочие активы счета
Если к учетной записи mein-senec.de привязано несколько систем (замененное устройство остается видимым рядом со своим преемником), адаптер распознает все из них при запуске и создает каждую из них под именем `_meinsenec.Plants.{steuereinheitnummer}.`.

По умолчанию запрашивается только первая система. Каждая дополнительная система имеет свой собственный переключатель в разделе `control.Plants.{steuereinheitnummer}.poll`, который изначально выключен. Когда этот переключатель активируется, более медленный уровень запроса включает эту систему и заполняет ее той же структурой измеренных значений, что и основная система.

| Состояние | Содержание |
|-------|--------|
| `_meinsenec.Plants.{sn}.System.*` | Название продукта, номер устройства, номер системы |
| `_meinsenec.Plants.{sn}.Measurements.Monthly.*` | Суточные значения за месяц |
| `_meinsenec.Plants.{sn}.Measurements.Yearly.*` | Ежемесячные значения в год |
| `_meinsenec.Plants.{sn}.Measurements.AllTime.*` | Итого |
| `_meinsenec.Plants.{sn}.Autarky.*` | Самодостаточность за период |
| `_meinsenec.Plants.{sn}.Autarky.*` | Самообеспеченность за период |

Суммарные значения извлекаются один раз при первом обнаружении системы, даже если переключатель выключен — таким образом, окончательные значения деактивированного устройства доступны без постоянного запроса к нему.

Обратите внимание, что каждая дополнительно активированная система увеличивает количество запросов к порталу. Если вам нужны только исторические данные по более старому устройству, лучше оставить переключатель выключенным.

### Внешние источники
![Внешние источники](../../../de/adapterref/iobroker.senec/media/admin-external.png)

Добавьте внешние источники энергии от других адаптеров ioBroker — например, балконные фотоэлектрические системы, дополнительные инверторы, автономные настенные зарядные устройства, тепловые насосы или внешние аккумуляторные батареи. Значения нормализуются в ваттах и отображаются на диаграмме потока энергии и кривой мощности в реальном времени на панели управления.

Воспользуйтесь функцией **Поиск по идентификатору штата**, чтобы найти идентификатор штата нужной точки данных и вставить его в таблицу.

| Столбец | Описание |
|--------|-------------|
| Идентификатор штата / Формула | Один идентификатор штата (например, `solar.0.power`) или формула со ссылками на `{stateId}` (например, `{wallbox.0.l1_amps} * {wallbox.0.l1_volts}`) |
| Тип | Фотоэлектрические панели, потребительские (настенные панели, тепловые насосы и т. д.) или аккумуляторные батареи |
| Единица измерения | Вт или кВт — применяется к конечному значению |
| Режим | **Интеграция** = добавить к общему значению SENEC (один узел). **Разделение** = отобразить как отдельный узел в потоке энергии |
| Состояние заряда батареи | (Только для батареи) Идентификатор состояния заряда (%) |
| Емкость | (Только батарея) Емкость батареи в кВт·ч — позволяет оценивать время |
| Метка | Отображаемое имя на диаграмме потока энергии |

Формулы поддерживают операторы `+ - * / ( )`. Идентификаторы состояний без фигурных скобок автоматически определяются, если они содержат арифметические операторы. Для сложных формул планируется внедрение конфигуратора на основе панели управления с интерактивным выбором состояний.

### Отладка и ведение журналов

Настраивается для каждого коннектора (Local, API, mein-senec.de, Connect):

- **Показывать опрос в информационном журнале** — Отображает сообщения о состоянии опроса в информационном журнале, а не только в журнале отладки.
- **Запись запросов и ответов в журнал** — Запись подробностей HTTP-запросов на уровне отладки (может содержать конфиденциальные данные)
- **Диагностика очереди в информационном журнале** — Отображает статистику очереди в информационном журнале (только для API и веб-версии)

#### Создать отладочный журнал
Большинство проблем можно выявить по лог-файлу, а без него — практически ни одной.

1. Установите уровень логирования для экземпляра на **debug**: ioBroker Admin → Instances → senec instance → Log level selection field. Также доступен вариант `silly`, но он редко дает больше информации и генерирует много лишнего шума.
2. На вкладке адаптера **Отладка и логирование** включите параметр *Логирование запросов и ответов* для соответствующего коннектора. Этот параметр изменяет статус "запрос не удался" на "данный URL-адрес ответил с таким-то статусом".
3. Дайте процессу поработать достаточно долго, чтобы проблема возникла хотя бы один раз. Для медленно обрабатываемых запросов — значений измерений, ежемесячных или годовых данных — это может означать ожидание следующего цикла вместо перезапуска.
4. Скопируйте лог из вкладки «Логи» ioBroker или используйте файл из `/opt/iobroker/log/`.
5. Затем переключитесь обратно на **информацию**. Журналы отладки очень обширны и заполняют жесткий диск на несколько недель.

**Пожалуйста, проверьте перед пересылкой.** Журнал запросов содержит URL-адреса и ответы, которые могут включать идентификатор системы, номер системы и серийный номер. Пароли не включены, но это ваши данные. Замените все, что вы не хотите делать общедоступным.

#### Сообщить об ошибке
Пожалуйста, отправляйте отчеты через [GitHub](https://github.com/nobl/ioBroker.senec/issues). Вот что ускоряет обработку отчета:

- **Какая система** — модель и, если известна, версия прошивки (файлы `_local.FACTORY` и `_local.SYS_UPDATE` содержат оба параметра, при условии, что локальный коннектор запущен).
- **Какие коннекторы** активны, поскольку один и тот же симптом может иметь разные причины локально и в облаке.
- **Версии для Adapter и ioBroker**, а также версия для Node.js
— **Что ожидалось и что произошло вместо этого** — «уровень заряда батареи отсутствует» можно отредактировать, «не работает» требует предварительного уточнения.
- **Соответствующий фрагмент журнала** на уровне отладки, содержащий несколько строк до и после ошибки, а не только строку с ошибкой.

Прежде чем начать: неправдоподобные значения обычно исходят от устройства, а не от адаптера. Адаптер в основном передает значения, поэтому температура или уровень заряда, которые отображаются некорректно на панели управления, обычно будут выглядеть так же некорректно и в веб-интерфейсе устройства. Быстрый просмотр там часто решает проблему — а если нет, то это сравнение является наиболее полезной информацией в сообщении.

## Интегрированная панель управления

Данные Cloud API хранятся в разделе `_api.Anlagen.{systemId}.*`:

- `Dashboard.currently.*` — Значения мощности в реальном времени (Вт)
- `Измерения.Ежедневно.*` — Почасовые данные измерений (кВт·ч)
- `Измерения.Ежемесячно.*` — Данные ежедневных измерений (кВт·ч)
— `Измерения.Ежегодно.*` — Ежемесячные данные измерений (кВт·ч)
- `Измерения.За все время.*` — Суммарные показатели за весь период эксплуатации (кВт·ч)
- `SystemDetails.*` — Сведения о батарее, температура, микропрограмма
- `SystemStatus.*` — Рабочий статус, флаги функций

### Состояния сети (`_meinsenec.*`)
Данные mein-senec.de хранятся в разделе `_meinsenec.*`:

- `Статус.*` — Текущие значения мощности (кВт), рабочее состояние
— «Измерения.*» — Исторические данные измерений (кВт·ч)
— «Автаркия.*» — Процент самообеспеченности (день/неделя/месяц/год/всего)
- `EmergencyPower.*` — Настройки резерва аварийного электропитания
- `PeakShaving.*` — Настройки пикового бритья
- `SGReady.*` — Настройки SG-Ready
— «Розетки.*» — Состояния переключаемых розеток

### Состояния соединения (`_connect.*`)
Данные SENEC.Connect хранятся в разделе `_connect.Systems.{system_id}.*`, в подразделах, посвященных батареям и счетчикам. Учетная запись может включать несколько систем; каждая получает свой собственный канал, названный в соответствии с ее моделью и адресованный через идентификатор системы, указанный в `bessNameplate` — это гарантирует сохранение состояния системы, даже если API возвращает системы в другом порядке. `_connect.info.systemCount` сообщает, сколько систем видит API.

Раздел `bessNameplate` всегда запрашивается, независимо от настроенных разделов, поскольку он содержит этот идентификатор.

Сообщения о состоянии стены хранятся аналогичным образом, под соответствующими кодами `id`: `_connect.Systems.{system_id}.evse.{wallbox_id}.*`. Если сообщение о состоянии стены исчезает из ответа, его состояние удаляется, а не сохраняются последние значения.

Если система не сообщает `system_id`, вместо этого используется ее серийный номер. Система распознается по каждому идентификатору, который она когда-либо сообщала, поэтому ответ, в котором отсутствует один из этих идентификаторов, не приведет к переходу системы на новый путь. Если ответ вообще не содержит идентификатора, система использует его позицию в ответе, как это было до версии 2.15.0, и очистка приостанавливается на это время.

Состояния системы, которая больше не отправляет данные в API, удаляются. В адаптерах до версии 2.15.0 системы нумеровались в соответствии с их позицией в ответе (`_connect.Systems.0.*`); эти состояния удаляются во время первого опроса после обновления, как только системы будут идентифицированы.

**Для пользователей, регистрирующих состояния SENEC.Connect с помощью адаптера истории (History, InfluxDB, SQL): Этот параметр привязан к самому состоянию и будет потерян вместе со старым состоянием. Автоматическое ведение журнала не возобновится — пожалуйста, повторно включите ведение журнала для состояний по новым путям после обновления.**

### Внешние состояния (`_external.*`)
Данные из внешних источников хранятся в разделе `_external.{typ}.{index}.*`:

| Штат | Описание |
|-------|-------------|

| `_external.battery.{n}.power` | Питание от внешней батареи (Вт, знак) |
| `_external.battery.{n}.soc` | Уровень заряда внешней батареи (%) |
| `_external.battery.{n}.capacity` | Емкость внешнего аккумулятора (кВт·ч) |
| `_external.{typ}.{n}.label` | Пользовательская метка |
| `_external.{typ}.{n}.mode` | Режим отображения (интегрированный/раздельный) |
| `_external.{typ}.{n}.sourceId` | Идентификатор или формула иностранного государства |

## Поиск неисправностей
**Устройство не отвечает / часто перезагружается**: Уменьшите интервал опроса для устройств с высоким приоритетом или удалите пользовательские точки данных с высоким приоритетом. Устройство SENEC имеет ограниченные ресурсы.

**Нет данных из API/веб-интерфейса**: Проверьте свои учетные данные для входа на mein-senec.de на вкладке «Учетная запись SENEC». Адаптер регистрирует ошибки аутентификации на уровне предупреждения.

**Панель управления не загружается**: Убедитесь, что ioBroker.web работает на порту 8082. Панель управления предоставляется в виде веб-расширения в рамках `/senec/`.

**Отсутствующие состояния**: Доступные состояния зависят от модели вашего SENEC, версии прошивки и настроенных разъемов. Не все состояния доступны во всех системах.

**Состояния управления не отображаются**: Функции управления должны быть явно включены в настройках управления устройством. Для каждого элемента управления требуется определенный активный разъем.

**Ошибка TLS-сертификата при локальном подключении**: Адаптер автоматически обрабатывает проверку сертификата. Проверьте `_local.tls.mode`, чтобы узнать, какой метод проверки активен. Если активен режим TOFU и вы хотите перейти на проверку CA, включите коннектор mein-senec.de — адаптер попытается автоматически загрузить сертификат CA. Если предыдущая загрузка не удалась, измените `_local.tls.certFetchFailed` на `false`, чтобы повторить попытку.

### 2.15.1 (2026-08-23)

### 2.15.0 (2026-08-14)
- 🔎 **Wanted: testers for the SENEC.Connect connector.** I cannot see what your subscription returns, and real responses are what this connector is missing — especially from accounts holding more than one system, and from responses containing more than `battery` and `meter` (`evse`, `bessNameplate`). If SENEC.Connect reports anything at all for your account, please get in touch in the [ioBroker forum thread](https://forum.iobroker.net/topic/30620/neuer-adapter-senec-home-adapter) or via a [GitHub issue](https://github.com/nobl/ioBroker.senec/issues).
- **Breaking (SENEC.Connect only):** The systems of a SENEC.Connect account were stored by their position in the API response, as `_connect.Systems.0.*`, `_connect.Systems.1.*` and so on. The API does not promise an order, so on an account with more than one system that position can change from one poll to the next — two systems then swap their states inside the same history, with nothing in the values to show it happened. Each system is now stored under the system id from its `bessNameplate` section instead, for example `_connect.Systems.P4H1-1234567.*`, and gets a channel named after its model. A system is remembered by every identifier it has ever reported, so a response that omits one of them does not move it; a system that reports no identity at all keeps its old position-based path and is left alone. The old numbered states are deleted on the first poll after the update; scripts, charts and visualisations that refer to them have to be pointed at the new paths, and the history recorded under the old paths ends there. **If you log these states with a history adapter, that setting is stored on the state and does not survive the move — switch logging back on for the new paths, or recording stops silently.** Accounts with a single system are affected the same way, but nothing else changes for them.
- **Breaking (SENEC.Connect only):** Wallboxes are stored under the `id` they report rather than their position in the response, for the same reason and with the same consequence — `_connect.Systems.{system_id}.evse.{wallbox_id}.*`. A wallbox that disappears from the response now has its states removed instead of leaving them frozen at their last values, looking current.
- New: `_connect.info.systemCount` reports how many systems SENEC.Connect returns, and the states of a system the API stops reporting are removed.
- New: SENEC.Connect has its own request timeout, adjustable between 5 and 120 seconds and 30 seconds by default. It previously borrowed the local appliance's timeout, which is capped at ten seconds and is not even shown unless the local connection is switched on — so a slow cloud response failed every poll with no reachable setting to change.
- Fix: A SENEC.Connect reply that arrived with a success code but did not contain the expected data — an error page or a captive portal, for instance — left the connector reporting itself as connected indefinitely while nothing was being read.
- Fix: A SENEC.Connect polling interval outside the permitted range is corrected on start-up, as the other intervals already were. Only a value written directly into the instance settings could get there, but a negative one made the adapter poll a request-metered API in a tight loop.
- Fix: A SENEC.Connect request in progress is now cancelled when the adapter stops, instead of running on and writing during shutdown, and it identifies itself with the same user agent as the adapter's other requests.
- Fix: Clearing the SENEC.Connect section list in the settings fell back to fewer sections than the field's own default, silently dropping wallbox data.
- Change: The `bessNameplate` section is now always requested from SENEC.Connect regardless of the configured sections, because it carries the id the states are stored under. The API is billed per request, not per section, so this costs nothing.
- Fix: When mein-senec.de measurement detail states were cleared at the daily rollover and written again in the same cycle, they came back as bare values — the name, unit and role were gone, because the adapter still believed the deleted definitions existed.
- Fix: On appliances not set to German, `ENERGY.STAT_STATE_Text` was never created at all. It puts the numeric system state into plain language — "Laden", "Akku voll", "Fernabschaltung" — but the English and Italian tables were stored under a name the adapter never looked them up by, so nothing was written and no error appeared. English is also what the adapter falls back to when it cannot read the appliance's language, so this affected most installations. The state now appears; on an affected system it shows up as a new datapoint after the update. `FACTORY.COUNTRY_Text` was missing on Italian appliances for the same reason.
- Fix: System state 41 was labelled "Schlafmodus" / "Sleeping mode". The appliance itself calls it "Abschaltung Lithium" / "Lithium shutdown", which is a different condition; the Italian text already said so. State 74 also carried a spelling mistake.
- New: Three more numeric datapoints are translated into text — `BMS.MANUFACTURER_Text` names the battery module generation (BMZ or Ampace / LFP), `PWR_UNIT.ENFLURI_Text` says which meter a power unit is measured by, and `CASC.STATE_Text` gives the cascade state.
- **Change: A datapoint your appliance does not have no longer gets a state, and an existing one says so.** The adapter asks every appliance for the same set of datapoints and no model provides all of them, so the answer "I do not have that one" is normal rather than a fault. Until now that answer was stored as the value, so the state read `VARIABLE_NOT_FOUND`. No state is created for it any more, and one that already exists is set to "not provided by appliance" so it is obvious at a glance instead of sitting there with a stale number that still looks current. Nothing is deleted, nothing is reported as a problem, and nothing is required of you. A datapoint that merely failed to be read this once is left untouched, because the real reading is expected back. A whole section your appliance does not have is handled the same way; it previously left behind a state called `<SECTION>.OBJECT_NOT_FOUND` holding nothing. This covers what the adapter asks for by name and the sections it requests — a field that quietly vanishes from a section still being provided cannot be detected this way, because the appliance simply omits it rather than saying anything about it.
- Fix: An unreadable datapoint could be published as a real-looking measurement. The appliance answers with a word where a number was expected, and that word slipped into the conversions for flags, factors, dates and IP addresses: a flag was stored as `true`, a scaled value as `NaN`, a timestamp as "Invalid Date" and an address as garbage. Nothing is stored for such an answer any more, so a state either holds a real reading or does not exist. A datapoint answering with an empty value no longer becomes `0` either, and a few value formats the appliance uses were decoded wrongly — text beginning with "u" could be read as a number, so a state could show 14 where the appliance had sent no reading at all.
- Change: `ENERGY.GUI_BAT_DATA_OA_CHARGING` is no longer polled every few seconds. A SENEC.Home V3 does not have it, it is absent from every field that appliance reports for this section, and the appliance's own web interface never asks for it. It remains defined, so an older appliance that still provides it keeps the state from the slower poll.
- Fix: The appliance's display language was read once at start-up, in a race with the first poll of the datapoint that carries it. On a fresh installation the adapter could therefore stay on English for the whole session, and changing the language on the appliance never took effect until the adapter was restarted. It is now picked up as soon as the appliance reports it, and a language the adapter has no texts for falls back to English instead of silently leaving every translated state empty.
- Fix: A code that is not in a translation table was shown as "(unknown)", which discarded the very number needed to identify it. It now reads "(unknown 7)". If you see one, the number is worth reporting.
- Change: Translated `_Text` states are no longer marked writable — writing to them never did anything — and are declared as text rather than as a measurement. Existing ones are corrected on the first poll after the update.
- Fix: The operating-mode text on the web dashboard now comes from the appliance's own system state on English and Italian systems as well. It previously fell back to the cloud status text there, because the local text did not exist.
- Fix: Several labels in the English and Italian system-state lists were misspelled, one Italian entry contained a stray fragment of an untranslated string, and some Italian entries were missing their accents.
- Change: The adapter warns when the datapoints configured for high-priority polling make a request large enough to approach the size the appliance can still answer. Beyond that size the appliance replies with a truncated body, which used to surface only as a connection error.

### 2.14.1 (2026-08-02)
- Fix: Emptying one of the additional high-priority datapoint fields left its "add datapoints to polling" box ticked, and the adapter then reported a faulty configuration on every start although nothing was configured at all. Such a field is no longer treated as an error, which also settles it for instances that are already in this state; clearing the field now unticks the box as well. ### 2.14.0 (2026-08-01)
- Fix: With the local connection switched on but no IP address entered, the adapter repeatedly tried to reach 0.0.0.0 and logged a connection error on every attempt. It now says once that no address is configured and waits for one.
- Change: A new instance now starts with no connector preselected — pick the ones you want in the settings. The local connection is no longer switched on in advance, and its address field starts empty instead of showing 0.0.0.0. Existing instances keep their settings unchanged.
- Fix: When the SENEC sign-in service rejected the stored token and was itself unreachable, the adapter attempted a full login twice and then kept two recovery loops running side by side, doubling every request. It now makes one attempt and retries on a single schedule.
- Fix: If the appliance was unreachable at start-up and only answered on a later attempt, sections found during that attempt were not actually polled until the adapter was restarted.
- Fix: Four of the six mein-senec.de queue diagnostic states were always empty. They now report real values and count finished requests rather than started ones, so the success rate is no longer dragged down by work still in progress.
- Fix: The two mein-senec.de debug settings only took effect when measurement history polling happened to be switched on as well. They now work on their own.
- Fix: An external source using a formula with several references was recalculated once per reference at start-up, reading every referenced state repeatedly. It is now calculated once.
- Fix: A battery level of infinity from an external source, and a kilowatt reading too large to express in watts, are no longer written to states.
- Fix: When mein-senec.de asks the adapter to wait before retrying, a wait expressed as a date is now understood as well as one expressed in seconds. An implausibly long wait is capped at an hour so the connector always recovers on its own.
- New: The timeout for ordinary SENEC API requests is configurable, and its default is raised from 10 to 30 seconds. The API is regularly slow enough that dashboard and system status requests were timing out, which loses the whole reading until the next poll cycle. Measurement history keeps its own, longer limit.
- Fix: An error reply from mein-senec.de was treated as if it were data. A failed request could write an error page into the status states, advance the "last poll" timestamp and leave the connector reporting itself as connected. Responses are now checked centrally, so a failure is a failure everywhere.
- Fix: The adapter no longer keeps its request rate up when mein-senec.de is struggling. A server error now pauses the whole queue briefly, exactly as rate limiting already did, and the server's own requested delay is honoured. Control commands are still never repeated automatically.
- Fix: If the SENEC login had to be renewed and that renewal failed, the adapter could end up with no token, no scheduled retry and no error — silently stuck until restarted. It now retries with a growing delay, so it recovers on its own.
- Fix: Measurements for "today" and "yesterday" could be fetched for the wrong day between midnight and the UTC changeover — up to two hours every night in Central European time, and any part of the night in other time zones.
- Fix: The battery level recorded from mein-senec.de lost a full day twice a year, at the daylight-saving changeovers, because two adjacent days were not recognised as adjacent.
- Fix: Sections the appliance did not list during discovery are no longer dropped from polling. A restricted or partial answer could previously reduce the adapter to polling almost nothing, including the live values.
- Fix: A failing poll step is now counted, so a system that is only partly readable is reported instead of passing as healthy.
- Fix: External energy sources sharing one foreign state now all update. Previously only the last one configured for a given state received changes, and a state used both directly and in a formula drove only one of the two. Values are also read once at startup instead of showing 0 until the source next changes, and a formula that divides by zero no longer writes Infinity.
