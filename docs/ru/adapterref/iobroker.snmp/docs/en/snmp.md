# Информация об адаптере SNMP

## Общая информация

Протокол SNMP (Simple Network Management Protocol) — это стандартный интернет-протокол для сбора и организации информации об управляемых устройствах в IP-сетях, а также для изменения этой информации с целью корректировки поведения устройств. К устройствам, обычно поддерживающим SNMP, относятся кабельные модемы, маршрутизаторы, коммутаторы, серверы, рабочие станции, принтеры и многое другое.

SNMP широко используется в управлении сетями для мониторинга сети. SNMP предоставляет управляющие данные в виде переменных на управляемых системах, организованных в базу управляющей информации (MIB), которые описывают состояние и конфигурацию системы. Затем эти переменные могут быть удаленно запрошены (и, в некоторых случаях, изменены) управляющими приложениями.

Было разработано и внедрено три значимые версии SNMP. SNMPv1 — это оригинальная версия протокола. Более поздние версии, SNMPv2c и SNMPv3, отличаются улучшенной производительностью, гибкостью и безопасностью. (Текст взят из Википедии, свободной энциклопедии)

SNMP-адаптер использует так называемые OID (идентификаторы объектов) для считывания этих значений с настроенного устройства.

## Конфигурация

Адаптер запрашивает указанные OID (идентификаторы объектов), которые сгруппированы в группы OID, которые, в свою очередь, назначаются устройствам. Данные конфигурации вводятся на нескольких вкладках в том порядке, в котором они отображаются: сначала устройства, затем считываемые ими OID. Устройство, группа OID которого еще не существует, может быть сохранено — адаптер предупреждает об этом и пропускает это устройство до тех пор, пока не будут определены его OID.

| Формат         | выбирать   | как хранится значение                                               | Строка, число, логическое значение, JSON или автоматический режим — см. _раздел «Формат и тип состояния»_ ниже. |
| записываемый   | логический | Следует установить значение true, если OID доступен для записи.     | Состояние становится доступным для записи и записывается обратно на устройство (см. _раздел «Запись»_ ниже).    |

Вы можете легко активировать/деактивировать любой OID, установив флаг активности. Обратите внимание, что идентификатор состояния ioBroker для хранения считанных данных обычно формируется путем объединения имени устройства (см. вкладку «Устройства») и имени OID, указанного здесь. Вы можете использовать точки внутри имени OID для построения структуры папок.

Если некоторые OID не всегда доступны, рассмотрите возможность установки необязательного флага, чтобы избежать ненужных ошибок. Обратите внимание, что для этого требуется использование протоколов SNMP v2c или SNMPv3.

#### Формат и тип состояния

Формат определяет способ хранения считанного значения, а вместе с ним и тип состояния ioBroker:

| Формат                 | тип штата  | ценить                                                                                  |
| ---------------------- | ---------- | --------------------------------------------------------------------------------------- |
| Нить                   | нить       | значение в виде текста                                                                  |
| Число                  | число      | числовое значение; данные, не являющиеся числовыми, устанавливают качество на 0x01.     |
| Логический             | логический | false для 0 или пустого значения, true в противном случае.                              |
| JSON                   | нить       | `{"type":"<type>","data":<value>}` чтобы скрипты получали значение вместе с его типом.  |
| Шестнадцатеричный дамп | нить       | байты значения как `76 01 04 00 27 10` способ отображения двоичных данных в MIB-браузере |
| Автоматический         | смешанный  | Тип соответствует типу SNMP значения.                                                   |

**Hex dump** предназначен для двоичных данных, которые выдают некоторые устройства — например, счетчики обслуживания принтера. Такая строка OctetString читается как `vy'swz'tx{'u` с любым другим форматом, в то время как шестнадцатеричный дамп сохраняет его работоспособность: пары разделены пробелами, поэтому `val.split(' ')` В скрипте задаются байты. Работает с OctetString, Opaque и Counter64, преобразует целое число в его собственное шестнадцатеричное представление (10000 становится `27 10`) и отклоняется для OID или IP-адреса, которые не содержат собственных байтов. Записываемый OID получает в ответ шестнадцатеричный дамп, с пробелами или без них, а также с ведущим символом или без него. `0x`.

При использовании **режима Automatic** целочисленный тип (Integer32, Counter32, Gauge32, TimeTicks, Counter64, …) становится числом, логический тип — логическим значением, а все остальное (OctetString, OID, IpAddress, Opaque) — строкой. Состояние создается следующим образом: `mixed` Потому что устройство само решает, что поступит. Выберите один из фиксированных форматов, если скрипту или диаграмме требуется стабильный тип.

#### Шаблоны

В таблице выше **шаблоны** позволяют обмениваться целыми группами OID в виде файла, так что набор OID, собранный однажды, можно использовать повторно — в другом экземпляре, на втором устройстве того же типа или кем-либо еще на форуме.

_Функция «Сохранить как шаблон»_ записывает OID выбранной группы в файл. `<group>.snmp-template.json` Сама группа не является частью файла: она относится к установке, а не к классу устройств, и выбирается заново при импорте.

Импорт осуществляется из двух источников: _«Поставляемый шаблон»_ предлагает наборы, поставляемые с адаптером, а _«Из файла»_ берет шаблон, присланный вам кем-то другим. Кнопка рядом с ними добавляет OID в выбранную группу; переключатель позади нее переключается в _режим «Заменить»_ , который удаляет уже имеющиеся в группе OID. Ничего не сохраняется до тех пор, пока не будет нажата кнопка «Сохранить» в диалоговом окне.

Поставляются `System` (системная группа, на которую отвечает каждое устройство), `Interface 1` (счетчики первого порта коммутатора), `Host` (время работы, объем памяти и загрузка процессора компьютера), `Printer` (счетчик страниц, тонер и состояние принтера) и `UPS` (батарея и оставшееся время работы). Они используют OID стандартных MIB — устройство, которое отвечает только на MIB своего производителя, оснащено браузером MIB.

Шаблон представляет собой обычный JSON и может быть написан вручную:

```json
{
    "format": "snmp-template",
    "version": 1,
    "name": "Brother HL-L2350DW",
    "deviceClass": "network printer",
    "description": "what the template is good for",
    "mib": "Printer-MIB",
    "oids": [
        {
            "oidName": "pages",
            "oidOid": "1.3.6.1.2.1.43.10.2.1.4.1.1",
            "oidFormat": 1,
            "oidWriteable": false,
            "oidOptional": false
        }
    ]
}
```

`format` и `name` должны быть там, `oids` не должен быть пустым, и каждая запись должна `oidName` и `oidOid`; `deviceClass`, `description` и `mib` Они отображаются при импорте и являются необязательными. `oidFormat` Формат таблицы — число: 0 — строка, 1 — число, 2 — логическое значение, 3 — JSON, 4 — шестнадцатеричный дамп, 99 — автоматический. Запись без этого параметра интерпретируется как «автоматический».

### Авторизация TAB

На этой вкладке представлена информация об авторизации SNMP V3.

<p align=center><img src="img/snmp_tab_authorization.jpg" width="600" /></p>

| Параметр             | Тип   | Описание                                | Комментарий                                                              |
| -------------------- | ----- | --------------------------------------- | ------------------------------------------------------------------------ |
| Имя (идентификатор)  | текст | идентификатор данных авторизации        | должен совпадать с идентификатором авторизации на планшетных устройствах |
| Уровень безопасности | выбор | желаемый метод обеспечения безопасности | см. описание                                                             |
| Имя пользователя     | текст | имя пользователя для аутентификации     |                                                                          |
| Метод                | выбор | метод хеширования паролей               | md5, sha, sha224, sha256, sha384 или sha512                              |
| Ключ авторизации     | текст | пароль для аутентификации               |                                                                          |
| Шифрование           | выбор | метод шифрования                        | des, aes, aes256b или aes256r                                            |
| Ключ шифрования      | текст | ключ шифрования                         |                                                                          |

Обратите внимание, что имя (идентификатор) должно быть уникальным. Идентификатор аутентификации устройства на вкладке _«Устройства»_ должен совпадать с одним из этих имен — начальные и конечные пробелы игнорируются с обеих сторон. Устройство, использующее SNMP v3, идентификатор аутентификации которого ничему не соответствует, пропускается с предупреждением, поскольку в противном случае адаптер запросил бы информацию без имени пользователя, и устройство ответило бы «Неизвестное имя пользователя», что ничего не говорит о реальной причине.

При выборе протокола SNMP V3 требуется расширенная аутентификация. На устройствах в столбце Auth-Id указывается имя блока аутентификации. На этой вкладке необходимо выбрать желаемый уровень безопасности следующим образом:

- Минимальные требования - необходимо только имя пользователя.
- Аутентификация — требуется имя пользователя и пароль.
- Аутентификация и шифрование — требуются имя пользователя, пароль и ключ шифрования.

Обратите внимание, что указанный уровень безопасности должен поддерживаться целевым устройством, а имя пользователя, пароль и ключ шифрования должны совпадать с данными, введенными на целевом устройстве. Вы можете использовать один и тот же блок авторизации для нескольких устройств, если они используют одни и те же данные.

### TAB MIB

Здесь вы загружаете MIB-файлы своих устройств и просматриваете их содержимое.

| Параметр  | Тип  | Описание                  | Комментарий                                                                                     |
| --------- | ---- | ------------------------- | ----------------------------------------------------------------------------------------------- |
| MIB-файлы | файл | MIB-файлы ваших устройств | Все загруженные файлы хранятся в одной папке, поэтому MIB-файл может импортировать другой файл. |

MIB-файлы, поставляемые с адаптером (SNMPv2-MIB, RFC1213-MIB, IF-MIB и другие базовые модули SMI), всегда доступны и не требуют загрузки.

<p align="center"><img src="img/snmp_tab_mib.jpg" width="600" /></p>

Ниже поля загрузки **в браузере MIB** отображается само устройство. Вверху вы выбираете **устройство** , для которого собираются OID — его группа OID заполняется автоматически, поэтому вам обычно не нужно вводить имя группы.

Дерево ниже всегда отображает устройство, чтение происходит в режиме реального времени и по одному уровню за раз: начальный OID указывает первый уровень, открытие папки считывает ее содержимое. Таким образом, считывается только то, на что вы смотрите, и вы видите значения, которые действительно существуют. Загруженные MIB-файлы присваивают этим значениям их имена. `1.3.6.1.4.1.48690.10.2.1.2.1` становится `pName.1` с синтаксисом, правами доступа и текстом DESCRIPTION в виде всплывающей подсказки. OID, который не охватывает MIB, сохраняет свои номера. Список **модулей MIB** переходит к началу MIB, поэтому вам не нужно знать его OID; начальный OID также можно ввести.

Для этого требуется запущенный экземпляр, и устройство должно быть сохранено хотя бы один раз — устройство, существующее только в диалоговом окне, пока нельзя прочитать. В мастере настройки на вкладке _«Устройства»_ это возможно, поскольку там устройство отправляется целиком вместе с запросом.

Значение, считанное из строки таблицы, передаёт её индекс, поэтому оно используется как есть. Сам столбец не указывает на значение — он помечен, и при его открытии отображаются строки, из которых нужно выбрать значение. Скалярное значение используется как... `<OID>.0` Именно здесь SNMP сохраняет свою единственную ценность, и `.0` снова отсутствует в идентификаторе объекта.

Кнопка «плюс» в строке добавляет этот OID в указанную выше группу OID, **кнопка «Добавить все»** добавляет все значения, отображаемые в данный момент фильтром, а кнопка папки добавляет все значения ниже этого узла — всю таблицу одним щелчком. OID, уже содержащийся в группе, помечается галочкой вместо знака «плюс», поэтому его нельзя добавить дважды. Имя OID берется из MIB, формат устанавливается на _автоматический_ , а _возможность записи_ определяется на основе предложения MAX-ACCESS из MIB.

Итак, обычная процедура для нового устройства такова: создайте устройство с его IP-адресом на вкладке _«Устройства»_ , загрузите сюда его MIB-файл, если он у вас есть, затем выберите устройство в браузере MIB и выберите нужные значения — или введите OID вручную на вкладке _«Группы OID»_ . Пока группа OID устройства не содержит хотя бы один активный OID, адаптер пропускает это устройство с предупреждением и продолжает работу, чтобы браузер MIB мог по-прежнему читать MIB-файлы и само устройство.

### Ловушки TAB

Ловушка работает в обратном направлении: устройство отправляет её самостоятельно, когда что-то происходит — порт выходит из строя, ИБП переключается на питание от батареи, в принтере заканчивается бумага — а адаптер только прослушивает это событие. Здесь ничего не опрашивается, поэтому ловушка приходит, когда приходит.

<p align=center><img src="img/snmp_tab_traps.jpg" width="600" /></p>

| Параметр                                         | Тип        | Описание                                                                          | Комментарий                                                                                                  |
| ------------------------------------------------ | ---------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Приём ловушек                                    | логический | Откройте UDP-сокет и слушайте ловушки и уведомления.                              | Без него адаптер только опрашивает систему.                                                                  |
| Порт                                             | число      | UDP-порт для прослушивания                                                        | Устройства отправляют данные на порт 162; в Linux порт ниже 1024 может быть занят только пользователем root. |
| Адрес привязки                                   | текст      | адрес этого хоста для прослушивания                                               | пустые прослушивания на каждом интерфейсе                                                                    |
| Используйте IPv6                                 | логический | прослушивать IPv6 вместо IPv4                                                     | Отправитель IPv4 по-прежнему распознается, сопоставление `::ffff:` удален                                     |
| Сообщество                                       | текст      | Сообщество должно передавать ловушку SNMP v1 или v2c.                             | Ловушка с другим сообществом отклонена и зарегистрирована.                                                   |
| Идентификатор авторизации (SNMP v3)              | текст      | идентификатор набора авторизации, пользователь которого может отправлять ловушки. | Пусто, если не ожидается никаких ловушек SNMP v3.                                                            |
| Принимайте каждую ловушку, не проверяя.          | логический | Проверка не производится ни для сообщества, ни для пользователя SNMP v3.          | Для организации процесса каждый, кто прибудет в порт, сможет написать письмо в Штаты.                        |
| Также принимаются ловушки неизвестных устройств. | логический | Обработать ловушку, отправитель которой не настроен как устройство.               | такая ловушка только добирается `info.trap.*`                                                                 |

Ловушка не указывает имя устройства, она просто приходит — таким образом, адрес, с которого она пришла, определяет, какому устройству она принадлежит. Ловушка с адреса, который не настроен как устройство, отбрасывается, если не задана последняя опция. Ловушка SNMP v1 дополнительно сообщает адрес агента, к которому она относится, что используется, когда сам отправитель не является настроенным устройством — именно это обеспечивает работу ретранслятора.

Сообщение Inform — это сообщение-ловушка, требующее подтверждения; адаптер отвечает на него до того, как обработает, поэтому отправитель не повторяет его.

Обратите внимание, что порт должен быть доступен: 162 — это привилегированный порт в Linux, и контейнер или брандмауэр должны пропускать UDP. Если порт не может быть привязан, причина записывается в лог.

| Отслеживание всех SNMP-запросов и ответов.     | логический  | Записывать каждый запрос и каждый ответ в лог в формате JSON.                           | Для обращения в службу поддержки: журнал увеличивается с каждым опросом, после этого отключите эту функцию.                           |

Параметр «Размер пакета параметров» можно использовать для уменьшения количества запрашиваемых OID в одном запросе. В зависимости от целевого устройства количество запрашиваемых IOD в одном запросе может быть ограничено. В таком случае устройство может ответить ошибкой TOOBIG. В этом случае попробуйте уменьшить значение параметра «Размер пакета параметров».

Опция **«не закрывать сессию при ошибке»** сохраняет сессию чтения устройства открытой, когда запрос не удается. Обычно адаптер закрывает сессию при ошибке и открывает новую для следующей попытки, что является правильным решением для большинства устройств. Однако некоторые устройства перестают отвечать после такого переподключения — для них следует включить эту опцию.

Опция **трассировки всех SNMP-запросов и ответов** записывает каждый отправленный адаптером запрос и каждый полученный ответ в журнал в формате JSON, помеченный соответствующими символами. `[trace]` и устройство, к которому оно принадлежит:

```
[trace] [printer] get request ["1.3.6.1.2.1.43.11.1.1.9.1.1"]
[trace] [printer] get answer {"err":null,"varbinds":[{"oid":"1.3.6.1.2.1.43.11.1.1.9.1.1","type":2,"value":1200}]}
```

Он охватывает опросы устройств, запись записываемого OID и запросы браузера MIB. Двоичные данные отображаются следующим образом: `{"type":"Buffer","data":[…]}` Таким образом, ничего не теряется при попадании в лог. Строки записываются на информационном уровне, поэтому трассировку можно собрать, не переключая весь экземпляр в режим отладки, — но она увеличивается с каждым опросом, поэтому отключите эту опцию после завершения анализа.

Опция **использования имен MIB** изменяет сразу две вещи. Столбец OID в наборах OID также принимает символическое имя, например, `IF-MIB::ifDescr.1` (или `ifDescr.1` без модуля), который адаптер преобразует в числовой OID при запуске, используя загруженные MIB-файлы. Идентификатор состояния ioBroker больше не формируется из имени OID, а из символа MIB, поэтому приведенный выше пример в итоге оказывается в `snmp.0.<device>.ifDescr.1` вместо `snmp.0.<device>.<OID-name>`.

Внимание: изменение этой опции меняет идентификаторы состояний всех OID, которые охватывает MIB. Объекты, записанные ранее, сохраняют свои старые идентификаторы и остаются в качестве "сирот" — удалите их вручную, если они больше не нужны. OID, которые не охватываются загруженным MIB, продолжают использовать свое имя OID.

## Состояния и объекты

Для каждого активного устройства адаптер создает один объект устройства — папку. `info` со статусом этого устройства и одним состоянием для каждого активного OID группы OID, назначенной ему:

| идентификатор                     | тип        | роль                 | значение                                                                               |
| --------------------------------- | ---------- | -------------------- | -------------------------------------------------------------------------------------- |
| `snmp.<instance>.info.connection` | логический | индикатор.подключено | верно, пока хотя бы одно устройство отвечает.                                          |
| `<device>`                        | устройство | -                    | `common.statusStates` указывает на два штата ниже                                      |
| `<device>.info.online`            | логический | индикатор.доступен   | истинно, пока устройство отвечает                                                      |
| `<device>.info.error`             | логический | индикатор.ошибка     | После ошибки значение становится истинным, после следующего успешного чтения — ложным. |
| `<device>.info.error_text`        | нить       | текст                | сообщение о последней ошибке                                                           |
| `<device>.<OID-name>`             | см. формат | см. ниже             | Считанное значение; точки в имени OID становятся папками.                              |
| `<device>.<OID-name>-type`        | нить       | текст                | Тип SNMP значения, только при наличии опции _добавления типов состояний._              |
| `<device>.<OID-name>-raw`         | нить       | json                 | varbind в исходном виде, но с опцией _добавления необработанных состояний._            |

`<device>` — это название устройства; в режиме совместимости это IP-адрес. `_` вместо `.` Эти идентификаторы используются скриптами и диаграммами, поэтому они не изменяются — за одним исключением, которое указано в параметре _«Использовать имена MIB_ для документов» выше.

Роль состояния значения определяется его типом, чтобы визуализация знала, что это такое:

| тип штата                            | только для чтения | записываемый |
| ------------------------------------ | ----------------- | ------------ |
| число                                | `value`           | `level`      |
| логический                           | `indicator`       | `switch`     |
| нить                                 | `text`            | `text`       |
| смешанный (формат _автоматический_ ) | `state`           | `state`      |

При включенном приемнике ловушек каждое устройство получает еще четыре состояния, и тот же набор состояний существует и ниже. `info` удерживая последнюю ловушку любого отправителя:

| идентификатор                               | тип   | роль   | значение                                                                     |
| ------------------------------------------- | ----- | ------ | ---------------------------------------------------------------------------- |
| `<device>.trap.oid`                         | нить  | текст  | числовой идентификатор последней ловушки                                     |
| `<device>.trap.name`                        | нить  | текст  | Символ, присвоенный MIB, числовой идентификатор (oid), если MIB отсутствует. |
| `<device>.trap.json`                        | нить  | json   | Вся ловушка со всеми её приманками, см. ниже.                                |
| `<device>.trap.count`                       | число | ценить | ловушки, полученные от этого устройства с момента запуска экземпляра         |
| `info.trap.address`                         | нить  | текст  | адрес, откуда пришла последняя ловушка                                       |
| `info.trap.oid` /`.name` /`.json` /`.count` |       |        | То же самое относится и к последней ловушке любого отправителя.              |

**Подпишитесь на `count` ** Реагировать на ловушку: это меняется с каждой отдельной ловушкой, в то время как `oid` и `name` Остаются неизменными при повторении действия устройства. Остальные три состояния уже записаны, когда `count` изменения.

В JSON-файле содержится вся информация, полученная в результате обработки запроса:

```json
{
    "oid": "1.3.6.1.6.3.1.1.5.3",
    "name": "IF-MIB::linkDown",
    "version": 1,
    "address": "192.168.1.2",
    "sender": "public",
    "inform": false,
    "upTime": 4,
    "enterprise": "1.3.6.1.4.1",
    "agentAddr": "192.168.1.2",
    "generic": 2,
    "specific": 0,
    "varbinds": [
        { "oid": "1.3.6.1.2.1.2.2.1.1.3", "name": "IF-MIB::ifIndex.3", "type": "Integer32", "value": 3 }
    ]
}
```

`version` 1, 2 или 3, `sender` Сообщество отвечает за имя пользователя, с которым была отправлена ловушка, и `inform` Указывается, нужно ли было это признавать. `enterprise`, `agentAddr`, `generic` и `specific` Эти четыре поля отображаются только для ловушки SNMP v1 — именно так такая ловушка себя описывает. `oid` Это то, что из них выдает RFC 3584, поэтому можно сравнить ловушку v1 и ловушку v2c. Привязки переменных перечислены в порядке их поступления, включая `sysUpTime.0` и `snmpTrapOID.0` Ловушка SNMP v2c начинается с определенного значения; их значения декодируются так же, как это делает _автоматический_ формат.

### Качество

Каждое значение содержит код качества ioBroker, поэтому скрипт может отличить реальное значение от отсутствующего:

| качество | значение                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------ |
| 0x00     | хорошо                                                                                           |
| 0x01     | Значение не удалось преобразовать в заданный формат.                                             |
| 0x02     | Устройство не ответило (тайм-аут), последнее значение остается.                                  |
| 0x44     | Устройство сообщило об ошибке, значение установлено на null.                                     |
| 0x84     | Идентификатор OID отсутствует на этом устройстве (NoSuchInstance), значение установлено на null. |

### Письмо

OID, помеченный как _доступный для записи,_ создает состояние, доступное для записи, на которое подписывается адаптер. Установка его без `ack` записывает значение на устройство с помощью SNMP. `set` Значение кодируется обратно в тип SNMP последнего считанного значения, поэтому такой OID должен быть считан хотя бы один раз, прежде чем его можно будет записать — до тех пор адаптер будет выдавать сообщение "невозможно записать в неинициализированное состояние".
