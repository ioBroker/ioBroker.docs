# Результаты исследования контроллера умного дома MCDU

**Дата исследования:** 14.02.2026\
&#x20;**Исследователь:** Субагент (mcdu-research)\
&#x20;**Проект:** Перепрофилирование WinWing MCDU в качестве контроллера умного дома ioBroker.

---

## Управляющее резюме

В этом документе обобщены результаты исследований, проведенных в рамках проекта по реверс-инжинирингу WinWing MCDU, и возможности интеграции с ioBroker. WinWing MCDU — это полнофункциональный блок управления полетом с USB-связью, встроенным дисплеем, более чем 60 физическими кнопками и управляемыми светодиодами. Существующая работа по реверс-инжинирингу обеспечивает прочную основу для реализации протокола USB. ioBroker предлагает несколько путей интеграции (REST API, WebSocket, пользовательский адаптер), подходящих для данного варианта использования.

**Основной вывод:** Этот проект **технически осуществим** и имеет управляемую сложность. Аппаратный протокол хорошо документирован, а ioBroker предоставляет гибкие возможности интеграции.

## Часть 1: Аппаратное обеспечение и протокол WinWing MCDU

### 1.1 Обзор оборудования

**Устройство:** WinWing MCDU-32 (многофункциональный блок управления и отображения)\
&#x20;**Ссылка на товар:** <https://ea.winctrl.com/view/goods-details.html?id=945>\
&#x20;**Интерфейс:** USB HID (устройство ввода данных человеком)

**Идентификаторы USB:**

- Идентификатор поставщика:`0x4098`
- Идентификаторы продуктов (настраиваются через SimAppPro):
  - `0xbb36` - MCDU-32-CAPTAIN
  - `0xbb3a` - MCDU-32-OBSERVER
  - `0xbb3e` - MCDU-32-CO-PILOT

### 1.2 Возможности ввода

**Всего кнопок:** более 60 физических кнопок, привязанных к отчетам HID.

**Категории кнопок:**

1. **Клавиши выбора строки (LSK):** всего 12 кнопок.
   - L1, L2, L3, L4, L5, L6 (левая сторона)
   - R1, R2, R3, R4, R5, R6 (правая сторона)

2. **Функциональные клавиши:** 10 кнопок
   - DIR, PROG, PERF, INIT
   - ДАННЫЕ, F-PLN, RAD NAV, FUEL PRED, SEC F-PLN, СВЯЗЬ УВД
   - Меню MCDU, аэропорт
   - BRT (яркость), DIM

3. **Навигация:** 4 клавиши со стрелками (вверх, вниз, влево, вправо)

4. **Буквенно-цифровая клавиатура:**
   - Цифры: 0-9
   - Письма: АЗ
   - Специальные символы: Точка (.), +/-, /, SP (пробел)

5. **Клавиши управления:**
   - OVFY (Overfly)
   - CLR (Clear)

**Протокол подачи сигналов кнопки:**

Кнопки считываются через`hid.read()` возвращают массивы размером 25 байт.

- **Байт 1:** Всегда`0x01` (Идентификатор отчета)
- **Байты 2-11:** Битовая карта состояния кнопок (каждый бит представляет одну кнопку)
- **Байты 18-25:** Данные датчика освещенности (обнаружение окружающего освещения)

**Пример сопоставления кнопок (байт 2):**

```
0x01: L1
0x02: L2
0x04: L3
0x08: L4
0x10: L5
0x20: L6
0x40: R1
0x80: R2
```

Полная схема расположения кнопок задокументирована по байтам 2-11 (см. репозиторий GitHub для полной таблицы).

### 1.3 Возможности дисплея

**Тип дисплея:** Встроенный ЖК-экран\
&#x20;**Разрешение:** Не задокументировано явно (по-видимому, основано на символах, аналогично реальным дисплеям MCDU).\
&#x20;**Поддержка цветов:** Возможность настройки нескольких цветов с помощью определений цветовой палитры.

**Протокол управления дисплеем:**

**1. Блок инициализации (первый блок)**

Необходимо отправить один раз для определения цветовой палитры и режимов отображения. Это большая многопакетная передача, распределенная между несколькими операциями записи по USB (\~17 последовательных записей).`device.write()` команды).

**Цветовые определения (формат RGBA):**

- Цвет фона:`0x20, 0x20, 0x20, 0xff` (темно-серый)
- Цвета текста соответствуют индексам (0x00-0x19):
  - Белый:`0xff, 0xff, 0xff, 0xff`
  - Желтый:`0xff, 0xff, 0x00, 0xff`
  - Зеленый:`0x00, 0xff, 0x00, 0xff`
  - Голубой:`0x00, 0xff, 0xff, 0xff`
  - Пурпурный:`0xff, 0x00, 0xff, 0xff`
  - Янтарь:`0xff, 0x63, 0x00, 0xff`
  - Настраиваемые цвета

**2. Блок отрисовки текста (второй блок)**

После инициализации текст отображается с использованием 64-байтовых пакетов, начинающихся с`0xf2` .

**Кодировка текста:**

- **3 байта на символ:**
  - Байты 1-2: Атрибуты символов (цвет, размер) в формате little-endian.
  - Байт 3: код символа ASCII

**Характеристики характера:**

- Базовый формат:`0x0042` (обычный белый текст)
- Добавлять`0x016b` переключиться на мелкий шрифт
- Добавлять`0x0021` циклически менять цвета (повторяющийся)

**Пример:** Обычный белый "А":`0x42, 0x00, 0x41`

**Специальные символы (многобайтовый UTF-8):**

- Обозначение градуса (°):`c2 b0`
- Стрелка вверх (↑):`e2 86 91`
- Стрелка вниз (↓):`e2 86 93`
- Левая стрелка (←):`e2 86 90`
- Стрелка вправо (→):`e2 86 92`
- Открытый треугольник (Δ):`ce 94`
- Прямоугольный замкнутый треугольник (▶):`e2 96 b6`
- Левый замкнутый треугольник (◀):`e2 97 80`
- Открытая площадь (☐):`e2 98 90`
- Открытый ромб (◊):`e2 ac a1`

**Макет отображения:** текст начинается в верхнем левом углу и располагается слева направо, сверху вниз. При заполнении экрана последний блок текста должен быть дополнен.`0x00` байтов для достижения длины в 64 байта.

### 1.4 Светодиодные индикаторы

**Доступные светодиоды:** 8 индикаторов состояния.

**Управление светодиодами:** Команда:`device.write([0x02, 0x32, 0xbb, 0x00, 0x00, 0x03, 0x49, 0xXX, 0xYY, ...])`

- **Байт 8 (XX):** выбор светодиода
  - `0x08` : НЕУДАЧА
  - `0x09` : FM (Управление полетами)
  - `0x0a` : MCDU
  - `0x0b` : МЕНЮ
  - `0x0c` : FM1
  - `0x0d` : ИНД (Индекс)
  - `0x0e` : RDY (Готов)
  - `0x0f` Статус (горизонтальная полоса)
  - `0x10` : FM2

- **Байт 9 (YY):** состояние светодиода
  - `0x01` : НА
  - `0x00` : ВЫКЛЮЧЕННЫЙ

### 1.5 Регулировка яркости

**Подсветка кнопок:**

```python
device.write([0x2, 0x32, 0xbb, 0x0, 0x0, 0x3, 0x49, 0x0, 0xcc, 0x0, 0x0, 0x0, 0x0, 0x0])
```

`0xcc` = значение яркости (0-255)

**Подсветка дисплея:**

```python
device.write([0x02, 0x32, 0xbb, 0x00, 0x00, 0x03, 0x49, 0x01, 0xff, 0x00, 0x00, 0x00, 0x00, 0x00])
```

`0xff`= значение яркости (0-255)

### 1.6 Датчики освещенности

**Датчики:** 2 датчика внешней освещенности (слева и справа)

**Местоположение данных:** байты 18-25 буфера чтения HID.

**Диапазон значений:** от 0 до \~3060 (12 \* 255)

**Формула (левый датчик):**`value = byte19 * 255 + byte18`

**Пример использования:** Автоматическая регулировка яркости дисплея/кнопок в зависимости от окружающего освещения.

### 1.7 Существующие работы по обратному проектированию

**Репозиторий GitHub:** <https://github.com/alha847/winwing_mcdu>\
&#x20;**Автор:** alha847\
&#x20;**Статус:** «Обратное проектирование практически завершено»

**Доступные ресурсы:**

- Примеры скриптов на Python с использованием`hid` библиотека
- Скрипт Lua для интеграции с X-Plane (`lra333_winwing_mcdu_driver.lua` )
- Полная документация по протоколу USB (кнопки, дисплей, светодиоды, яркость).
- Тестовые скрипты для отображения текста.

**Используемая среда разработки:**

- MacBook M1 Pro

- SimAppPro (программа для настройки WinWing), работающая в виртуальной машине Windows 11.

**Основные выводы из работы с Repo:**

- Технология USB HID обеспечивает стабильную и хорошо изученную связь.
- Протокол отображения сложен, но полностью документирован.

- Работает на разных платформах (протестировано на macOS, вероятно, работает и на Linux/Windows).

## Часть 2: Варианты интеграции с ioBroker

### 2.1 Обзор ioBroker

**Что такое ioBroker?**\
&#x20;ioBroker — это платформа IoT с открытым исходным кодом для автоматизации умного дома. Она использует модульную архитектуру адаптеров для интеграции различных устройств и сервисов.

**Основные понятия:**

1. **Объекты:** Метаданные, описывающие устройства, каналы и точки данных.
2. **Состояния:** Фактические значения точек данных с метками времени и флагами подтверждения.
3. **Адаптеры:** плагины, которые подключают ioBroker к внешним системам.
4. **События:** Уведомления об изменении состояния в режиме реального времени.

**Флаг подтверждения (ack):**

- `ack=false` Команда (например, «включить свет»)
- `ack=true` Подтверждение состояния (например, «свет теперь включен»)

### 2.2 Подход к интеграции 1: REST API (простой API)

**Адаптер:**`iobroker.simple-api`\
&#x20;**GitHub:** <https://github.com/ioBroker/ioBroker.simple-api>\
&#x20;**Статус:** зрелый, но ioBroker рекомендует использовать`rest-api` вместо

**Ключевые конечные точки:**

| Конечная точка           | Метод    | Описание                                          | Пример                                          |
| ------------------------ | -------- | ------------------------------------------------- | ----------------------------------------------- |
| `/get/stateID`           | ПОЛУЧАТЬ | Прочитать состояние с полными метаданными         | `/get/system.adapter.admin.0.alive`             |
| `/getPlainValue/stateID` | ПОЛУЧАТЬ | Только для чтения значения состояния (текст)      | `/getPlainValue/admin.0.memHeapTotal` → `31.19` |
| `/getBulk/id1,id2,...`   | ПОЛУЧАТЬ | Эффективное чтение данных из нескольких состояний | `/getBulk/temp.living,temp.bedroom`             |
| `/set/stateID?value=X`   | ПОЛУЧАТЬ | Установить значение состояния                     | `/set/lights.living?value=1`                    |
| `/setBulk`               | GET/POST | Установить несколько состояний                    | `/setBulk?light1=0&light2=1`                    |
| `/states?pattern=X*`     | ПОЛУЧАТЬ | Перечислите все штаты, соответствующие шаблону.   | `/states?pattern=hm-rpc.0.*`                    |
| `/objects?pattern=X*`    | ПОЛУЧАТЬ | Перечислите все объекты, соответствующие шаблону. | `/objects?pattern=system.adapter.*`             |

**Аутентификация:**

- Параметры URL:`?user=admin&pass=secret`
- HTTP Базовая аутентификация
- Токены Bearer OAuth2

**Форматы ответов:**

- JSON (по умолчанию)
- Простой текст (для`getPlainValue` )
- Добавлять`?prettyPrint` для удобочитаемого JSON

**Плюсы:**

- ✅ Простые HTTP-запросы (клиентская библиотека не требуется)
- ✅ Работает с любым языком программирования (Python, Node.js, Bash)
- ✅ Подходит для проведения опросов и периодической записи.
- ✅ Хорошо задокументировано

**Минусы:**

- ❌ Нет обновлений состояния в реальном времени (требуется опрос)
- ❌ Неэффективно при быстром нажатии кнопок → циклы смены состояний
- ❌ Более высокая задержка, чем у WebSocket

**Вариант использования MCDU:**

- Первоначальный прототип панелей мониторинга только для чтения.
- Опрос состояния ioBroker каждые 1-2 секунды для обновления отображения MCDU.

### 2.3 Интеграционный подход 2: WebSocket (socket.io)

**Адаптер:**`iobroker.socketio`\
&#x20;**GitHub:** <https://github.com/ioBroker/ioBroker.socketio>\
&#x20;**Важно:** начиная с версии 4.0 используется **чистый WebSockets** (а не библиотека socket.io).

**Клиентская библиотека:** [@iobroker/socket-client](https://github.com/ioBroker/socket-client)

**Поддерживаемые методы (документированы в @iobroker/socket-classes):**

**Государственные операции:**

- `getState(id)` - Читать одно состояние
- `getStates(pattern)` - Прочитать несколько штатов
- `setState(id, state)` - Запись состояния
- `subscribe(pattern)` - Подписаться на обновления состояния
- `unsubscribe(pattern)` Отписаться

**Операции с объектами:**

- `getObject(id)` - Чтение метаданных объекта
- `getObjects()` - Прочитать все объекты
- `setObject(id, obj)` - Создание/обновление объекта

**Операции с файлами:**

- `readFile(adapter, filename)`
- `writeFile(adapter, filename, data)`

**Подписка на мероприятия:**

- `on('stateChange', callback)` — Следите за обновлениями в штате
- `on('objectChange', callback)` - Отслеживать обновления объектов

**Плюсы:**

- ✅ **Обновления в режиме реального времени** через подписку WebSocket
- ✅ Двусторонняя связь
- ✅ Более низкая задержка, чем в REST
- ✅ Эффективно для частых обновлений (нажатия кнопок → мгновенные изменения состояния)
- ✅ Доступна официальная библиотека клиентских приложений

**Минусы:**

- ❌ Сложнее, чем REST API
- ❌ Требует поддержания постоянного соединения
- ❌ Необходима логика переподключения WebSocket

**Вариант использования MCDU:**

- **Идеально подходит для использования в производстве.**
- Подпишитесь на обновления состояния умного дома → мгновенные обновления дисплея MCDU
- Нажатия кнопок → Команды WebSocket → Управление устройством
- Пример: Подписаться на`washing_machine.status` → Обновить отображение MCDU после завершения цикла

### 2.4 Подход к интеграции 3: Пользовательский адаптер ioBroker

**Что такое адаптер?**\
&#x20;Плагин для ioBroker, написанный на JavaScript/TypeScript, который запускается как управляемый процесс внутри ioBroker.

**Шаблон адаптера:** [@iobroker/create-adapter](https://github.com/ioBroker/create-adapter)\
&#x20;**Пример репозитория:** <https://github.com/ioBroker/ioBroker.example>

**Возможности адаптера:**

- Прямой доступ к внутренним базам данных состояний/объектов ioBroker.
- Автоматическое управление жизненным циклом (запуск/остановка/перезапуск)
- Административный интерфейс для настройки
- Встроенная система ведения журналов и обработки ошибок.
- Можно создавать пользовательские объекты/состояния в пространстве имен ioBroker.

**Стек разработки адаптеров:**

- **Язык программирования:** JavaScript или TypeScript
- **Тестирование:** Mocha, Chai, Sinon
- **Качество кода:** ESLint
- **Менеджер пакетов:** npm

**Типичная структура адаптера:**

```
iobroker.mcdu-controller/
├── admin/              # Web UI for adapter configuration
│   ├── index_m.html
│   └── custom.css
├── lib/                # Core logic
│   └── mcdu.js         # USB communication layer
├── main.js             # Adapter entry point
├── io-package.json     # Adapter metadata
└── package.json        # npm dependencies
```

**Крючки жизненного цикла адаптера:**

- `onReady()` - Вызывается при запуске адаптера
- `onStateChange(id, state)` - Вызывается при изменении состояния подписки
- `onMessage(obj)` - Требовались сообщения от межадаптеров
- `onUnload(callback)` - Вызывается перед остановкой работы адаптера

**Плюсы:**

- ✅ **Встроенная интеграция с ioBroker** (отображается в административном интерфейсе)
- ✅ Прямой доступ к базе данных (максимальная скорость работы)
- ✅ Можно создавать пользовательские объекты (например,`mcdu.0.button.L1` ,`mcdu.0.display.line1` )
- ✅ Автоматический перезапуск при сбое
- ✅ Встроенные механизмы подписки на состояние
- ✅ Проще всего установить другим пользователям (через административную панель ioBroker)

**Минусы:**

- ❌ Требуется Node.js (использование Python невозможно)
- ❌ Более сложная первоначальная настройка
- ❌ Необходимо следовать инструкциям по использованию адаптера ioBroker.
- ❌ Доступ по USB из Node.js (необходимо)`node-hid` или`usb` библиотека)

**Вариант использования MCDU:**

- **Лучший вариант для публичного распространения** (адаптер, которым можно делиться).
- MCDU отображается в ioBroker как устройство со своими собственными состояниями.
- Пользователи настраивают страницы через административный интерфейс.
- Примеры показывают:
  - `mcdu.0.button.L1` - Нажата левая кнопка 1
  - `mcdu.0.display.text` - Текущее отображаемое содержимое
  - `mcdu.0.led.FAIL` - Состояние светодиода "Сбой управления"

### 2.5 Рекомендуемый подход к интеграции

**Для прототипирования (этапы 1-2):**

- **Внешний скрипт на Python + REST API**
  - Быстрая итерация
  - Используйте существующие примеры HID на Python из репозитория WinWing.
  - Простые HTTP-запросы для чтения/записи состояний ioBroker

**Для производства (этапы 3-5):**

- **Внешний сервис Node.js + WebSocket**
  - Обновления состояния в режиме реального времени
  - Решение профессионального уровня
  - Проще в обслуживании, чем адаптер, изготовленный на заказ.

**Для публичного распространения (необязательно):**

- **Пользовательский адаптер ioBroker**
  - Переупакуйте сервис Node.js в адаптер ioBroker.
  - Обеспечивает удобную установку для пользователя.
  - Интегрируется в административный интерфейс ioBroker.

## Часть 3: Шаблоны состояния и объектов ioBroker

### 3.1 Чтение «умных» штатов

**Пример: Запрос всех источников света**

```bash
# REST API
GET http://iobroker-host:8087/states?pattern=hm-rpc.0.*.STATE&prettyPrint

# Returns:
{
  "hm-rpc.0.living_room.light.STATE": { "val": true, "ts": 1234567890 },
  "hm-rpc.0.bedroom.light.STATE": { "val": false, "ts": 1234567891 }
}
```

**Пример: Считывание данных с одного датчика**

```bash
# REST API
GET http://iobroker-host:8087/getPlainValue/weather.0.current.temperature

# Returns:
22.5
```

**Пример: Подписка на изменения состояния (WebSocket)**

```javascript
// Node.js with @iobroker/socket-client
const socket = new SocketClient('http://iobroker-host:8082');

await socket.connect();
await socket.subscribe('washing_machine.0.status');

socket.on('stateChange', (id, state) => {
  console.log(`${id} changed to ${state.val}`);
  // Update MCDU display
});
```

### 3.2 Запись команд управления

**Пример: Включение/выключение света**

```bash
# REST API
GET http://iobroker-host:8087/set/lights.living.STATE?value=1&ack=false

# Returns:
{"id": "lights.living.STATE", "value": 1}
```

**Пример: Установка температуры**

```bash
# REST API
GET http://iobroker-host:8087/set/heating.bedroom.target?value=21.5&type=number
```

**Пример: Массовая запись**

```bash
# REST API
POST http://iobroker-host:8087/setBulk
Content-Type: text/plain

lights.living=1&lights.bedroom=0&heating.target=22
```

### 3.3 Типичные идентификаторы состояний умного дома

**Формат:**`adapter.instance.device.channel.state`

**Примеры:**

- `hm-rpc.0.kitchen.light.STATE` - Выключатель света Homematic
- `mqtt.0.solar.power` - Выходная мощность солнечной панели
- `sonoff.0.washing_machine.status` - Состояние стиральной машины
- `weather.0.current.temperature` - Текущая температура
- `history.0` — Адаптер исторических данных

### 3.4 Типы значений состояния

| Тип        | Пример                    | Вариант использования      |
| ---------- | ------------------------- | -------------------------- |
| логический | `true` ,`false`           | Светильники, выключатели   |
| число      | `22.5` ,`1500`            | Температура, мощность (Вт) |
| нить       | `"running"` ,`"idle"`     | Сообщения о состоянии      |
| объект     | `{"temp": 22, "hum": 65}` | Сложные данные             |
| нулевой    | `null`                    | Недоступные датчики        |

## Часть 4: Технические препятствия и проблемы

### 4.1 Потенциальные проблемы

**1. Права доступа к USB-накопителю (Linux/macOS)**

- **Проблема:** для HID-устройств требуются повышенные права доступа или правила udev.
- **Решение (Linux):** Создать правило udev для идентификатора поставщика.`0x4098`
  ```
  SUBSYSTEM=="usb", ATTRS{idVendor}=="4098", MODE="0666"
  ```
- **Решение (macOS):** Может потребоваться запуск скрипта с помощью`sudo` или с использованием разрешений IOKit

**2. Сложность протокола отображения**

- **Проблема:** Последовательность инициализации нескольких пакетов является ненадежной.
- **Решение:** Создать надежную библиотеку драйверов дисплея с обработкой ошибок.
- **Рекомендация:** Проведите тщательное тестирование с помощью захвата сетевых пакетов из SimAppPro.

**3. Отображение состояний ioBroker**

- **Проблема:** Различные адаптеры для умного дома используют непоследовательные правила именования.
- **Решение:** Создать гибкий конфигурационный файл, сопоставляющий идентификаторы состояний ioBroker со страницами MCDU.
- **Пример:** Пользователь определяет`weather_temp: "weather.0.current.temperature"` в конфигурации

**4. Кодирование текста для отображения**

- **Проблема:** дисплей MCDU использует 3-байтовую кодировку символов (не стандартную UTF-8).
- **Решение:** Создать библиотеку кодировки символов для преобразования формата ASCII/UTF-8 в формат MCDU.
- **Примечание:** Для специальных символов (стрелок, знаков препинания) требуется кодировка UTF-8 → многобайтовая.

**5. Производительность обновления в реальном времени**

- **Проблема:** Опрос REST API каждую секунду приводит к задержке.
- **Решение:** Используйте подписки WebSocket для мгновенных обновлений.
- **Резервный вариант:** реализовать адаптивный опрос (быстрее для активных страниц, медленнее для страниц в режиме ожидания).

**6. Управление состоянием навигации по страницам**

- **Проблема:** MCDU необходимо отслеживать текущую страницу, контекст кнопки и буферы ввода.
- **Решение:** Реализовать конечный автомат для навигации по страницам.
- **Примеры штатов:**`DATA` ,`CLIMATE` ,`ENERGY` ,`APPLIANCES`

**7. Повторное подключение USB-устройства**

- **Проблема:** При отключении/повторном подключении MCDU скрипт аварийно завершает работу.
- **Решение:** Внедрить мониторинг USB-устройств и логику автоматического переподключения.

**8. Частота обновления дисплея**

- **Проблема:** Неизвестна оптимальная частота обновления для обновления дисплея.
- **Решение:** Провести эмпирическое тестирование (начать с 5 Гц, корректировать в зависимости от производительности).

### 4.2 Меры по смягчению последствий

| Испытание                             | Уровень риска | Смягчение последствий                                       |
| ------------------------------------- | ------------- | ----------------------------------------------------------- |
| Разрешения USB                        | Низкий        | Описание настройки udev приведено в файле README.           |
| Протокол отображения                  | Середина      | Используйте существующие примеры на Python в качестве参考.    |
| картирование штатов                   | Низкий        | файл конфигурации JSON                                      |
| Кодирование текста                    | Середина      | Создайте многоразовую библиотеку кодирования.               |
| Обновления в режиме реального времени | Низкий        | Используйте WebSocket (хорошо задокументировано).           |
| Навигация по страницам                | Середина      | Разработайте ясный конечный автомат заранее.                |
| Повторное подключение USB             | Низкий        | Используйте конструкцию try-catch с циклом переподключения. |
