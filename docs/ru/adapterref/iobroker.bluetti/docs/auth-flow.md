# Процесс аутентификации, выбора токена и устройства в BLUETTI

> **Статус реализации (июль 2026 г.): реализовано и проверено в рабочем режиме.** Вход через OAuth, обмен/обновление токенов, обнаружение/выбор устройств и опрос только для чтения реализованы и были подтверждены сквозным тестированием на реальной учетной записи BLUETTI (Elite 30 V2) на js-controller 7.0.7. Приведенные ниже разделы представляют собой **первоначальный план проектирования** и сохранены для истории; в случаях, когда они не соответствуют реализации, приоритет имеют следующие примечания:
>
> - **Поставляются учетные данные клиента по умолчанию.** Система единого входа BLUETTI не выдает клиент OAuth для каждого пользователя; адаптер по умолчанию использует фиксированный клиент, применяемый в официальной интеграции с Home Assistant.`client_id=HomeAssistant` ,`client_secret=SG9tZUFzc2lzdGFudA==` (Отправлено дословно — _не_ декодировано в base64). Администратор больше не отображает поля ввода client-id/secret; экспертные переопределения по-прежнему работают посредством прямого редактирования нативных объектов.
> - **Вращающийся токен OAuth хранится в зашифрованном состоянии.`auth.tokenJson` ), а не в исходной конфигурации.** Каждая запись в`system.adapter.<ns>` Перезапуск экземпляра приводит к тому, что сохранение токена (или временного статуса аутентификации) в нативных полях вызывает циклы перезапуска при входе в систему и при каждом обновлении токена. Устаревшие нативные поля`oauthTokenJson` ,`oauthLastRefresh` , и`authStatus` были удалены в #140.
> - **Динамический URL-адрес обратного вызова ioBroker Admin работает.** BLUETTI принимает его как на этапе авторизации, так и на этапе получения токена; для этого клиента нет фиксированного списка разрешенных URI перенаправления.
> - **Обмен токенов использует стандартный формат тела запроса** (client\_id/secret в теле запроса, без базовой аутентификации, без PKCE, без области действия). Авторизация`code` Запрос токена поступает в закодированном виде от администратора и должен быть декодирован из URL-адреса перед отправкой, иначе BLUETTI его отклонит.`invalid_grant` .
> - **REST-запросы отправляют токен доступа без`Bearer ` префикс.**
>
> Все открытые вопросы внизу этого документа решены вышеизложенным. Остается один известный вопрос: поле истечения срока действия токена в BLUETTI еще не анализируется, поэтому токен обновляется при каждом опросе (это безвредно, поскольку токен находится в состоянии, но неэффективно).

Статус: план архитектуры репозитория для задачи #15. Этот документ предназначен для отслеживания в репозитории GitHub, чтобы будущая работа по реализации могла начинаться с тех же предположений о потоке аутентификации и открытых вопросов. Для работы с этим документом не требуются учетные данные BLUETTI для производственной среды.

## Решение

Реализация полноценного процесса аутентификации OAuth непосредственно в коде пока **не** является следующим безопасным шагом.

Небольшая первоначальная реализация становится целесообразной только после того, как еще один экспериментальный запуск с поддержкой источника подтвердит точные детали запроса/ответа BLUETTI OAuth вне вспомогательного механизма OAuth Home Assistant:

- принимает ли BLUETTI динамический URL-адрес обратного вызова ioBroker Admin в качестве`redirect_uri` ,
- точные параметры URL-адреса авторизации,
- Точная форма/текст обмена токенов и необходимые заголовки.
- Определяет, всегда ли возвращаются токены обновления и как формируются поля истечения срока действия.

В провайдере и тестах уже реализована реализация внедрения токена, одной попытки обновления и API-кода для определения срока действия токена.`805` а также сопоставление ошибок облачной аутентификации и аутентификации. Недостающим звеном является пользовательский интерфейс загрузки OAuth и настройка постоянного токена/устройства.

| заголовок REST-аутентификации          | Название заголовка`Authorization` Значение представляет собой необработанную строку токена доступа без каких-либо дополнительных данных.`Bearer ` префикс |
| Сигнал истечения срока действия токена | HTTP 401/403 или код API BLUETTI`805`                                                                                                                     |

Из документации по администрированию/адаптерам ioBroker:

- В конфигурации JSON можно использовать`sendTo` кнопка с`openUrl` запросить у адаптера URL-адрес для начала аутентификации OAuth и открыть его для пользователя.
- Администратор раскрывает`/oauth2_callbacks/<adapterNamespace>/` затем отправляет`oauth2Callback` сообщение этому экземпляру адаптера с параметрами запроса.
- Конфиденциальные поля, изначально встроенные в адаптер, могут быть перечислены в`encryptedNative` и`protectedNative` в`io-package.json` Они расшифровываются во время работы адаптера, но не хранятся в открытом виде.
- В ioBroker существует более новая централизованная система хранения учетных данных, но она требует более новых версий платформы, чем те, которые в настоящее время заявлены в этом адаптере. Для первого варианта реализации лучше подойдет зашифрованная/защищенная собственная конфигурация.

Проверка работоспособности конечной точки OAuth, 02.07.2026:

- GET-запрос к`https://sso.bluettipower.com/oauth2/grant` с`response_type=code` ,`client_id=HomeAssistant` локальный ioBroker-подобный сервис`redirect_uri` (`http://127.0.0.1:8081/oauth2_callbacks/bluetti.0/` ), и случайный`state` Возвращен HTTP-код 200 со страницей входа в BLUETTI.
- Это подтверждает, что BLUETTI не отклоняет динамический URL-адрес обратного вызова до входа в систему.
- Это **не** доказывает, что перенаправление после входа в систему и обмен токенами проходят успешно с использованием URL-адреса обратного вызова ioBroker.

## Предлагаемый сценарий взаимодействия пользователя

1. Пользователь открывает конфигурацию экземпляра адаптера BLUETTI в административной панели ioBroker.
2. Администратор показывает:
   - текущий статус авторизации,
   - **Аутентификация с помощью кнопки BLUETTI** .
   - Управление выбором устройства отключено до успешной аутентификации.
   - Выбранные серийные номера/названия устройств после обнаружения.
3. Кнопка представляет собой JSON-конфигурацию.`sendTo` действие, например, команда`getOAuthStartLink` , с`openUrl: true` .
4. Адаптер принимает`getOAuthStartLink` и строит:
   - случайный`state` ценить,
   - URL-адрес обратного вызова:`${data._origin}oauth2_callbacks/${adapter.namespace}/` ,
   - URL-адрес авторизации BLUETTI с идентификатором клиента, URL-адресом обратного вызова и состоянием.
5. Администратор открывает страницу входа/согласия BLUETTI.
6. BLUETTI перенаправляет на URL-адрес обратного вызова административной панели ioBroker с помощью`code` и`state` .
7. Администратор отправляет`oauth2Callback` к экземпляру адаптера.
8. Адаптер проверяет`state` обмены`code` Для хранения данных токена, данные токена сохраняются в зашифрованном виде, а затем извлекаются продукты пользователя.
9. Пользователь возвращается к настройкам адаптера и выбирает одно или несколько устройств BLUETTI.
10. Вызовы адаптера`bindDevices` для выбранных серийных номеров и сохраняет метаданные выбранного устройства.

## Возможность использования OAuth в административной панели ioBroker.

Использование OAuth в административной панели ioBroker вполне реально **, если BLUETTI динамически принимает URL-адрес обратного вызова административной панели** .

Предпочтительнее использовать прямой обратный вызов администратора, поскольку он обеспечивает локальность потока и не требует использования облачного прокси ioBroker в производственной среде. Вероятная структура обратного вызова:

```text
http(s)://<admin-host>:<admin-port>/oauth2_callbacks/bluetti.0/
```

Риск: интеграция с Home Assistant использует структуру OAuth/учетных данных приложения Home Assistant. Если BLUETTI проверит зарегистрированный для фиксированный URI перенаправления,`HomeAssistant` Клиент ioBroker не может просто повторно использовать динамический URL-адрес обратного вызова административной панели. В этом случае остаются следующие варианты:

1. Запросить/согласовать работу совместимого с BLUETTI/ioBroker приложения OAuth или конечной точки облачного кода OAuth ioBroker.
2. использовать документированную службу обратного вызова/прокси-сервера с фиксированным статусом.
3. Не следует внедрять OAuth до тех пор, пока BLUETTI не предоставит поддерживаемую стратегию перенаправления.

**Не** следует использовать сбор логинов/паролей или автоматизацию браузера в качестве запасного варианта. Это будет ненадежно и небезопасно для опубликованного адаптера.

## Обработка обратного вызова и состояния

Адаптер должен обрабатывать две команды сообщений:

| Командование        | Направление             | Цель                                                                                                   |
| ------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------ |
| `getOAuthStartLink` | Администратор → Адаптер | Создайте состояние и верните URL-адрес авторизации через `{ openUrl }`                                 |
| `oauth2Callback`    | Администратор → Адаптер | Проверка запроса обратного вызова, обмен кодом, сохранение токенов, возврат`{ result }` или`{ error }` |

Правила обработки данных:

- Сгенерировать криптографически случайный символ`state` .
- Сохраняйте состояние ожидания с коротким значением TTL, например, 10 минут.
- В первом варианте реализации допустимо использование состояния в оперативной памяти; если адаптер перезапускается во время входа в систему, обратный вызов завершается неудачей, и пользователь повторяет попытку.
- На более позднем этапе повышения уровня безопасности можно сохранить состояние ожидания в каталоге данных экземпляра с очисткой TTL.
- Никогда не заходите в систему`code` , токен доступа, токен обновления или полный URL-адрес обратного вызова.

## Хранение токенов

Храните данные токена в зашифрованном виде.`auth.tokenJson` состояние, а не поля конфигурации.

| Поле                         | Чувствительный | Цель                                                                                            |
| ---------------------------- | -------------: | ----------------------------------------------------------------------------------------------- |
| `auth.tokenJson` (состояние) |             да | JSON-строка, содержащая ответ с токеном: токен доступа, токен обновления, поля created/expires. |
| `deviceSerial` (родной)      |       частично | Серийный номер выбранного устройства, используемого для опроса и привязки устройств.            |

`auth.tokenJson` зашифровано с помощью`this.encrypt()` и сохраняется как состояние ioBroker, чтобы избежать перезапуска адаптера при ротации токенов.

### Оценка безопасности (#141)

Он`auth.tokenJson` государство объявляется с`read: false, write: false` и его значение зашифровано посредством`this.encrypt()` Это обеспечивает защиту от:

- Случайное отображение в дереве объектов административного интерфейса (скрыто от просмотра)
- Утечки данных из резервных копий и прямой доступ к файловой системе (зашифрованные данные в состоянии покоя)

Это **не** защищает от администратора ioBroker, который может прочитать необработанное значение состояния с помощью скриптов или REST API и расшифровать его, используя ключ шифрования, действующий на уровне всего экземпляра. Это приемлемый компромисс:

- Администраторы ioBroker уже имеют полный доступ к системе (файловая система, база данных, другие адаптеры, собственная конфигурация).
- Перемещение токена в`encryptedNative` Это привело бы к повторному запуску цикла перезапуска адаптера при каждом обновлении токена (каждая запись в native-config запускает перезапуск js-controller), что и было той самой проблемой, которая была решена путем перемещения токенов в состояние в #140.
- Хранение токена в файловой системе приведет к потере встроенного шифрования ioBroker и усложнит отладку.

Зашифрованное состояние — это правильный подход, соответствующий идиоматике ioBroker, для ротации токенов, которая не должна приводить к перезапуску адаптера.

Серийные номера устройств не являются секретами OAuth, но могут идентифицировать оборудование пользователя. Их не следует записывать полностью. Решение о шифровании принимается производителем продукта; защита этих данных является разумной мерой.

Для сохранения обновленных данных токена необходимо не только изменить, но и обновить объект экземпляра.`this.config` Реализация должна быть обновлена.`system.adapter.<namespace>.native` с помощью объектных API ioBroker, сохраняя несвязанные собственные поля.

## Обновление токена при перезапуске адаптера

При запуске адаптера:

1. Прочитайте и проанализируйте зашифрованный текст.`auth.tokenJson` состояние.
2. Если отсутствует, установите.`info.connection = false` и статус авторизации для`not_authenticated` ; не проводить опрос.
3. Для вычисления достоверности используйте:
   - `expires_at - 30s` , или
   - `created_at + expires_in - 30s` .
4. Если срок действия токена истек или близок к истечению, обновите его перед первым запросом.
5. Например, после неудачной попытки обновления следует ограничить количество попыток, в соответствии с защитным поведением интеграции с Home Assistant.
6. Сохраните успешно обновленный токен в зашифрованном собственном конфигурационном файле.
7. Восстановите существующий`BluettiCloudProvider` с`BluettiTokenProvider` что:
   - возвращает текущий токен доступа.
   - Обновляет и сохраняет токен по запросу.
   - Помечает аутентификацию как истекшую, когда провайдер обнаруживает HTTP-код 401/403 или код API.`805` .

Ошибки обновления не следует рассматривать как сбои в работе устройств BLUETTI.

## Выбор устройства и привязка устройств

Выбор устройства должен происходить после успешной аутентификации OAuth и до опроса.

Поток:

1. Вызовы адаптера`getUserProducts()` используя новый токен.
2. Административная конфигурация получает список устройств через`sendTo` /`selectSendTo` Управление осуществляется либо адаптером, либо он сохраняет обнаруженный список для отображения после обратного вызова OAuth.
3. Пользователь выбирает один серийный номер.
4. Вызовы адаптера`POST /api/bluiotdata/ha/v1/bindDevices` с`{ "bindSnList": [deviceSerial] }` .
5. Адаптер сохраняет выбранный последовательный порт.
6. При опросе используется только выбранный последовательный порт.

Представление:

| Значение Native/config  | Использовать                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------- |
| `deviceSerial: string`  | Целевой показатель опроса                                                               |
| `bindDevices` результат | Используется только для подтверждения конфигурации; не отображает состояния управления. |

В первой реализации это должно быть только для чтения.`fulfillment` Управляющие конечные точки остаются вне области видимости.

## Таксономия ошибок

Сбои аутентификации, облачных сервисов и устройств должны оставаться раздельными, поскольку состояние работоспособности после сбоя зависит от этого различия.

| Источник                                                        | статус поставщика   | Состояние адаптера/аутентификации |                    `info.connection` | Влияние модели отключения электроэнергии                   |
| --------------------------------------------------------------- | ------------------- | --------------------------------- | -----------------------------------: | ---------------------------------------------------------- |
| Отсутствует токен                                               | `auth_failed`       | `not_authenticated`               |                                 ЛОЖЬ | Нет оснований подозревать отключение электроэнергии.       |
| Недействительный/просроченный токен, HTTP 401/403, API `805`    | `auth_failed`       | `reauth_required`                 |                                 ЛОЖЬ | Нет оснований подозревать отключение электроэнергии.       |
| Таймаут обновления токена в сети                                | `cloud_unreachable` | `refresh_deferred`                |                                 ЛОЖЬ | Облачное хранилище недоступно, а не отключение устройства. |
| Ошибка таймаута шлюза/сетевая ошибка во время опроса            | `cloud_unreachable` | `authenticated`                   |                                 ЛОЖЬ | можно пометить телеметрию как устаревшую                   |
| Ошибка API без аутентификации                                   | `provider_error`    | `authenticated`                   |                                 ЛОЖЬ | сбой поставщика/API                                        |
| Продукт `online != "1"`                                         | `ok`                | `authenticated`                   | ложное значение для этого устройства | сигнал отключения устройства                               |
| Опрос успешно пройден хотя бы для одного выбранного устройства. | `ok`                | `authenticated`                   |                             истинный | телеметрия свежая                                          |

`info.connection` Это значение должно быть истинным только в том случае, если аутентификация работает и хотя бы одно выбранное устройство возвращает пригодный для использования статус/телеметрию.

## Минимальная последовательность реализации

1. **OAuth start-link/state helper**
   - `src/lib/bluetti-oauth-flow.ts` Формирует URL-адрес авторизации на основе источника ioBroker Admin и пространства имен адаптера.
   - Используется 10-минутная память.`state` TTL, проверяет состояние/код обратного вызова, отклоняет ошибки OAuth и обрабатывает состояния только один раз, чтобы предотвратить повторное воспроизведение.
   - Модульные тесты охватывают параметры URL, нормализацию коллбэков, однократное потребление состояния, истечение срока действия и коллбэки для обработки ошибок OAuth.
   - Этот вспомогательный модуль намеренно не подключен к...`main.ts` еще.

2. **Менеджер токенов без цикла опроса**
   - `src/lib/bluetti-stored-token-provider.ts` анализирует сохраненный JSON-токен и предоставляет доступ к существующему.`BluettiTokenProvider` интерфейс и остается независимым от`main.ts` .
   - Это поддерживает`expires_at` и`created_at + expires_in` , 30-секундный буфер истечения срока действия, явно указанный`markTokenExpired()` , регулирование скорости обновления после сбоев, сохранение токена обновления, если BLUETTI не предоставляет новый токен обновления, и функция обратного вызова для сохранения JSON-файла обновленного токена.
   - Модульные тесты охватывают расчет срока действия, обновление, сохранение данных, регулирование скорости обновления, некорректно сохраненные данные, сохраняемые токены обновления и редактирование.

3. **клиент обмена токенов OAuth**
   - `src/lib/bluetti-oauth-token-client.ts` отправляет стандартные тела форм OAuth в`/oauth2/token` с использованием учетных данных, предоставленных собственной конфигурацией ioBroker.
   - Это поддерживает`authorization_code` обмен и`refresh_token` обновить с помощью внедренного`fetchImpl` обработка тайм-аутов, структурированные ошибки, нормализация ответов и редактирование.
   - Модульные тесты охватывают структуру тела/заголовка запроса, нормализацию даты создания, запросы на обновление, ошибки OAuth, ошибки HTTP, недействительные ответы, тайм-аут, сетевые ошибки и удаление секретного ключа.
   - Форма запроса обеспечивается интеграцией с Home Assistant и соглашениями OAuth; обмен данными после входа в систему по-прежнему требует проверки обратного вызова ioBroker в реальном времени.

4. **Настройка аутентификации администратора и подключение обратного вызова.**
   - `admin/jsonConfig.json` имеет одну кнопку`sendTo` процесс аутентификации для`getOAuthStartLink` Поля ввода client-id/client-secret больше не отображаются.
   - `io-package.json` включает`messagebox` и магазины`oauthClientSecret` в качестве защищенного и зашифрованного собственного поля.
   - `src/main.ts` ручки`getOAuthStartLink` ,`oauth2Callback` , и`getDevices` сохраняет JSON-токен на стороне сервера.`auth.tokenJson` состояние, и не возвращает токен в ответы администратора.
   - Обнаружение/выбор устройств по-прежнему намеренно не осуществляется с помощью проводов.

5. **Выбор устройства администратора**
   - Добавьте элементы управления конфигурацией JSON для выбора устройства.
   - Добавить обработчики сообщений адаптера для`discoverDevices` и`saveSelectedDevices` .
   - Если сохраняются полные серийные номера, выбранные серийные номера следует хранить в защищенных/зашифрованных полях.

6. **Интеграция жизненного цикла поставщика услуг**
   - Поставщик токенов Wire и выбранные серийные номера в`src/main.ts` .
   - Начинайте опрос только после аутентификации и выбора устройств.
   - Создание объектов телеметрии следует отложить до более поздних выпусков, посвященных телеметрии (#4/#6), если только это не требуется для минимального объема данных.`info.connection` доказательство.
