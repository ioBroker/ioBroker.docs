## Процесс настройки и аутентификации OAut

В файле README, указанном в исходном коде, описывается процесс настройки Home Assistant, в ходе которого пользователь добавляет...`bluetti` интеграция, выполняется авторизация OAuth, подтверждает, что Home Assistant может получить доступ к учетной записи/облаку BLUETTI, входит в учетную запись BLUETTI, связывает ее с Home Assistant и выбирает устройства (`README.md:105-135` ).

Интеграция использует фреймворк OAuth/application-credentials от Home Assistant:

- `config_flow.py:15-19` Импортирует учетные данные клиента OAuth по умолчанию. Адаптер использует те же встроенные настройки по умолчанию для входа в систему администратора и по-прежнему позволяет вносить изменения в настройки для опытных пользователей посредством прямого редактирования нативных объектов.
- `application_credentials.py:13-16` Создает URL-адреса авторизации и токена на основе настроенного базового URL-адреса SSO.
- `oauth.py:24-38` реализует`OAuth2FlowHandler` После вызова функции обратного вызова OAuth процесс продолжается до выбора устройства.
- `oauth.py:93-102` использует`self._oauth_data['token']['access_token']` создать`ProductClient` и позвонить`get_user_products()` .
- `oauth.py:137-149` Отображает доступные устройства в виде списка для множественного выбора в Home Assistant.
- `oauth.py:42-90` звонки`bind_devices()` для выбранных серийных номеров устройств и магазинов приложений.`auth_implementation` ,`token` и отобранные`products` в записи конфигурации.

### Обработка токенов

- REST-запросы отправляют токен доступа в виде пустого файла.`Authorization` значение заголовка, без`Bearer ` префикс в исходном коде (`api/bluetti.py:63-65` ).
- В заголовках соединения WebSocket/STOMP также отправляется токен доступа.`Authorization` (`api/websocket.py:20-25` ).
- `AsyncConfigEntryAuth.async_get_access_token()` звонит в Home Assistant`async_ensure_token_valid()` перед возвратом токена доступа (`oauth.py:172-175` ).
- `AuthTokenRefresh` Проверяет срок действия токена один раз при запуске и ежедневно.`oauth.py:191-205` ).
- Действительность токена рассчитывается либо на основе одного из следующих параметров:`expires_at` или`created_at + expires_in` с 30-секундным запасом прочности (`oauth.py:209-225` ).
- Если до истечения срока действия токена осталось менее семи дней, интеграция обращается к реализации OAuth в Home Assistant.`async_refresh_token(...)` Частота обновления ограничивается максимум одним разом в час после предыдущей попытки обновления.`oauth.py:241-267` ).
- Обработка истечения срока действия токена осуществляется с помощью событий.`onTokenExpired` и постоянное уведомление`notifyTokenExpire` (`const.py:7-8` ,`oauth.py:178-239` ).
- Вебсокет`ERROR` рамки с`msgCode == 805` рассматриваются как истечение срока действия токена и прекращают соединение WebSocket.`api/websocket.py:153-161` ).

Особенность исходного кода, которую необходимо проверить перед реализацией: проверка обработки истечения срока действия REST-токенов.`data['code'] == 805` в`api/bluetti.py:93-101` , в то время как модель ответа представляет собой`msgCode` (`api/unify_response.py:7-20` Это может быть ошибка в исходном коде или несоответствие формы ответа.

## WebSocket / процесс обновления с помощью push-уведомлений

Интеграция с вышестоящим сервером также открывает соединение STOMP-overWebSocket:

- URL-адрес WebSocket формируется путем добавления`/websocket` к настроенной базе WSS (`api/websocket.py:19-25` ), в результате чего`wss://gw.bluettipower.com/api/edgeiotgw/ws-coordination//websocket` с текущей строкой профиля. Двойная косая черта должна быть проверена, но, скорее всего, она допустима или нормализована сервером/клиентом.
- При открытии клиент отправляет STOMP-запрос.`CONNECT` рамка с`accept-version` ,`Host` ,`Authorization` , и`heart-beat` заголовки (`api/websocket.py:75-85` ).
- После`CONNECTED` кадр, он подписан на`/ws-subscribe/user/<user-name>/notify` (`api/websocket.py:162-168` ).
- На`MESSAGE` Тело кадра передается обработчику (`api/websocket.py:169-170` ).
- `BluettiData.web_socket_message_handler()` Ожидается формат JSON, где`data.deviceSn` определяет измененное устройство, а затем запускает`device.async_update()` для этого серийного номера (`models.py:46-56` ).

Для первой реализации ioBroker используется опрос.`deviceStates` Это более простой и проверенный путь. Использование WebSocket можно отложить, если этого не требуют ограничения по задержке или скорости соединения.

### Поведение сопоставления сущностей в Home Assistant

- Датчики создаются, когда`fnType == 'SENSOR'` и`sensorInfo` присутствует (`sensor.py:87-96` ).

- Сущности переключателей создаются, когда`fnType == 'SWITCH'` (`switch.py:24-29` ).
- Выбранные сущности создаются, когда`fnType == 'SELECT'` и`supportModeValues` присутствует (`select.py:24-28` ).

## Обработка ошибок и сигналы состояния

Подтвержденное поведение, основанное на исходном коде:

- Реакции REST, отличные от 2xx, вызывают`ApplicationRuntimeException` со статусом HTTP и текстом ответа (`api/bluetti.py:86-88` ).
- Обнаружено истечение срока действия токена WebSocket, как`ERROR` рамка`msgCode == 805` (`api/websocket.py:153-161` ).
- Истечение срока действия токена запускает уведомление Home Assistant, а не бесконечную бесшумную повторную попытку.`oauth.py:227-239` ).
- Состояние устройства в сети отображается следующим образом:`BluettiDevice.online` истинно, когда`online == '1'` (`models.py:172-174` ).
- Если опрошенное устройство возвращает`isBindByCurUser == '0'` , вышестоящий проект запускает процесс очистки после отвязки устройства (`models.py:201-229` а затем логика очистки в том же файле).

Открыта возможность разработки дизайна для ioBroker:

- Сопоставьте HTTP-коды 401/403 и код истечения срока действия токена 805 с явным статусом аутентификации/конфигурации, а не с подозрением на сбой.
- Сопоставьте тайм-ауты шлюза/сети со статусом доступности провайдера/облака.
- Карта`online != '1'` к состоянию устройства вне сети, отдельно от сбоя облачного сервиса/API.
- Держать`info.connection` conservative: true только в том случае, если поставщик может аутентифицировать и вернуть пригодную для использования телеметрию/статус хотя бы для одного выбранного устройства.

## Требования к безопасности и редактированию

Следующие данные ни в коем случае не должны регистрироваться адаптером ioBroker:

- пароль учетной записи BLUETTI
- токен доступа
- токен обновления
- `Authorization` заголовок
- полные исходные идентификаторы учетных записей
- полные серийные номера устройств, если иное не указано явно.
- Исходные телеметрические данные до редактирования

В исходном коде есть как минимум одна закомментированная отладочная строка, которая должна была бы записать в лог токен доступа (`api/websocket.py:31-33` ), а ведение журнала REST-запросов может включать тела запросов (`api/bluetti.py:67-74` В реализации ioBroker следует использовать явный санитайзер, а не копировать эти шаблоны логирования.

## Решение: целесообразность прямого взаимодействия с облачным провайдером.

Прямой облачный провайдер BLUETTI вполне подходит для использования адаптера ioBroker, хотя и с некоторыми оговорками.

Причины, подтвержденные источниками:

- Официальная интеграция существует и поддерживается`bluetti-official` (`README.md:6-11` ).
- В исходном коде присутствуют хосты для производственной системы единого входа (SSO), шлюза и WebSocket.`profile/application.yaml:1-5` ).
- REST-конечные точки для списка устройств и статуса устройств присутствуют и четко структурированы (`api/product_client.py:30-50` ).
- EL30V2/PR30V2 указаны как поддерживаемые официальной интеграцией (`README.md:36-50` ).

Необходимые оговорки по реализации:

- Первоначальная реализация должна быть полностью облачной и доступной только для чтения.
- Не следует реализовывать состояния управления в версии 0.1, даже несмотря на то, что исходный код предоставляет конечную точку для выполнения.
- В шаблоне следует предусмотреть место для процесса администрирования/аутентификации с поддержкой OAuth. Простая конфигурация в формате JSON с именем пользователя и паролем не считается достаточной с точки зрения проверки исходного кода.
- Опрос через`deviceStates` Первым путем для передачи телеметрии должен быть WebSocket; его можно добавить позже.
- Перед тем как пометить поля, выходящие за рамки матрицы поддержки в файле README, как проверенные, по-прежнему необходимо получить реальные, прошедшие очистку данные полезной нагрузки EL30V2.

## Неизвестные факторы / блокировщики

- Точные детали предоставления доступа по протоколу OAuth и требования к перенаправлению находятся за пределами абстракции вспомогательного механизма Home Assistant.
- Поддерживает ли BLUETTI безопасный поток аутентификации OAuth без поддержки высокой доступности, подходящий для административного интерфейса ioBroker.
- Поля ответа в виде токенов на практике (`expires_at` ,`expires_in` (обновить наличие токена, области действия).
- Exact EL30V2`stateList` форма полезной нагрузки и`fnCode` ценности.
- Включает ли телеметрия EL30V2 информацию о режиме ИБП, режиме обхода, оставшемся потреблении Вт·ч, температуре или другие более подробные диагностические данные.
- Ограничения скорости для`deviceStates` опрос.
- Умеет ли статус облачного хранилища четко различать сбой API BLUETTI, отключение интернета, отключение устройства от сети и сбой учетной записи/аутентификации?
- Является ли использование двойной косой черты в URL-адресах WebSocket преднамеренным или допустимым.
- Является ли код истечения срока действия REST-токена`code == 805` или`msgCode == 805` в ответах в режиме реального времени.
