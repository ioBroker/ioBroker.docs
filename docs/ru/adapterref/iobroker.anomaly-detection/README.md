# ioBroker.anomaly-detection

[Английский](/#/adapters/anomaly-detection) · **Немецкий** ( [README.de.md](/#/adapters/anomaly-detection) )

Изучает нормальное поведение выбранных числовых состояний ioBroker и сообщает о статистически необычных значениях локально.

> **Искусственный интеллект не используется.** Адаптер не использует сервисы машинного обучения, облачные API или генеративный ИИ. Все оценки рассчитываются локально с использованием детерминированных математических и статистических методов, таких как медианы, медианное абсолютное отклонение (MAD), ограниченные временные рамки и устойчивые наклоны. Результаты объяснимы и воспроизводимы при использовании одних и тех же входных данных и конфигурации.

## Что это делает

Статические пороговые значения не могут отражать контекст: 8 кВт могут быть нормой утром и необычным позже в теплое воскресенье. Этот адаптер поддерживает ограниченные надежные базовые уровни для каждого настроенного числового состояния. Он оценивает каждое входящее обновление состояния; он не опрашивает исходные состояния.

Адаптер объединяет следующие детерминированные детекторы:

- **Надежное отклонение значений:** Медианное абсолютное отклонение (MAD) обнаруживает значения, выходящие за пределы изученного диапазона, не допуская, чтобы одно экстремальное значение исказило базовую линию.
- **Темп изменений:** сравнение `delta / elapsed time` Таким образом, нерегулярные интервалы обновления источника обрабатываются корректно.
- **Зависание:** опционально обнаруживает многократно полученные одинаковые значения сверх заданного периода времени. Само по себе отсутствие обновления никогда не классифицируется как зависание.
- **Временная базовая линия:** по умолчанию используются почасовые интервалы, при желании возможно дальнейшее разделение по дням недели. В случаях с небольшим количеством дней/времени используется базовая линия по времени суток, а затем глобальная базовая линия.

`score` Это детерминированное значение степени тяжести/уверенности от 0 до 100, а не статистическая вероятность и не диагноз физической причины.

## Математическая основа

Адаптер использует ограниченную, устойчивую статистику. Он не строит нейронную сеть, не обращается к сервисам искусственного интеллекта и не предполагает, что измерения поступают через фиксированные интервалы времени.

### Устойчивое отклонение значений (медиана и MAD)

Для обученной базовой линии со значениями `x₁ … xₙ` Ожидаемое значение — это медиана:

`m = median(x₁ … xₙ)`

Разброс измеряется с помощью медианного абсолютного отклонения (MAD):

`MAD = median(|xᵢ − m|)`

Для нового значения `x` Адаптер вычисляет надежный z-балл:

`robust z = 0.6745 × |x − m| / MAD`

Настроенная **чувствительность** — это z-оценка, при которой этот детектор достигает значения 100. В отличие от среднего арифметического и стандартного отклонения, медиана/MAD не сильно искажается одним экстремальным значением. Если `MAD = 0` Неизменное значение считается нормальным, а изменение значения рассматривается как существенное отклонение.

Пример: усвоенные значения вокруг `100 W` с медианой `100 W` и МАД `2 W` делать `120 W` гораздо более сильное отклонение, чем `103 W`.

### Отклонение скорости изменения

Для последовательных значений скорость рассчитывается с использованием фактического прошедшего времени:

`rate = (current value − previous value) / elapsed seconds`

В качестве базового показателя скорости используется тот же расчет медианы/среднеарифметического отклонения, что и в детекторе значений. Это позволяет обнаружить необычно быстрое изменение, даже если полученное абсолютное значение все еще выглядит правдоподобным.

Пример: уровень в резервуаре обычно меняется на `−0.01 %/s` изменение `−0.5 %/s` может указывать на необычно быструю потерю.

### Обнаружение зависшего состояния

Этот метод основан на правилах, а не на распределении. При многократном получении одинаковых значений адаптер записывает первую метку времени. `t₀` Застревание при поиске возможно только в следующих случаях:

`current timestamp − t₀ ≥ configured stuck duration`

Отсутствующее обновление не считается повторяющимся значением и, следовательно, не может привести к зависанию процесса поиска.

Пример: с продолжительностью `120 minutes` положение клапана, которое продолжает точно передавать информацию. `50` Продолжительность пребывания более двух часов считается подозрительной.

### Временной базовый уровень и резервный вариант

Значения хранятся глобально и, если эта функция включена, в временных интервалах. Интервал рассчитывается исходя из местного времени суток:

`bucket = floor(minutes since midnight / configured bucket size)`

При включенном контексте дня недели день недели добавляется к этому ключу. Ожидаемый базовый уровень выбирается только в том случае, если он содержит как минимум **минимальное количество изученных выборок** . Порядок резервного варианта следующий:

`weekday + time bucket → time bucket → global baseline`

Пример: бытовая нагрузка на `09:15` сравнивается с полученными знаниями `09:00–10:00` поведение, а не ночные значения.

### Базовый уровень с учетом контекста

Настроенные состояния контекста генерируют дополнительный ключ, например: `pump.on=true`, `mode=eco`, или `temperature=10–15` Числовые контекстные значения не используются напрямую; они сопоставляются с фиксированным интервалом:

`bucket start = floor(context value / bucket width) × bucket width`

Например, с шириной `5`, `12.3` принадлежит `10–15` Допустимый контекст сопоставления должен содержать как минимум **минимальное количество изученных примеров,** прежде чем он будет использован. Допустимый, но еще незрелый контекст остается в `learning` и не сравнивается с несвязанной обычной временной/глобальной базовой линией. Если контекст отсутствует или недействителен, адаптер использует вместо него обычный временной резервный вариант. Комбинации контекста, категориальные значения и выборки ограничены, чтобы предотвратить неограниченный рост объема памяти.

### Постоянное обнаружение сдвига уровня

Этот детектор работает с остатками:

`residual = actual value − expected value`

Он сравнивает устойчивую медиану ограниченного недавнего остаточного окна с долгосрочным ожидаемым остаточным значением (обычно близким к нулю), нормализованным относительно базового среднего абсолютного отклонения (MAD). Кандидат должен оставаться в одном и том же направлении при повторных оценках, прежде чем будет зафиксирован сдвиг уровня вверх или вниз. Это предотвращает превращение единичного пика в точку изменения.

Пример: насос, исторически расположенный близко `185 W` который остается рядом `240 W` приводит к устойчивым положительным остаткам и может быть идентифицирован как сдвиг уровня вверх.

### Выявление трендов

Для выявления тренда также используются остатки, поэтому сначала вычитается нормальное ежедневное поведение. Он вычисляет все допустимые попарные наклоны из ограниченного окна наблюдения:

`slopeᵢⱼ = (residualⱼ − residualᵢ) / (timestampⱼ − timestampᵢ)`

Итоговый наклон — это медиана этих наклонов (устойчивый наклон в стиле Тейла-Сена). Медиана делает влияние отдельных выбросов значительно меньше, чем обычная регрессия методом наименьших квадратов. Для выявления тренда требуется не менее 12 выборок за шесть часов.

Пример: продолжительность нагрева, которая постепенно увеличивается от `27` к `39 minutes` На протяжении нескольких дней наблюдается положительный остаточный наклон, даже если ни один из периодов не является экстремальным выбросом.

### Совокупный балл и обучение

Каждый детектор вносит ограниченный вклад в виде оценки. `0` к `100` Сигналы, отражающие значение/контекст, изменение уровня и тренд, рассматриваются как коррелированные данные о поведении: во взвешенный балл включается только самый сильный из них, что позволяет избежать двойного учета. Сигналы, отражающие скорость и застой, могут вносить независимый вклад. Согласованность между независимыми сильными сигналами добавляет небольшой ограниченный бонус; итоговый балл всегда ограничивается определенным значением. `0–100`.

Наблюдения, достигающие или превышающие **пороговое значение аномалии** , обычно исключаются из процесса обучения, что предотвращает немедленное возвращение текущей неисправности в нормальное состояние. Подтвержденные изменения уровня являются явным исключением: их значения постепенно изучаются, так что новый допустимый рабочий уровень может стать новой базовой линией.

## Конфигурация

Добавьте по одной строке для каждого источника в таблице **отслеживаемых числовых состояний** . Только состояния ioBroker с `common.type: number` поддерживаются.

Важные значения по умолчанию намеренно выбраны консервативными:

- Для запуска модели требуется 30 обученных примеров. `monitoring` (Настраивается для каждого источника).
- Чувствительность определяется надежным z-баллом, равным 3,5.
- Настойчивый `detected` Для получения этого показателя требуется оценка не ниже 70 за пять минут.
- В системе восстановления используется 10-точечный гистерезис, предотвращающий колебания вблизи порогового значения.
- Датчик застревания по умолчанию отключен и использует 120 минут при включении.
- Контекст времени суток включен с шагом в 60 минут (настраивается для каждого источника); контекст дня недели является необязательным.

Изменения настроек вступают в силу после перезапуска адаптера. Дублирующиеся идентификаторы источников игнорируются после первой включенной строки. Отсутствующие настроенные объекты остаются подписанными, поэтому их можно использовать после появления, но адаптер регистрирует предупреждение при запуске.

Когда строка источника удаляется из конфигурации и адаптер перезапускается, созданное под ней поддерево изменяется. `anomaly-detection.0.sources` и его сохраненная модель удаляются. При очистке используется сохраненный исходный идентификатор сгенерированного устройства, и удаляется только точное сгенерированное поддерево; временно недоступные источники, которые остаются настроенными, сохраняются.

### Аналитический обзор: история и аномалии

Вкладка **«Текущие оценки аномалий»** предоставляет компактную, адаптивную диаграмму **«История и аномалии»** для каждого отслеживаемого источника. Диаграмма изначально свернута и загружает историю только при открытии. Период можно изменить между **1 ч** , **6 ч** , **24 ч** (по умолчанию) и **7 днями** ; изменение периода приводит к перезагрузке данных для данного источника.

В диаграмме используется единица измерения состояния из ioBroker (например). `W`, `%`, или `°C`) и масштабирует область отображения в соответствии с фактической шириной карточки. Отображается:

- **Значение** – исторические данные измерений из настроенного поставщика истории.
- **Ожидаемый диапазон** – полупрозрачная полоса, изготовленная исключительно из исторического материала. `decisionLow` /`decisionHigh` Значения, действительные на каждую временную метку. Отсутствующие исторические границы остаются пустыми; текущий диапазон никогда не проецируется назад.
- **Контекст оценки** – едва заметная подсветка фона только для временных интервалов, чей сохраненный контекст соответствует контексту, используемому в текущей оценке. Названия контекстов используют ioBroker. `common.name` где это возможно.
- **Аномалия** – красный треугольник появляется только тогда, когда адаптер находится в сложенном состоянии. `detected: true` для проведения исторической оценки. Исторические памятные знаки не меняют текущий статус значка.

При наведении курсора или касании точки отображается информация, доступная для этого конкретного исторического временного интервала: значение и единица измерения, ожидаемый исторический диапазон (или явное уведомление о недоступности), статус, переведенная причина, оценка и контекст. Для отклонений значения/контекста во всплывающей подсказке также отображается конкретное расстояние выше или ниже исторического диапазона. Результаты по скорости, застреванию, тренду и сдвигу уровня сохраняют свое объяснение, специфичное для детектора, и не отображаются как искусственно созданные отклонения диапазона.

В легенде диаграммы указаны **значения** , **ожидаемый диапазон** , **контекст оценки** и **аномалия** . Небольшая заметка содержит количество заметных исторических измерений за выбранный период. Это не зависит от текущего статуса **«Норма»** или **«Аномалия»** ; адаптер хранит отдельные диагностические снимки, поэтому в заметке подсчитываются отображаемые снимки, а не создаются группы аномальных событий.

## Обучение и настойчивость

Нормальные наблюдения постепенно обновляют глобальную и настроенную временную базовую линию. Наблюдения, достигающие или превышающие настроенный порог аномалии, исключаются из процесса обучения, поэтому текущая неисправность не принимается за норму. Адаптер хранит только ограниченное количество выборок (240 на базовую линию) и компактные метаданные модели, а не неограниченный необработанный временной ряд.

## Расширенное обнаружение

Все расширенные детекторы по умолчанию отключены. Контекстно-ориентированное обнаружение изучает отдельные базовые уровни для до трех контекстных состояний: логических, строковых/перечисленных или числовых. Числовые контексты используют настраиваемые блоки фиксированной ширины. При отсутствии или недействительности безопасного контекста используется обычный временной и глобальный базовый уровень; действительный, но незрелый контекст остается в процессе обучения.

Метод обнаружения устойчивых сдвигов уровня сравнивает ограниченное недавнее остаточное окно с устойчивым ожидаемым базовым уровнем и требует повторных подтверждений, прежде чем сообщить о сдвиге вверх или вниз. Подтвержденные сдвиги постепенно воспринимаются как новая норма.

Для определения тренда используется ограниченный медианный наклон, учитывающий временную метку, по остаткам (`actual - expected`), чтобы избежать ложных срабатываний, вызванных нормальным временным поведением. Для этого требуется не менее 12 образцов в течение шести часов.

Адаптер обнаруживает статистические несоответствия; он не диагностирует неисправности оборудования и не доказывает причинно-следственную связь. Историческая бутстрап-обучение использует только нормальную модель; контекстные базовые модели обучаются на основе реальных значений, поскольку универсальные поставщики истории не могут надежно восстанавливать произвольные контекстные значения.

### Зрелость контекстной модели и резервный вариант

`sampleCount` Это количество сохраненных глобальных выборок модели ценности. Это **не** доказывает, что обучен каждый контекст. Например, `sampleCount=240` может сосуществовать с `contextSampleCount=3` для `pump.on=false`.

Выбор базового уровня для текущего наблюдения осуществляется явно:

1. Допустимый контекст сопоставления, содержащий как минимум **минимальное количество изученных выборок,** использует свою контекстно-специфическую базовую модель. В рамках этой модели временная иерархия такова: `weekday + time bucket → time bucket → context-global`.
2. В корректном контексте сопоставления, содержащем слишком мало выборок, базовый уровень значений еще не используется. В результате получается: `learning`, `baselineScope=insufficient` Кроме того, сравнения значений, темпов, сдвигов уровней и трендов, которые могли бы ввести в заблуждение при работе в новом режиме, не проводятся.
3. Если контекстно-зависимое обнаружение отключено, или заданное значение контекста отсутствует или недействительно, используется обычная иерархия: `weekday + time bucket → time bucket → global`.

Первое наблюдение после любого изменения контекста не приводит к сравнению скорости. Это предотвращает рассмотрение ожидаемого перехода ВКЛ/ВЫКЛ как необычной скорости исключительно из-за изменения операционного контекста. Постоянное обнаружение сдвига уровня и тренда работает с остатками только тогда, когда доступно ожидаемое значение.

Историческая бутстрап-обработка импортирует только историю отслеживаемых источников. Она обучает глобальные, временные, будние и скоростные модели; она не извлекает и не выравнивает по времени произвольную историю контекстных состояний. Таким образом, контекстно-специфические модели обучаются на основе последующих наблюдений в реальном времени.

Детектор оценивает остаточные значения (`actual − expected`), а не исходные значения, и требует как минимум **12** остаточных образцов, охватывающих не менее **шести часов** .                                                                                                                                                         |

Обнаружение с учетом контекста создает отдельную модель для каждой наблюдаемой комбинации контекста, с ограниченным максимумом в 32 сохраненные комбинации. Числовые значения контекста группируются по **ширине числового сегмента** ; логические значения и значения строк/перечислений не требуют ширины. Историческая бутстрап-методика обучает базовые показатели значений, скорости и времени, но базовые показатели контекста обучаются на основе наблюдений в реальном времени, поскольку универсальные поставщики истории не могут надежно восстанавливать произвольные значения состояния контекста.

### Практический пример насоса

Для определения состояния электропитания насоса сначала включите параметры **«Отклонение значения»** , **«Обнаружение с учетом контекста»** и **«Постоянное обнаружение изменения уровня»** . Первоначально оставьте **параметры «Скорость изменения»** , **«Застревание»** и **«Тенденция»** отключенными: обычные запуск, остановка и переходы между режимами могут вызывать быстрые изменения, в то время как неактивный насос может законно оставаться в текущем состоянии. `0 W` Время суток является необязательным параметром и должно быть включено только после того, как будет собрано достаточно репрезентативных данных; контекст будних дней обычно изначально не требуется.

Используйте состояние включения/выключения насоса и режим работы в качестве контекста. Затем модель сможет изучить отдельные нормальные режимы поведения, например, для:

- Насос выключен
- Насос включен в нормальном режиме
- Насос включен в режиме наддува

Не добавляйте состояние клапана, значение расхода или заданное значение в качестве начального контекста, если нет доказательств того, что это существенно объясняет мощность насоса. Если сами переходы в нормальном режиме работы конкретного насоса вызывают подозрения, функцию «Скорость изменения» можно включить позже, после наблюдения за типичным нормальным режимом работы.

### Принципы конфигурации

1. Начните с простого и включите только те детекторы, которые соответствуют физическому поведению, которое вы хотите отслеживать.
2. Не стоит включать каждый детектор просто потому, что он существует.
3. Добавляйте контекст только тогда, когда он объясняет ожидаемое значение; чем больше контекста, тем меньше обучающих выборок на каждый контекст.
4. Начните с настроек чувствительности и порога аномалий по умолчанию. Повышайте допустимое отклонение только после обнаружения действительно ложных срабатываний.
5. Используйте исторические данные для обучения только в том случае, если выбранный период соответствует нормальной работе; не проводите обучение преимущественно на основе известных периодов неисправностей.
6. Статистическая аномалия указывает на необычное поведение по сравнению с изученными данными. Она не доказывает наличие физической неисправности или её причины.

### Использование ИИ-помощника для выбора настроек

Искусственный интеллект-помощник может предложить начальную конфигурацию, если ему предоставить URL-адрес файла README и описание сценария использования мониторинга. Укажите физическую величину, что представляет собой источник, как часто он обновляется, какие другие состояния ioBroker описывают условия работы, являются ли внезапные изменения или длительные периоды стабильности нормой, существуют ли суточные или еженедельные закономерности, имеют ли значение внезапные сдвиги или постепенный дрейф, и доступны ли исторические данные.

Настройки, сгенерированные ИИ, являются лишь первоначальной рекомендацией и должны быть проверены на соответствие фактическому поведению устройства. Сам адаптер остается детерминированным и не использует ИИ.

Пример подсказки:

> Мне нужно отслеживать потребление электроэнергии насосом. Состояние включения/выключения насоса и режим работы доступны в качестве дополнительных состояний ioBroker. Переходы между запуском и остановкой вызывают быстрые, но нормальные изменения мощности. Длительное изменение мощности по сравнению с обычным режимом работы будет иметь значение. У меня есть история InfluxDB за 30 дней. На основе этого README порекомендуйте настройки обнаружения аномалий и объясните каждый вариант.

## Дополнительная историческая начальная подготовка.

Для каждого источника выберите **«Импортировать существующую историю»** и выберите **источник истории** из раскрывающегося списка. Ручной ввод намеренно недоступен. Список содержит только полные, включенные идентификаторы экземпляров поставщика истории ioBroker, такие как `influxdb.0`, `history.0`, или `sql.1`, у которых включена история именно для этого состояния. Адаптер определяет это на основе поддерживаемых параметров для каждого состояния. `common.custom.<instance>.enabled` конфигурация и поставщика `getHistory` эта функция позволяет не запрашивать базы данных истории только для заполнения конфигурации.

Псевдонимы остаются настроенным источником данных в реальном времени. Для исторической загрузки адаптер сначала использует историю, настроенную для самого псевдонима, а затем проверяет целевой объект чтения псевдонима. Если оба имеют историю в одном и том же поставщике, история псевдонима имеет приоритет. Если совместимый поставщик не указан, история для этого состояния (или его целевого объекта псевдонима) не включается, но **функция обучения только на основе значений в реальном времени** остается полностью доступной.

Период обучения по умолчанию составляет 30 дней (минимум 7) с не более чем 1000 импортированными образцами. Недопустимые значения и временные метки отбрасываются, дублирующиеся временные метки объединяются, а даже слишком большие наборы результатов отбираются по всему временному диапазону. Надежный проход MAD исключает очевидные экстремальные исторические значения перед обучением. Базовые уровни скорости рассчитываются только между хронологически смежными образцами с интервалом не более шести часов. Исторические промежутки никогда не приводят к застреванию результатов.

Импортированная совместимая модель повторно используется после перезапуска. Изменение поставщика истории, периода обучения или ограничения выборки запускает новый импорт. Перед каждым импортом среда выполнения повторно проверяет выбранного поставщика и его включенную конфигурацию истории. Недопустимые устаревшие значения, такие как `0` отклоняются немедленно и никогда не отправляются `getHistory` Запрос. Чтобы явно отбросить и переобучить модель аномалий, установите `sources.<sanitized-source-id>.retrain` к `true`; адаптер сбрасывает его на `false` с `ack=true` Эта команда намеренно сохраняет полную прогностическую модель, которая перестраивается только тогда, когда её историческая модель или обучающая база нуждаются в бутстрапе. Если импорт истории не удался или вернул слишком мало пригодных данных, исходный код остаётся пригодным для использования и продолжает обучение в реальном времени. `analysis.bootstrapStatus`, `analysis.status`, и `analysis.sampleCount` Показать результат импорта.

## Прогнозирование

Дополнительное прогнозирование позволяет получить ограниченный локальный прогноз для каждого отслеживаемого числового состояния. Прогноз генерируется на основе постоянной обучающей базы и не использует облачные сервисы или API ИИ. Модель поддерживает профили уровня/тренда, сезонности и времени суток и выбирает настроенную модель с помощью детерминированного тестирования.

Точки прогноза сохраняют свои реальные временные метки и интервал модели; конечная точка при необходимости сокращается, чтобы оставаться в пределах заданного горизонта. Тренд и сезонная фаза продвигаются от последнего обучающего наблюдения до текущего времени прогноза, включая доли интервала модели. Текущее текущее значение отображается отдельно в виде фактического маркера; оно не вставляется в пунктирную последовательность прогноза и не соединяется с ней. Это позволяет увидеть разницу между текущим измерением и ожидаемым значением модели в начале координат прогноза без создания искусственного градиента.

В карточке прогноза отображаются горизонт прогнозирования, выбранная модель, интервал модели, источник обучения, количество обучающих выборок, время последнего обучения, сезонность и классификация качества. Качество основано на исторической средней абсолютной ошибке (MAE). Состояния прогноза могут быть следующими: `disabled`, `learning`, `ready`, `unreliable`, или `error` Ограниченные или ненадежные прогнозы остаются видимыми при наличии явного статуса.

Настройки прогнозирования задаются для каждого источника: включение, горизонт прогнозирования, интервал обновления, минимальное и максимальное количество обучающих точек, а также режим сезонности (выкл., автоматический или ручной). Начальное обучение может использовать текущие значения или совместимый поставщик исторических данных. Сохраненные модели и их ограниченные обучающие базы сохраняются после перезапуска адаптера; недостающие или несовместимые обучающие данные обрабатываются без замены модели, основанной на исторических данных, на модель, использующую только текущие данные.

Версия алгоритма прогнозирования теперь — 8. Модели, построенные с помощью более старого алгоритма, аннулируются и перестраиваются на основе настроенного источника истории или новых обучающих данных в реальном времени. Это предотвращает интерпретацию старых коэффициентов с помощью скорректированных формул прогнозирования.

Прогностическая интерполяция останавливается на интервалах, превышающих как шесть часов, так и шесть медианных интервалов источника. Затем для обучения используется самый новый непрерывный участок; участок ниже минимального количества обучающих выборок ожидает дополнительных данных и сохраняет существующую подобранную модель, если она доступна. Повторные наблюдения в один момент времени не считаются новыми обучающими выборками. Неконечные промежуточные вычисления приводят к явной ошибке без точек прогнозирования.

## Ограничения

Аномалия означает, что значение или поведение необычно по сравнению с полученными данными наблюдений. Она не устанавливает первопричину. Некачественные исходные данные, длительные периоды отсутствия репрезентативной нормальной работы, изменение поведения оборудования или неподходящие настройки детектора могут приводить к ложным срабатываниям или пропуску аномалий. Проанализируйте первоначальные результаты обучения и при необходимости настройте каждый источник данных.

## Конфиденциальность

Обработка данных и хранение моделей полностью локальны в ioBroker. Никакие отслеживаемые значения не передаются во внешние сервисы ИИ, аналитические сервисы или облачные API.
