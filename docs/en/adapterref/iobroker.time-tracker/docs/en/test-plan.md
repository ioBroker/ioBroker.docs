# Acceptance and test plan (first real tests)

This document is the working guide for the **first tests on a real ioBroker installation**. It describes requirements,
test data, the test cases T1–T29 with their expectation and the acceptance criteria. For the installation up to the
first punch there is [`getting-started.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/getting-started.md); its steps correspond to the preparation below. The
public `README.md` is English (a requirement of the adapter checker); this operations document is also available in
German in [`../de/testplan.md`](https://github.com/sadam6752-tech/ioBroker.time-tracker/blob/main/docs/de/testplan.md) (the original text, with the protocol as it was kept).

## 1. Goal

To prove that the adapter does in productive operation what the specification (sections 3, 4, 9) demands: punch
(online, offline, terminal), calculate (target, breaks, balance, vacation, public holidays), report (Excel, PDF), enforce
permissions on the server, back up and restore.

## 2. Test environment

| Item            | Requirement                                                                                                                                                                                              |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ioBroker        | js-controller ≥ 6.0.11, admin ≥ 7.6.20                                                                                                                                                                   |
| Node.js         | ≥ 22 (checked locally with 22.22)                                                                                                                                                                        |
| Ports           | adapter port free (default `8092`), `127.0.0.1` is enough for the test                                                                                                                                   |
| HTTPS           | **required** for the installation of the PWA (service worker); in the test either the own certificate of the adapter (**Use HTTPS**), a reverse proxy (nginx/caddy) with a self-issued certificate, or a device in the same network with a valid certificate |
| Browser         | Chrome/Edge (Android) or Safari (iOS) for the installation; desktop browser for the API view                                                                                                             |
| Terminal device | tablet/phone in kiosk mode (screen stays on) **or** a browser tab                                                                                                                                        |
| Time            | one hour for the run; T3 (offline) needs quiet to watch the synchronisation                                                                                                                              |

Two accounts are mandatory: **administrator** (everything) and **employee** (own data only) — only that way permission
errors become visible.

## 3. Installation for the test

```bash
cd <repo>
npm ci
npm run install:pwa
npm run build:pwa      # creates www/ (web app)
npm run build          # creates build/ (adapter)
npm run dev-server     # starts the adapter in a throw-away js-controller
```

Alternatively into an existing installation: install the published package `iobroker.time-tracker` from npm as
described in [`getting-started.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/getting-started.md).

After the start: open the instance, check **port** and **bind address**, set `report_font_path` only if PDF reports in
`ru`, `uk` or `zh-cn` are needed (otherwise the report answers with `422 report_font_missing` — that is expected
behaviour, not an error).

| Language                                 | Checked font (17.09.2026, real report with the embedded font)                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ |
| `ru`, `uk`                               | `arial.ttf` (Arial covers Cyrillic)                                                        |
| `zh-cn`                                  | `malgun.ttf` (Malgun Gothic covers the Chinese characters)                                 |
| `pl`                                     | `arial.ttf` — the Polish letters (ś, ć, ł, ż, ę) are outside the built-in font             |
| `de`, `en`, `fr`, `it`, `es`, `nl`, `pt` | none needed; with a font set it is embedded as well                                        |

A **missing** file or a font without the needed characters leads to the same error message as a setting that is not set
at all — so the report is never delivered with empty boxes.

## 4. Test data

1. Sign in on the admin form: the account `admin` (or the configured login) with the start password of the instance
   setting — if it is empty, a random start password stands **once in the adapter log** — **change the password at once**
   (the adapter demands that at the first login). A start password entered **after** the first start counts as well, as
   long as the first administrator has not changed the start password yet: restart the instance, then the log says
   `… exists already and still has its start password - it was set from the instance settings now` and the login works
   with the entered value. After the change in the app, the adapter warns `the configured start password is not used`
   instead (D15 in [`decisions.md`](/#/docs/adapterref/iobroker.time-tracker/docs/en/decisions.md)).
2. In the web app under **Administration → Employees** create:
    - `anna` (role _employee_), password according to the policy (≥ 8 characters, upper and lower case, digits)
    - `chef` (role _manager_, if the acceptance of other people's months is to be tested)
    - set a **badge PIN** (4–8 digits) for `anna` → for T4
3. Check the work profile of `anna` in the web app (**Administration → Employees → _Work profile_**): employment level,
   weekly hours, working days, overtime model, vacation days, carry-overs and **paid break minutes per day** (e.g. `15` =
   a quarter of an hour of the break is paid, `0` = the break is not paid); in addition choose the **break rule** in
   **Administration → Settings** (default: punched break, otherwise the scale).
4. Create a **terminal** — in the web app under **Administration → Terminals** (or by `POST /api/terminals`), leave
   PIN required switched on. Then open the kiosk view on the device: the administration shows the finished address
   `http://<adapter host>:<port>/terminal?token=<device token>` for it (it shows the token **once**; the device
   remembers it for the next start).
5. Create the public holidays for the test year (setting _holiday country_), check the absence type _vacation_.

## 6. Acceptance criteria

- **T1–T13 are green.** T14–T17 successful at least once each.
- The restore from the backup (T10) is proven: copy the file, restart the adapter, the data are there.
- Every deviation is logged (number, observation, assessment) and either fixed or deliberately taken over as an open
  point.

## 9. Fallback scenario

- The adapter writes **only** into its data directory (SQLite file) and into its own ioBroker objects. An existing old
  application stays untouched and can keep running.
- Fallback: `iobroker stop time-tracker`, save the database file, keep operating the old application.
- Before every test run create a backup (T10) and copy the file **outside** the adapter directory.

## 10a. Check snippet for T21 (for looking up only, not part of the adapter)

`calendar.absences` is JSON; this script in the **scripts tab** writes the absences running today into the log and
reports again at every update of the adapter:

```js
const id = "time-tracker.0.calendar.absences";

/** Writes the absences running today into the log. */
function checkCalendar() {
	const state = getState(id);
	if (!state || !state.val) {
		log("time-tracker: no absences yet", "warn");
		return;
	}
	const today = formatDate(new Date(), "YYYY-MM-DD");
	const running = JSON.parse(state.val).filter(a => a.approval === "approved" && a.from <= today && a.to >= today);
	log(
		running.length === 0
			? "time-tracker: nobody is absent today"
			: `time-tracker: ${running.map(a => `${a.name} - ${a.type} (${a.code}) until ${a.to}`).join(", ")}`,
	);
}

checkCalendar();
on(id, checkCalendar);
```

## 11. Development notes (web interface)

**Browser tests** (`npm run e2e`, folder `test/e2e/`): they start `test/e2e/server.mjs` — that is the real API on an
in-memory database with the built web files from `www/`. No ioBroker needed, no network connection. Before the run
`npm run build:pwa` **must** have run; the tests block the service worker, otherwise Workbox would deliver the old files
from the precache.

> **Important:** check the exit code of the build first, then read the test result. An aborted build (e.g. an unused
> import) leaves `www/` unchanged — the tests then silently run against the **old** state.

> **One run is for exactly one server.** `playwright.config.ts` takes over a running E2E server
> (`reuseExistingServer`), and this server keeps its database **in memory**: a second run meets the state of the first.
> Then the double-scan protection discards punches within 30 seconds, and the check of the start password fails because
> it was changed already. Before another run end the server on port `8099` or start it fresh; a hard-aborted run
> otherwise leaves a zombie server on which the next round fails with `ERR_CONNECTION_REFUSED` (the check “actions do
> not lie on the text” in `test/e2e/layout.spec.ts` then also sees a different data stock than expected).

**Develop the web app against the running adapter** (fast feedback, React in development mode with readable errors):

```bash
npm --prefix src-www run dev     # port 5173, fetches /api/… through the proxy of 127.0.0.1:8092
```

Two pitfalls that cost time there:

- The proxy in `src-www/vite.config.ts` has to be written as a **computed** key `[API_PREFIX]`. With `API_PREFIX:` the
  literal text is compared, the proxy never applies and every API request lands in the app shell (the login then runs
  into nothing, `GET /api/auth/me` returns the HTML file).
- `@mui/icons-material` 5.x ships every symbol twice: as CommonJS (`Menu.js`) and as an ES module (`esm/Menu.js`).
  Without the alias in `vite.config.ts` the default import can arrive as a module object `{ default: … }` — React then
  aborts with “Element type is invalid … got: object” (React #130), and only after signing in, because the symbols occur
  only in the shell and in the forms.

After a change to `vite.config.ts` delete the cache `src-www/node_modules/.vite`, otherwise the dev server answers
`504 Outdated Optimize Dep`.

### A real ioBroker instance locally (dev-server)

`npm run dev-server setup` (once) and then `npm run dev-server watch` create a complete ioBroker installation with the
adapter under `.dev-server/default`. The web app then runs on `http://127.0.0.1:8092`, the admin interface on
`http://127.0.0.1:8081`. Without a start password in the instance settings, one is generated and written to the log
**once**:

```text
warn: time-tracker.0 administrator "admin" created with the start password "Zf-…" - change it at the first login
info: time-tracker.0 administrator "admin" exists already and still has its start password - it was set from the instance settings now
warn: time-tracker.0 the configured start password is not used: administrator "admin" changed his password already (empty the field "Start password of the first administrator" to silence this)
```

> **Windows 11 without `wmic`:** `dev-server watch` aborts there with `spawn wmic.exe ENOENT` — the tool reads the disk
> size through `wmic`, and this error is unhandled in version 0.8.0 (`wmic` was removed by Microsoft). Controller and
> adapter are installed by then; it is enough to start the controller directly:
>
> ```powershell
> cd .dev-server\default
> node node_modules\iobroker.js-controller\controller.js                     # runs in the foreground
> node node_modules\iobroker.js-controller\iobroker.js start time-tracker.0  # second console
> node node_modules\iobroker.js-controller\iobroker.js start admin.0          # optional: admin interface
> ```
>
> End with `iobroker.js stop time-tracker.0` or Ctrl+C in the controller window. On this way there is no hot reload:
> after changes run `npm run build` (adapter) or `npm run build:pwa` (web app) and restart the instance once.

So that changes to the web app arrive without a reinstallation, the delivered `www` folder can point to the one of the
repository (the adapter reads the files from disk at every request):

```powershell
cd .dev-server\default\node_modules\iobroker.time-tracker
cmd /c rmdir www                     # removes only the link, not the target
New-Item -ItemType Junction -Path www -Target <repository>\www
```

> **Link only `www`, and always remove junctions with `cmd /c rmdir`.** Two experiences from the set-up:
>
> - A junction is **not** suitable for the adapter code (`build/`): the js-controller then no longer finds the adapter
>   and ends it with `CANNOT_FIND_ADAPTER_DIR`.
> - `Remove-Item -Recurse` on a junction in PowerShell also deletes the **content of the target**. With
>   `cmd /c rmdir <path>` only the link disappears.
>
> After adapter changes therefore rebuild and copy the files:
>
> ```powershell
> npm run build
> Copy-Item build .dev-server\default\node_modules\iobroker.time-tracker\build -Recurse -Force
> ```

`.dev-server/` and `iobroker.*.tgz` are already covered in `.gitignore`.

> **Mind the port when testing:** `npm run test:integration` starts an ioBroker instance of its own and binds the same
> port as the adapter (default `8092`). If your own instance is running, the test instance cannot open its API and the
> check fails with “starts the HTTP API on the configured port” — so stop your own instance first
> (`iobroker.js stop time-tracker.0`).
