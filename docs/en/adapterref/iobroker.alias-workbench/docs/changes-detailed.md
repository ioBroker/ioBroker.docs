# Changes in detail

The release notes in the READMEs sum up what changes for users. This file has
the same changes in full, with cause and measurement, as they were noted while
fixing them — one section per release, newest first.

Deutsch: [aenderungen-ausfuehrlich.md](/#/docs/adapterref/iobroker.alias-workbench/docs/aenderungen-ausfuehrlich.md)

## Not yet released

* **Short view.** After clicking a device, the workbench now shows a summary by default: what it recognised the device as, room, function, place and name (the same fields as before), a traffic light from the checks, and a preview of how the alias will look in the object browser — new rows green, changed ones orange, removed ones struck through, with the device's current values. If everything fits, "Create alias" right below the preview is all that is left; next to it are "Checks" and "I need to set more". Template box, pattern choice, MQTT card and the row list are still there: the switch **Short | Detail** at the top right shows today's view unchanged.

  **Why.** The forum and other feedback said more than once that the workbench overwhelms on first opening: template box, pattern choice, MQTT card, twenty rows of roles and formulas, all at once. Normally none of it is needed — the workbench sets template, roles, formulas, name, room and function itself. Ricardo reviewed a mock-up as an HTML page on 25.11.2026 and decided: tree on the left unchanged, a summary on the right, "Save as template" hidden in the short view, a switch to today's view.

  **How it is built.** The short view rebuilds nothing. `zeichneErgebnis` draws everything as before; whatever is added from the template box on (box, MQTT card, row list, changes card, usage, the pattern choice in the header) carries the class `nur-detail`, and a card `nur-kurz` sits in front of it. Switching only changes visibility through a class on `body` — an open detail or the focus in a field is not lost. The traffic light reads the same results as the "Checks" dialog (`pruefErgebnisse`), plus `pruefeSchreiben` and open guesses; the preview comes from `baueObjekte` and `verwaiste`, i.e. the same calculation as the dry run. The choice is kept in localStorage (`alias-workbench.ansicht`), default is Short. The buttons in the card do nothing of their own: they take label and lock of the bar buttons and press them; the bar hides them in the short view and disappears when nothing else is left in it. Test points AB1–AB6.

* **Rows a check is about are marked.** In the detailed view, a row named by a check now carries a sign in front of its name — red ✕ for an error, orange ! for a hint, the text of the check as tooltip; a click opens the row. Before, you only saw it in the "Checks" dialog and had to look for the row. The traffic light of the short view also shows what the MQTT card reports in its header (offline, send points missing, delayed feedback).

  **How it is built.** Besides their text, the checks now pass the rows they mean (`zeilen`, for "Target can" also `texte` per row); `zeilenBefunde` sorts that by row name, `zeichneErgebnis` keeps it in `S.zeilenBefunde`, and the row list sets the sign from it. The chips of the MQTT card come from `mqttBefundeAus`, and `mqttBefunde` hands the same list to the traffic light. If the "publish" check already reports missing or mute send points, the traffic light leaves out the chips saying the same. Reason: Ricardo on 25.11.2026 at `PC_Bastelzimmer` — the card said "OFFLINE", the traffic light said nothing, and the hint about SET was only in the dialog. Test points AB4, AB7.

* **"N send points missing" only where the alias needs them.** The yellow chip in the header of the MQTT card counted every command the device knows and that has no point yet — `Sleep`, `SleepMode` … —, so it stood at almost every Tasmota although hardly anyone needs them. Now it only counts missing send points a ticked row of the alias wants to write to. The expanded card and the dialog still list all of them. Ricardo on 25.11.2026 at `Bastelzimmer_Licht`: "normally you almost never need them". The same applies since the same day to "N cannot send" (`gebrauchteStumme`): a mute `cmnd.Status` does not hurt any alias, only the helpers of the card, and is still listed as "mute" when expanded. A mute point the alias writes to stays red — the "publish" check reports it anyway. Counted in `gebrauchteFehlende`: missing points whose name follows `.cmnd.` in the write target of a ticked row. Test point H31.

* **A Tasmota with the factory topic is filed like any other.** With `%prefix%/%topic%/` the device lies under `cmnd`, `stat` and `tele`; the suggested place came from the branch you clicked — `alias.0.cmnd.<device>`, `alias.0.stat.<device>` … Now all three branches suggest the same place, formed like for every other Tasmota (`alias.0.<level above the prefix>.<device>`). `zielId` uses `gewohnterPfad` from `werte.js` for that — the levels above the prefix plus the device path, from the same calculation that merges the device (H20). Measured on the test system: all three branches of the Christmas device give `alias.0.SmartHome_Test.Weihnachten_aussen`, devices in the usual layout stay as they were. Ricardo on 25.11.2026: "it should come out just like my other Tasmota devices". Test point H32.

* **Empty room or function is marked.** The field turns orange with "pick a room" / "pick a function", and the traffic light of the short view says why it matters (Alexa, vis and the device adapter find devices by room; functions make groups such as "all lights"). A click on the hint jumps into the field. Nothing is blocked — a meter, for instance, simply belongs to no room. Orange rather than red, because red in the workbench means "this will not work" and the alias works without a room; a red field above a green traffic light would have contradicted itself. The traffic-light hints carry `feld`, and `springe` then only sets the focus. Ricardo on 25.11.2026: "so people are nudged towards some order". Test point N25.

* **Choosing the output in the short view.** For devices with several outputs (Tasmota power strip, multi-relay), the box "Recognised as …" now has the output selection too; switching it is the same as switching it in the template box. Without it, the short view only showed the first output; the template box with the selection was hidden. The short card builds no switching of its own: its field sets the one in the template box (`select.ausgangwahl`) and fires its `change` — the same path, including the question about existing aliases (C13). Ricardo on 25.11.2026. Test point AB11.

* **With neighbouring branches, every row names its branch.** After "Add neighbouring branches" (Matter puts switch and measurements in separate endpoints), each row says where it reads from — "from ElectricalSensor-2", "from OnOffPlugInUnit-1", "from info". The "from …" mark already existed for rows from a foreign source. After adding branches, however, the common parent is selected on the left (`zweigUmschalten`) and every row lies below it — so none counted as foreign. In branch mode each row now carries the first level below the parent. The same case from the other side: only `ElectricalSensor-2` clicked, but the existing alias `alias.0.Bastelzimmer.PC` reads from all three branches — `quelleHier` then returns the parent, and again every mark was missing (Ricardo: "I see nothing at all"). Both cases now go through `zweigBasis`. Measured on the production system at the GRILLPLATS plug (`matter.0.controller.2`). Ricardo on 26.11.2026. Test point AA6.

* **No false "slot already taken".** If a role fits two slots (`button.long` fits PRESS and PRESS_LONG of the button pattern), the row's detail no longer claims it does not count while it sits on the second one. `detail.js` asked `platzFuerRolle`, which returns the first slot the role fits. If the detector gives the row a slot of its own (`eigenerPlatz`), that one counts now. Found at the BILRESA button on the production system. Ricardo on 26.11.2026: "I don't understand the message". Test point E49.

* **Findings read as findings; a button without a value is none.** In the traffic light and at the row mark, a failed check now says what is wrong ("Source has no value yet" instead of "source has a value: PRESS"). Buttons (`button…`) that were never pressed are an orange hint ("Button not pressed yet") instead of an error. The checks carry a failure title `tf` besides their title `t`; traffic light and row mark use it, the dialog keeps the statements with ✓/✕. A button has no value until someone presses it — the BILRESA button therefore showed red "source has a value: PRESS, PRESS_LONG". A formula that throws is still an error on buttons too. Ricardo on 26.11.2026. Test point F12.

* **Buttons without the three dots.** "Create alias …", "Move …", "Remove alias …" and the other buttons that open a dialog first are now labelled without the trailing "…", in all eleven languages. The dots are the old desktop rule "a dialog comes first"; hardly anyone knows it today, and the dry run shows anyway that nothing has been written yet. Ricardo's decision of 25.11.2026: remove them everywhere for now. Placeholders and progress texts ("filter …", "writing …") keep them. Test point A13.

* **In the short view, "Update alias" is only active when something would change.** On an existing alias where nothing is different, it is grey with "No changes" next to it; changing room, function, place or name — or a newer template — makes it active. A changed room or function now also turns the channel row of the preview orange. It asks the same calculation as preview and dry run (`wuerdeAendern`): new or changed objects from `baueObjekte`, any enumeration change (`enumAenderungen` only returns what changes) and preselected removals from `verwaiste`; when in doubt the button stays active. Ricardo on 25.11.2026: "does the update button make sense there?" Test point AB8.

* **From the traffic light straight to the spot.** Every line of the traffic light can be clicked, and so can "Show in the detailed view": it switches to Detail and opens the area where you can act — the MQTT card for send points and feedback, the row itself for a finding about a row — expanded and scrolled into view. `zielVon` maps each finding to a target (MQTT card, row or top), `springe` opens it (`mqttAufklappen`, `S.openRow`), switches, redraws and scrolls there; rows carry `data-zeile` for that, the MQTT card the class `mqttkarte`. Ricardo on 25.11.2026: "it would be great if the area were already expanded in the detailed view". Test point AB9.

* **The empty right side is a card.** Before anything is picked, a card with an arrow to the left, a heading, the explanation of the mode and — when creating — three numbered steps; already when the tab opens. Built in `leerhilfe` (`sprache.js`) because it is there from the start — before, `beschrifteHtml` only put the grey sentence into the static `.empty` from `tab.html`, and the version from `ergebnis.js` only came after the first draw. Start, create, edit and the templates tab now use the same function. Ricardo on 25.11.2026: "make this message bigger and nicer". Test point AB10.

* **Each device opens in the short view — or as set.** New setting "Show when a device is picked" (section "Short and detailed view"): *Short view* (default) — every device opens short, the switch only holds until the next one; *Always the detailed view*; *Remember the last choice*. Before, the workbench remembered the choice in the browser, and whoever switched to Detail once never saw the short view again. Now every other device resets the view to the configured start (`ansichtFuer` in `zeichneErgebnis`); redrawing the same device leaves it. The setting is `startView` (`short` / `detail` / `remember`), read through `einstWert`, and counts as `short` when missing. The settings-page test now also checks the labels of select options for translations. Ricardo on 25.11.2026: "the short view should always show when switching; the settings decide whether you always want Detail or the last choice". The switch carries a tooltip saying where to set this (`short.viewTip`). Test point Q15.

## 0.14.1 (2026-11-22)

* **What goes into the database is English; what is only shown follows your language.** Three places were still German. The value list of the Tasmota colour effects (`Scheme`, slot EFFECT of the colour light template) is now `single colour, wake up, cycle colours up, cycle colours down, random` — it is written into the alias and the send point and stays there, so it is English like the value lists of the device adapters; the template is now version 7, and an existing alias shows the difference and takes the new list with "Reset to template". A send point the workbench creates now carries the fixed description `created by the Alias Workbench` instead of a text in the language of whoever clicked. And the descriptions in the "Create send points" dialog ("brightness 0 to 100" …) come from the language files, in all eleven languages. The command knowledge file has English field names.

  **How it was found.** Asked whether `tasmota-befehle.json` should be converted too, a search of the whole adapter for German text that users get to see turned up three places the English conversion of 0.14.0 had missed: the `was` descriptions in that file (shown in the dialog), the effect value list in that file and in `tasmota-rgb.json` (written into objects), and the description of created send points, which came from the dictionary and was written into objects in the UI language. Everything else — all UI strings in the code, the template names, the settings page, the enumerations — already goes through the language files or carries an English version.

  **Why the value list is English and not in the system language.** It would have been possible to write it in the system language. But it ends up in the database and stays there, the device adapters (hm-rpc, zigbee, shelly) write theirs in English, and the workbench compares an alias's value list with the template in both directions (G10): in the system language, switching the language later would have reported a difference on every effect alias. Ricardo's decision of 2026-11-22. Test points H28–H30.

## 0.14.0 (2026-11-22)

* **Creating data points in the MQTT adapter is a setting, off by default.** In the review of PR 6634 the checker bot noted under "MQTT helper creates objects in external adapter namespace" that `admin/js/mqtt.js` creates objects under `mqtt-client.0.…` — outside its own areas `alias.*` and `enum.*`. mcm1957 accepted it as an exception ("acceptable"). On 2026-11-22 Ricardo decided to make it the operator's decision anyway: `native.mqttObjects`, in the instance settings "Allow creating and changing data points in the MQTT adapter", default `false`.

  **What falls under it.** Not only "create send point". Querying needs a created `cmnd` object too — `cmnd.Status` for Status 5 and 11, `cmnd.TelePeriod` for the period — and so does SetOption59. Six paths are therefore locked: the single "create" and "allow sending" buttons, "Create missing" (the collective dialog), "Ask the device", the two SetOption59 buttons and "Create the N missing send points" in the dry run. The values remembered on the foreign object (`so59`, `telemetryPeriod`) stay in memory only without permission.

  **Locked at the entry, not deep inside.** Each of these paths goes through `mitMqttFreigabe`, which reads the setting **fresh** from the instance object and only then carries on — whoever flips the switch in another tab does not have to reload the workbench. Without permission a dialog opens that names the ids that would be created, with a button to `#tab-instances/config/system.adapter.alias-workbench.<n>`. The buttons stay visible: they show what would need doing, and the expanded MQTT card says the rest right at the top.

  **Measured on the test system on 2026-11-22** (test points H25–H27) on a fake device with `cmnd.Sleep` deleted, while recording the workbench's `socket.emit`: switch off → hint in the card, the single and the collective button open the lock dialog with the right id, `mqttEinzelnStill` returns an error, **not a single `setObject` outside `alias.`/`enum.`/`system.`**, the object is not in the database. Cross-check: switch on in the database only, no reload → the same button creates the point with `publish: true`. After `sync.sh` the existing instance carried `mqttObjects: false` — `iobroker upload` fills in the default. On both of Ricardo's systems the switch is on afterwards.

* **The conversion no longer hangs on an object that has gone.** Reported by Ricardo on 2026-11-22 with a screenshot: on the test system the dialog stood on "Converting…" and went no further. Cause: the task list was built from memory when the dialog opened and carried the whole object along. An alias deleted before the click made a step throw, and `reihum` never called its callback — the run had no end.

  Now every step reads its object **fresh** from the database. If it is missing, or no longer carries an old name, it is skipped and not counted; it is never created again. Every step has a 15-second deadline, a throw is caught, and a double or late answer counts only once. Three cases in `npm test` (throwing step, no answer, double answer). Recorded as test point A12, measured with an object deleted for the purpose.

* **A half-built alias no longer fills the log.** Going through the ioBroker log after the test bench run of 2026-11-21, every selection of one particular alias wrote `Error on "subscribeForeignStates": Alias … has no target`. The workbench subscribed to `alias.….*`; if a point without `common.alias.id` lies underneath, the controller rejects the whole pattern. Now `aboMusterFuer` subscribes the other points individually for aliases with such a point; without one it stays with the pattern. Measured as J14: subscription `[alias.0.wbJ14.MIT, 0_userdata.0.wbJ14quelle]`, the value 42 arrives, no line from `admin.0`; cross-check without the half-built point → `alias.0.wbJ14.*`. The warning from `javascript.0` about the same point remains — the script adapter subscribes to every alias itself; that is not the workbench.

* **The template format is English (layer C).** The hardest part of the conversion, because there was no unambiguous pattern like `native.x` for the alias objects. The same words meant other things in the code, on the same line: `z.typ` was a template field, the `typ:` beside it a draft field. A first attempt to rename file by file was rolled back — it would have left the adapter **silently** inconsistent: the files still carried `zustaende`, one reader already expected `points`, and `(v.points || [])` yields an empty list instead of an error.

  So it went in two moves. **C1** gave every variable holding a template an unambiguous name (`tpl`, `tplZeile`, `quellTpl` …) — pure renaming of local variables, no change in behaviour, with `no-undef` as the net: a missed spot leaves the name undefined, and the linter reports it at once. That happened five times; none of those faults reached a test. **C2** then renamed the fields — now through an unambiguous pattern, `tplZeile.rolle` → `tplZeile.role`.

  The name table exists exactly once, in `admin/js/migration.js`. It migrates the users' own templates, and it converted the 16 shipped files — one table, not two. It was found not by searching the files but by reading the function that **builds** a template (`baueVorlage`): the files do not even know `absolut`, `schreibenAbs`, `beschriftung` and `nachkommastellen`.

  Two faults almost slipped through on the way. A renamer replaced strings too — and `'typ'` and `'feld'` are also CSS classes in this project; the display would have broken without any test noticing. And the draft's read paths (`{punkt, feld, formel}`) carried the same carrier name in C1 as the template's real fallback sources; C2 would have renamed them too and broken the reading. Both were caught before deploying.

* **The fields on the alias objects carry English names.** `quelle` → `source`, `vorlage` → `template`, `vorlageVersion` → `templateVersion`, `ausZustand` → `templateState`, `geraetetyp` → `deviceType`, `musterVonHand` → `deviceTypeManual`, `vonHand` → `manual`, `angelegtVon` → `createdBy`, `attrappeAus` → `mockedFrom`.

  **`templateState`, not `fromState`.** The field holds the name of the template row a point came from — `SET`, `ACTUAL` — and is matched against `z.name` in the template's rows. The first draft called it `fromState`, which reads like "the id of the source"; that one is `source`.

  **Two fields that only showed up when counting.** `vonHand` (a point assigned by hand during a source swap) and `musterVonHand` (the device type was chosen rather than detected) appeared in no table — they surfaced only when every property ever written to a `native` was enumerated. The same count also showed what is **not** ours: `autocreated` is written by the user's `javascript.0`, `topic` comes from MQTT, `TYPE` from hm-rpc. Those stay, as mcm1957's exception for external systems requires.

  **`telemetryPeriod` and `telemetryPeriodAt` are not migrated** (formerly `takt`, `taktZeit`). They sit on mqtt-client points, that is in a foreign namespace, and writing there again would be the opposite of what the conversion is for. They are renamed all the same — they are a cache and are rewritten on the next query.

  **What the migration touches, and what it does not.** `native` and nothing else. The whole object goes back through `setObject`, which makes the old key fall away by itself, while `common` is passed through verbatim. Checked on the test system against the dump taken the same morning: 109 objects before and after, none gone, `common` byte for byte identical on **all 109**, `native` changed on exactly the 100 affected.

  **Writes go one after another, not all at once.** 100 simultaneous writes wake every reader at the same time; one by one is quieter. Measured: 47 objects in 3 seconds. What cannot be written is collected rather than aborting the run — a single refused object must not hold up the others.

  **The abort is a test case, not an accident.** While measuring, the session closed the tab mid-run: 53 converted, 47 still old. On the next open the dialog named exactly those 47 and finished them. Recorded as check point A11.

* **The four settings carry English names, and a migration brings the existing ones along.** `ikonRaeume`, `ikonFunktionen`, `ikonErsetzen`, `vorlagenVomAdmin` → `iconRooms`, `iconFunctions`, `iconReplace`, `templatesFromAdmin`. The trigger was the review of PR 6634 on 2026-11-17: mcm1957 marked the point `must be fixed` with a deadline of 2026-12-01, his reasoning being "Object Ids must use english names — unless they are directly supplied by external systems".

  **Why renaming alone would have been damage.** `einst(name)` reads from `system.adapter.alias-workbench.0.native` and falls back to a defaults table when a key is missing. All four defaults are `true`. After a plain rename, `einst('iconRooms')` would no longer have found the old key, would have fallen back to `true` — and a setting that had been switched off would silently have come back on. Exactly the kind of fault nobody notices.

  **The path not taken.** Reading both spellings everywhere would have touched the adapter in 92 places, each a second truth, and none of them ever going away again. Instead exactly **one** module knows the old names: `admin/js/migration.js`. Every other file knows the English ones only. A test holds that in place — it searches all remaining files in `admin/js/` plus `io-package.json` and `jsonConfig.json` for the four old names and fails as soon as one shows up.

  **Mandatory, but not silent** (Ricardo's decision of 2026-11-21, tenable at 21 installations according to iobroker.live): an instance carrying old names opens a modal dialog at startup that names the count and points out there is no way back. "Not now" does not close it but switches to "the workbench cannot work without the conversion" — behind a `showModal` nothing is operable anyway, so no second locking mechanism is needed.

  **Measured on the test system on 2026-11-21**, with `ikonRaeume` set to `false` beforehand: dialog open and modal, all four old names in the text, "Not now" leaves it standing, "Convert" reports four. Afterwards `iconRooms=false` — the switched-off value survived — the other three `true`, no old key left, and the user's own template in the same `native` untouched. Recorded as check point Q14.

  **A trap that only showed up on deployment.** `iobroker upload` carries the defaults from `io-package.json` into existing instances. Right after deploying, the live system's `native` held both: `ikonRaeume`…`vorlagenVomAdmin` **and** `iconRooms`…`templatesFromAdmin`, the latter with their default `true`. The first draft of this module gave precedence to the **new** key in that case — intended for "the conversion already ran and someone has saved since". But that case cannot arise: after the conversion the old key is gone, and `io-package.json` no longer knows it, so no deployment brings it back. Both present therefore always means: old is the real value, new is the carried-in default. So the old one wins — otherwise the migration itself would have caused the silent jump to `true`.

  And a second fault in the same breath: the first attempt simply overwrote the target key, which left the insertion order of the object deciding which value won. That order is guaranteed nowhere. Carried-in defaults are now skipped rather than overwritten, and both orders give the same result.

## 0.13.0 (2026-11-02)

* **type-detector 6.2.0: one device type more, and a smaller bundle.** The library moved from 6.0.3 to 6.2.0. 6.1.0 (2026-10-21) brought an ES module build that works in Node through both `require` and `import` as well as in browsers; because esbuild can shake that tree better, `admin/detector.js` shrank from 70.6 to 66.4 KB. 6.2.0 (2026-10-23) added the device type `tv` — 52 patterns instead of 51, with twenty places: `POWER`, `KEY`, `VOLUME`, `VOLUME_ACTUAL`, `MUTE`, `VOLUME_UP`, `VOLUME_DOWN`, `STATE`, `PLAY`, `PAUSE`, `STOP`, `NEXT`, `PREV`, `INPUT`, `APP`, `ART_MODE`, `UNREACH`, `MAINTAIN`, `ERROR`, `RSSI`.

  Nothing changes at the consumption place compared to 6.0.3: the expression still accepts both roles and `value.energy.consumed` is suggested. Measured on the shipped bundle (2026-11-02): both roles fill `CONSUMPTION`, and the header on the live system reads "type-detector 6.2.0 · 52 Muster".

  Check point A2 was carried along, as it named 51 patterns as an expected value. The number is now labelled for what it is: an expected value **against the library**, not against a fixed number in the plan. E6 keeps its dated measurement and gains the fresh one beside it — 752 places instead of 732, with the derivation untouched: the same eight places take their role from the expression, the same nineteen have none. The button label "all N patterns" comes from the library anyway (`pattern.allPatterns` with a placeholder); only two comments named the 51 outright.

* **The consumption point now carries `value.energy.consumed` — the role that is correct.** The unit at the `CONSUMPTION` place is Wh. That is energy, not power, so the role belongs under `value.energy.*` and not with the watts in `value.power.*` (`value.power` = W/kW). That is precisely why `value.power.consumption` appears struck through in the [ioBroker roles list](https://github.com/ioBroker/ioBroker.docs/blob/master/docs/en/dev/stateroles.md) — line 151 against line 156, both quoting the same unit Wh/kWh.

  Up to `@iobroker/type-detector` 6.0.2 the correct role was unusable all the same: the pattern `consumption` carried the expression `/^value\.power\.consumption$/`, that is exactly the struck-through one. A point with `value.energy.consumed` dropped out of the device without any message — the socket was still recognised as a `socket`, just without `CONSUMPTION`, and that is how it reached vis, Alexa and the device manager. Reported as [issue 334](https://github.com/ioBroker/ioBroker.type-detector/issues/334), fixed in PR 339, released as 6.0.3 on 2026-10-14; the expression now reads `/^value\.(energy\.consumed|power\.consumption)$/` and the place's `defaultRole` is `value.energy.consumed`. Measured against both versions on a socket with a `switch` and one consumption point in Wh: 6.0.1 fills `CONSUMPTION` only for the old role and leaves the place empty for the new one; 6.0.3 fills it for both.

  The four shipped templates (`messpunkt`, `tasmota-lampe`, `tasmota-mehrfach`, `tasmota-steckdose`) therefore write `value.energy.consumed` now, and their template version goes up with it, because this changes content rather than just a text. The library's suggestion applies unchanged — there is no exception in the bundle.

  **The price is stated, not talked away.** An alias is read not by the workbench but by every adapter with **its** detector version, and one older than 6.0.3 accepts the struck-through role only. Measured on the live system on 2026-10-14 — on the **pattern**, not on a version number, because two of the readers bake the detector into their frontend where no `package.json` reveals it: the admin's **device manager** (`iobroker.admin/adminWww/assets/…loadShare….js`) and **`iobroker.devices`** (`admin/assets/index-….js`) each carry a bundle in which `energy.consumed` appears nowhere — only `value\.power\.consumption`. Over npm come `5.0.15` inside `iobroker.matter` and `6.0.1` inside `@iobroker/mcp-server`, both with `/^value\.power\.consumption$/`. The `4.6.4` at top level belongs to `iobroker.hm-rpc` (`^4.6.0`) and reads no aliases. An Alexa bridge is not affected at all here: `iobroker.iot` and `iobroker.cloud` are not installed, and `iobroker.alexa2` does not use the detector. Until those catch up, a consumption point newly built from one of the four templates is missing there. Existing aliases are unaffected: the expression still accepts the old role, so they stay recognised. In the house itself 95 points carry the old role (Shelly meters, sockets, `matter.0.controller.2.…CONSUMPTION`) and none the new one — so the fault was one nobody had run into yet.

  **Measured again on 2026-11-02, after three weeks of waiting.** Two of the three readers have caught up: `iobroker.admin` 8.3.6 (2026-10-29) and `iobroker.devices` 4.2.7 (2026-10-25) now carry `/^value\.(energy\.consumed|power\.consumption)$/` with `defaultRole: 'value.energy.consumed'` in their baked bundle — checked in the npm package, not against a version number. `iobroker.matter` is still at 1.3.1 from 2026-07-23, but its main branch now requires `^6.0.1` instead of `^5.0.15`, so its next release gets it by itself. That is why the change ships now.

  Two tests hold this in place: one loads the shipped `admin/detector.js` into its own context and demands that the expression accept **both** roles, that the suggestion be the current one, and that both roles really fill `CONSUMPTION` in a detection run; the second reads the four template files, because the role lives there and not in the code.

## 0.12.0 (2026-10-14)

* **Source swapping asks the same recognition as the tree.** All four mapping stages started from the **old** source — same relative path, remembered template row, name or role of the old state. That works while both devices are built alike and fails completely once they are not: moving an alias from a Tasmota socket to a Matter socket produced **0 out of 8** mappings, for two devices that do the same thing. Both reasons were on the source side, never on the target — `mqtt-client` keeps no roles (measured on test and production: `stat.POWER`, `cmnd.POWER` and `tele.SENSOR` all carry no `common.role`, type `mixed`), and five of the eight points read from **one** telemetry JSON. Yet swapping asks the same question the workbench answers anyway when you click a device: which point **there** is the `ELECTRIC_POWER`? Now, before guessing, the draft of the **new** source is computed and mapped through its pattern slots — the template first, otherwise the detector. That carries in both directions, which was the point: to a device that labels its points (Matter: `role: value.power`, `unit: W`) the detector answers; to one that labels nothing, the template does. Measured at `mqtt-client.0.SmartHome.PC_Jonas`, the type detector makes only `info` out of ten nameless `mixed` points — but `tasmota-steckdose` fits with rank 2000020 and knows that `stat.POWER` is the status point and the power sits in `tele.SENSOR` under `ENERGY.Power`. On the production case: 0 of 7 before, 6 of 7 now, with separate read and write sources.
* **The formulas travel with the source.** `JSON.parse(val)?.ENERGY?.Power ?? null` does not describe "this is what power looks like" but "this is how you get power out of a Tasmota telemetry message". Left in place when swapping to Matter, it ran against a plain number: `JSON.parse(37)` yields 37, `37?.ENERGY` is `undefined`, and the point sat at `null` — four readings empty with no error anywhere, and `SET` would have written the string from `val ? "ON" : "OFF"` onto a boolean. Each direction now brings its own: none towards Matter (plain numbers there), the JSON formula again back to Tasmota. Display and writing use the same function for this — two code paths would be two truths, which is exactly what happened once during development.
* **Three bugs only measuring found.** First, the identifier the type detector reports is **not an object**: `abbild` builds it a flat image of its own in which `ElectricalSensor-2.ELECTRIC_POWER` becomes `…_ELECTRIC_POWER` with an underscore. Taken over unchecked, the alias would have pointed at an identifier that does not exist. Second, with two points of the same role the detector grabbed the wrong one (`ELECTRIC_POWER_B`); now the point named **exactly** like the slot wins — against the detector, not against a template, because a person wrote that. Third, the rule "with a simple source the read source counts for both" overwrote the write target from the template: the command would have landed on the status point, exactly the bug W20 and W22 abolish. Whether a point has one or two sources is not a property of the alias but of the device it hangs on.
* **A point no stage can find can be named by hand.** Until now the only choices were "remove" or leave it. The row now offers a list of every point on the new device, with role and unit beside it. What you pick there carries the mark "by hand" and the note that **formula, unit and value range stay as they are on the alias** — the workbench knows nothing about that point, so it changes nothing about it. A status point gets no write target either, even where the target would be writable: what counts is the alias point.
* **When the unit changes, the numbers sit beside it.** Tasmota delivers `ENERGY.Total` in kWh, Matter `CONSUMPTION` in Wh: the same meter, factor 1000, and invisible. Nothing is converted automatically, because the labelling itself is unreliable — Matter writes the unit `mA` on `CURRENT` and delivers amperes (0.926 at 245 W and 228 V, measured). An automation that believed the label would have made 926 A of it; it builds the error in instead of finding it. Instead the row states the finding ("on the alias A · new source: none"), shows what the alias displays today, and offers **two free fields**: unit and factor, both at the current state. The result recomputes as you type, without the dialog redrawing. Where the workbench knows something, a shortcut sits beside the field (`Wh`, `/ 1000`) — a suggestion from the labelling, checkable against the numbers above. Free fields, because fixed buttons fail where the target carries **no** unit at all: a JSON collector point has none, the unit sits in the field. The box only appears when the **new source** delivers something other than the old one — swapping between devices of the same kind shows nothing.
* **The remembered template is checked against the new source.** An alias remembers which template it came from, and the workbench keeps applying it until you explicitly change it — exactly right for a like-for-like replacement. After swapping to a differently built device the channel still read "Tasmota socket, forced, ✕ cmnd.POWER" and "21 without source". The dialog now checks the remembering against the **new** device: if it still fits, nothing changes; if it does not, it says why, names the number of affected points and — if a different template fits the new source — which one. Plus a pre-ticked box that drops the remembering. `native.geraetetyp` and the whole of `common` are left untouched: the swap changes the source, not what the device is.
* **Several branches can be selected as one device.** Some adapters spread one device across sibling branches: Matter stores a socket as a folder without data points of its own, holding two `device` nodes — the switch in one, the readings in the other — and an `info` channel. The folder was not selectable (a folder without direct data points counts as a signpost), and each endpoint on its own produced half a device: at the switch the detector recognised a socket and offered the five readings as "to be created" while the neighbouring branch already had them. **Ctrl-click** now adds a branch to the selection or takes it out; the selection moves to the common parent, and every branch involved is marked in the tree, the parent more faintly. The same sits in the **context menu**, for anyone without a keyboard, and in the header of the right-hand side as a button "Add neighbouring branches (N)" — where the adapter provides evidence, the tooltip says why: Matter writes the same `nodeId` and the same `statusStates.onlineId` to every endpoint. Internally `S.current` stays **one** node, the common parent; `S.zweige` says which of its branches belong to it. Making a list of it would have touched `S.current` in 91 places without any of them getting better. Point names are shortened where they are unambiguous: `OnOffPlugInUnit-1.SET` becomes `SET`. Not for Tasmota and not at its sections — there the branch carries meaning, and the templates address `stat.POWER` and `tele.SENSOR`. Nothing is merged automatically: many devices can sit side by side under one node, and only a person knows what counts as one device.
* **One rule sat in the wrong place.** The first version had `waehle()` clear the multi-selection on every call. That is right for a click on a **different** node — but `waehle(S.current)` means "rebuild the draft" in three places: after reloading the objects, after a change to the existing set, and after writing. A single new data point from the Admin would have taken the selection with it. Now only a different node clears it, and that a click on the parent means "all of it" is decided by the click itself.

## 0.11.0 (2026-10-11)

* **Template notes are German and English.** The description, the recognition note and each row note were a single German sentence, and the tab did not show them. They are now `{ "de", "en" }`, the same shape as the template name. The tab shows the admin language, otherwise English, otherwise German: in the template sheet under the name, in the recognition box, on the row and when it is opened, and on a device as the tooltip of the row name. The name hint stays one search pattern (`licht|lampe|light|…`). It matches the device name, which does not follow the admin language; separate language versions would miss “Lampe” on an English admin.
* **One dictionary for the settings page and the tab.** The page lived in `admin/i18n/` with eleven languages, the tab in `admin/sprachen/` with German and English. They were split because the adapter checker flags an `i18n` folder that lacks the other languages. There is now one file per language under `admin/i18n/`, the same keys, and the tab loads that same file. An unknown language falls back to English. The 0.10.0 note still describes the two dictionaries; that is the published release.
* **Object ids no longer contain umlauts.** The repository checker allows only `a-z`, `A-Z`, `0-9`, `-` and `_` in an id. `ä`/`Ä` becomes `ae`/`Ae`, `ö`/`Ö` `oe`/`Oe`, `ü`/`Ü` `ue`/`Ue`, `ß` `ss` — in the name field, in "Place under", in the move dialog and in the name of a new point. Dots in the folder field stay, they separate the levels. An existing alias whose id already contains an umlaut is left as it is, until the name field is left again. Leaving it and saving creates a second alias at the new id; the old one stays.
* **Rooms and functions keep the umlaut.** Both are the name of an enumeration, not an alias id. `Wohnküche` stays `Wohnküche`. When the workbench takes the folder from the room, the folder is `Wohnkueche` and the path is `alias.0.Wohnkueche.…`.
* **Typing a folder by hand does not rename the room suggestion.** `Küche` in "Place under" becomes the folder `Kueche`. The question below then also said `Kueche`, because it used the folder after it had been cleaned. It now uses the typed name: there is no room `Küche` — create and assign it? Confirming creates `enum.rooms.Küche`.
* **A Tasmota using the factory setting `%prefix%/%topic%/` is now treated as one device.** The MQTT adapters map the topic straight onto the object path, so with that setting a device is spread over `tele.<name>`, `stat.<name>` and `cmnd.<name>`, with no node holding it together. Measured on a switched-over test device: the workbench found nothing at all on the device node, showed a card with a plausible base path and "no commands found" one level up, and a send point created there would have been named `…SmartHome_Test.cmnd.POWER` — without the device level. The next device on the same prefix would have overwritten the first one, topic included. A single place now answers which points belong to a device and what they are called relative to it; both layouts yield the same names (`tele.STATE`, `cmnd.POWER`), which is why the shipped templates apply unchanged — they only ever address relative paths. Renamed prefixes (`Prefix1-3`) are recognised as soon as two devices share them.
* **"Ask the device" now also fetches the IP and the telemetry period.** The button was tied to the command list alone: once that was complete it disappeared, and with it the only way to obtain the other two. The device reports neither on its own — the IP only in `tele/INFO2` (sent once at boot) or `stat/STATUS5` (on request), the period only on request. So a device with a complete command list and an IP unknown for months offered no button at all, and anyone wanting to fetch it over HTTP needed the very IP they were looking for.
* **The telemetry period was read from the wrong place.** `TelePeriod` was taken from `tele/STATE`, where it is not. Counted across the whole estate: of 36 devices publishing `tele/STATE`, not one carried the field, and `StatusSTS` does not either; asked directly the device answers `{"TelePeriod":10}`. The lookup therefore returned nothing on all 42 devices, and the SetOption59 hint never named a number although it was built for exactly that. It is now requested and remembered on the request point.
* **`Status 5` is requested twice.** Captured on the broker: `cmnd/Status 5` went out, `stat/STATUS5` with the IP came back — and ioBroker was left with an object and no value. On first contact the MQTT adapter only creates the answer object and discards the value; `Status 11` has always been asked twice for that reason, `Status 5` only once. This also explains the `INFO` points that sit empty on some systems: they only arrive at device boot, and there is no second time.
* **The MQTT card says whether the device is reporting — three states, not two.** `Offline` is published by the broker the moment it loses the connection; that is a fact. `Online` is written by the device itself, once, on connecting, and then stays with the broker — it can be arbitrarily old, because a device running for a year never repeats it. A two-state display therefore reports a dead entry as green: in the test estate one device claimed `Online`, last changed over four years ago, without a single `tele/STATE`, and answered neither ping nor HTTP on its last known address. Now: `Offline` means offline; `Online` with telemetry younger than three telemetry periods means reachable; `Online` with stale or no telemetry means "not reporting"; no information means no mark at all. Only an explicit offline counts as offline — other firmwares use other words, and an unknown one means "do not know", not "gone". Measured across 41 devices: 27 reachable, 12 offline (from zero to 2031 days), one not reporting, one without information.
* **The detail row has a field for the value list.** `common.states` translates numbers into text — an HmIP valve state carries 0 to 8 with names, a window contact 0=CLOSED/1=OPEN. The admin turns that into a dropdown, vis and Alexa show the text, and the type detector requires it for some slots altogether. Until now it could only be inherited from a template: not seen, not created, not changed — although the workbench wrote it all along. In the test estate 1055 datapoints carried a value list, and none of 726 alias points did. Where the source has one and the draft does not, a button offers to take it over; "yields" shows the text for the value; and both deviation comparisons include it, against the existing object in both directions, so an existing list can no longer disappear silently.
* **The HmIP thermostat templates read the valve position from the wrong point.** The radiator and heating-group templates read the VALVE slot from `1.VALVE_STATE` with a percent unit. On HmIP that is a state code 0-8 (`ADAPTION_DONE`, `TOO_TIGHT`, `ERROR_POSITION`, …) and not an opening degree: a thermostat reporting code 4 showed "4 %". It never stood out because the number looks plausible. Measured across the estate, all 15 `VALVE_STATE` points are ENUMs with maximum 8, while `1.LEVEL` carries maximum 100 and the percent unit everywhere — and the radiator template already required `1.LEVEL` for detection anyway. Both now read `1.LEVEL`. That `hm-rpc` assigns the roles the other way round (`value.valve` on the state code, the generic `level` on the valve position) comes from a plain name table without any device distinction and makes no difference to the alias: the role comes from the template.
* **The device type field in the template sheet is searchable.** It was a dropdown with 52 entries. A dropdown cannot be searched, and since the label starts with the translated name, the browser type-ahead never found the raw one either. It now works like the pattern chooser used when building an alias: search over both names, arrow keys, Enter and Escape.
* **Shipped templates can be opened row by row.** Until now the row view was reserved for your own templates: to see which fallback sources, formulas or notes a shipped one carries you had to make an own copy first — and were left with a copy you never wanted. Every field in the block is disabled, so merely looking creates no working copy.
* **The row overview names the fallback read paths.** A row showed only the first path; that three more lay behind it was visible only once expanded. A "+3 fallback" mark now sits beside it.
* **The "must be present" mark showed the wrong question.** It read the template's recognition list — "must the device have this point for the template to apply at all" — instead of the row's own mandatory flag. At the HmIP heating group one row was marked where four are mandatory; the Tasmota templates marked none at all. The same applied to the checkbox in the expanded row, so the interface gave the right answer nowhere. Counted across all 16 templates, 15 now show a different number. The checkbox also wrote into the recognition list: ticking SET on the Tasmota light template would have bound it to `stat.POWER`, a point the MQTT adapter only creates once the device has been switched. It now sets only what it says.
* **Enumeration catalogue under Admin 8.0.x.** Admin ships 58 room and 62 function templates, translated and with icons. The workbench reads them from its bundles instead of keeping its own copy — a copy ages silently, and it was always the same 120 entries, id for id. Since Admin 8.0.x they sit elsewhere: no longer in a dedicated `Enums` chunk as JSON text in backticks passed through `JSON.parse`, but as plain JavaScript inside a shared module of 7.9 MB — unquoted keys, backtick strings. Two things were in the way. First a line `if (t.length > 3000000) return false;` that skipped exactly this file; under Admin 7.8.23 the catalogue sat in a bundle of 2,843,653 bytes, five percent below the limit — it never worked reliably, it just never tripped. Second the search pattern, which required `JSON.parse`. Both notations are now read, and the entries without `eval`: the shape is fixed and names contain no backticks. With the second notation the icons sit in the same module as base64 and are therefore ready at once instead of being fetched one by one.
* **A store for the catalogue.** Fetching 7.9 MB every time the tab opens would be unreasonable, so the result is kept as `katalog.json` in the adapter's file area — 545 KB under Admin 8, 30 KB under Admin 7, where icons are still fetched individually. It is only fetched again when Admin rewrites its bundles; the stamp is the asset file names from `index.html`, not the version number, because an interim build carries the same one. Neither the adapter configuration (26 KB, read on every start) nor a state (Redis keeps everything in memory) nor browser storage (tied to the single device) would be the right place. The file area only exists for an object of type `meta`; the workbench is `onlyWWW` and gets none from js-controller, so it creates `alias-workbench.0` itself on first use. Not `alias-workbench.admin` — that is where `iobroker upload` writes the interface files, clearing everything else. While fetching, a note in the bottom right says why it takes a moment this once.
* **Pattern names from the same store.** The workbench reads the translated device-pattern names from Admin, because `@iobroker/type-detector` is a library and ships no translations. Under Admin 8 that map sits in the same 7.9 MB module as the enumeration catalogue — until now both crawled it independently. A new module `ablage.js` now holds reading, writing and the stamp for both; whoever adds their part reads first and merges, so neither erases the other’s section. `ziehe()` now takes the language as an argument and `alleZiehen()` collects both interface languages at once — two kilobytes together, and in exchange a language switch does not trigger a second fetch of the large module. Measured on 2026-10-07 on the second load: production 404 instead of 2,255 KB, test system 419 instead of 864 KB. The store itself barely grows: 549 KB under Admin 8 (53 names per language), 32 KB under Admin 7 (44 per language).
* **Source counting: ancestor and descendant.** `quellenVerteilung` merged in two steps: everything below the main source into it, and below that nodes sharing **the same parent**. The second step therefore only knows siblings. `mqtt-client.0.inverter.HM600.ch0` ended up in group `…HM600`, `…inverter.HM600` in group `…inverter` — each alone, both left standing, and the chip said “4 sources” instead of three. An ancestor step has been added, with the safeguard of the sibling step. **Ordering turned out to be the catch**: placed before the sibling step it achieves nothing, because that step is what creates the flatter nodes which can then be ancestors at all. At the Victron charge controller `…solarcharger.288` only came into being from `…288.Dc` and `…288.Yield`, and only then was `…288.History.Daily.0` a descendant of it. Both steps now alternate until the list stops shrinking, at most three rounds. Measured against the production inventory: 146 aliases, the five target values of the test point hold, and nesting remains exactly where it should — at `0_userdata.0.Solar.Garten` with its three `channel` children.

That was often wrong: hm-rpc sets `read: false` as soon as a value merely cannot be *polled* — it is still reported. On the production system 76 such points had changed their value within the last month, `BOOST_MODE` on the heating controls among them; following the badge removed a working read source. What remains is a quiet “button” note when the read source really is a button press.
* **Choosing another pattern that does not apply yet leaves the ticks alone.** On the air conditioner (detected as thermostat), switching to “Air conditioner” removed setpoint and switch, because without MODE the pattern does not apply and gave no row a place. After suggesting and discarding, the setpoint was then missing and the pattern no longer applied. Now the ticks stay as long as the new pattern does not apply.
* **Suggesting gives a datapoint only one place.** While the pattern did not apply yet, every row looked free: a MODE just confirmed was guessed again on the second run, and the same source was also put on WORKING_MODE. Now a ticked row that already carries a place’s name and role counts as taken. Anyone wanting a source twice adds it by hand.
* **The pattern field names what is really missing.** Instead of “✕ MODE missing” next to a ticked MODE, it now shows the missing setpoint, as a group: “SET / SET_HEATING / SET_COOLING missing” — one of them is enough. Fixed along the way: an exclusion rule of the pattern matched almost every role in the workbench, so every setpoint counted as excluded.
* If the chosen pattern only applies after suggesting, the orange legend says so — “With ‘Suggest free slots’ it would apply.” — and offers the button right there.
* **Two buttons swapped places.** “Suggest free slots” now sits in the blue box after the pattern field, with the detection it belongs to. The button that shows the device’s whole inventory moved to the bar above the list and is now called **“Load all datapoints of the device”**, back **“Load the template proposal”**. Without a template it is not shown at all instead of greyed out.
* **After moving an alias, its source knows it again straight away.** Moving deletes as many objects as it creates, and the workbench only rebuilt its source → alias map when the number of objects changed. Selecting the source afterwards showed “will be created” and “Create alias …” — one click would have created a second alias next to the moved one. Only reloading the tab helped. Now every change to the objects counts, a source swap included.
* **“to source →” no longer jumps somewhere approximate.** If both an alias’s note and all of its points refer to a device that no longer exists, the button is now greyed out, and its tooltip names the missing source. Before, it jumped to the nearest folder above that still existed — on the test system, a folder with 31 unrelated devices.
* **A HomeMatic actuator without a template no longer brings maintenance clutter along.** So that no output is lost on a dual actuator, the workbench also ticks the switch of every further channel. That applied to maintenance channel 0 as well — and since every point counts as required there, `AES_KEY`, `DEVICE_IN_BOOTLOADER`, `DUTYCYCLE` and `RSSI_DEVICE` stood ticked in the draft. Now only channels with a function (socket, light, dimmer …) bring anything along.
* If a row’s role points to a place that **another row already holds**, the detail row now says so in a yellow note — “cmnd_POWER already holds SET — this row gets no place that way” — instead of “SET requires boolean, string is set”. The old advice did harm: following it took the SET place away from the switching point, and the switch could no longer switch.
* **A measured value no longer gets a write target.** Choosing a place in “Place in pattern” that the pattern keeps read-only (ELECTRIC_POWER, VOLTAGE, ACTUAL …) sets “writes to” to “— do not write —”. mqtt-client creates every point as writable, so on the 3D printer the power reading stood there with write target `tele.SENSOR` — a written value would have gone to the device. If a row still holds such a place with a write target, the detail row warns.
* If the pattern does not apply, the suggestion box with “No remaining datapoint fits” no longer sits above the orange legend — it contradicted it, since it deliberately leaves out rows changed by hand. Where it still appears, it now names those rows, in the right number (“stat_POWER was decided by hand …” instead of “1 rows were …”).
* In the detail row the **“reads from” and “writes to” pickers are wider** (420 instead of 260 px) — before, the end that tells points apart was cut off. The “Datapoint” heading above them is gone, and the formula is now called **read formula** and sits right under “reads from”, as the write formula sits under “writes to”. The note on separate sources now reads “Reads from somewhere else than it writes to: what is shown is what the device reports back — not the command sent last.” A place shared by several rows (ACTUAL under “Information”) now shows on each of them, not only on the last, and the note under “Role” no longer claims “no place” for it.
* The **name of a new point** can now be changed: the detail row now starts with a **Name** field, with the resulting ID shown small beneath it. Anyone who prefers `POWER` or `SET` to `cmnd_POWER` types it there. What the point does is decided by the role, not the name. On an existing alias the name stays fixed, because scripts and vis depend on it; the field refuses duplicate names.
* **If the pattern does not apply, the legend above the list says why** — “The socket pattern does not apply right now: SET is missing” — and whether an unticked row would get the place: “cmnd_POWER fits SET but is not ticked”, with a **tick it** button; if the row’s type does not fit either, the note says so and the button sets the type as well. Before, only “✕ SET missing” showed in the pattern field, and that the fitting row merely lacked its tick was not visible.
* The detail row now has **“Place in pattern”**, right next to the name: pick the place, say SET or ACTUAL, and the workbench fills in what the pattern prescribes for it — role, type, unit, value list. Before, one had to know that SET means the role `switch`. Taken places are greyed out with the row holding them; if a chosen place is not assigned, a note says why. Choosing “— don’t write —” now also counts in the preview.
* **Choosing another pattern re-sets the ticks** when no template is in force: ticked is then whatever has a place in the chosen pattern, plus the switch of every further channel — and every row on which something was already set by hand (role, unit, formula …). Before, this happened only once when the draft was built, and the old pattern’s ticks stayed afterwards. With a template and on an existing alias nothing changes. This also corrects a statement from 0.9.12: “— no template —” does not tick everything, but whatever has a place in the detected pattern; if only “Information” is detected, that is everything.
* For **“Information”** the pattern field now shows **“✓ 24 points”** instead of “24/31 filled”. That pattern takes any number of points, so the total grew with every tick and sounded as if something were missing. Where there is no maximum, none is shown; all other patterns keep “x/y filled”.
* A node without an object of its own now carries **“VIR”** in the tree instead of a dot, styled like DEV, CHA and FOL; the tooltip says “not a real folder”. Since the badges have the same width, the dot stood out among all the FOLs like an error — yet such nodes behave like folders. The name comes from ioBroker itself: the web adapter calls such a level `type: "virtual"`.
* A folder’s **“Devices”** card sorted differently from the tree beside it: on the robot vacuum it read `1, 10, 2, 3 …`, while the tree listed the same folders as `1, 2 … 9, 10`. It now sorts like the tree.
* **“Ask” for SetOption59 took an old answer for a new one.** If `stat.RESULT` still held a `{"SetOption59":"ON"}` from days ago, the card reported “enabled · just asked” after asking — even when the device was off and did not answer at all. Only what arrives after sending counts now, as it long has when asking for the command list; if no answer comes, “No answer …” is shown and nothing is recorded. “Ask” is also always there now, even when enabled — before, the button disappeared exactly then, and an old value could not be re-checked.
* The **“MQTT device”** card no longer opened on some devices: its header showed “–”, and nothing appeared below — no command list, no “Create”, no “Fix”. Since 0.9.12 the SetOption59 block only shows where a row reads from `tele/…`; on a device without such a row the card bailed out too early and never attached its content. Now only the SetOption59 block is left out, the rest is back.
* **The bulk dialog “Create send points …” created them with the wrong type.** A send point that comes with a write formula has to be `mixed` — otherwise the js-controller converts the formula's result back to the target's type on write, and `true` goes on the wire instead of `ON`. That rule has lived in `punktTyp` since 0.9.12, but only the single “create” button used it; the bulk dialog kept building from the raw type of the command knowledge and created `POWER`, `Fade` and `LedTable` as `boolean`. So whoever created several points at once got exactly those points wrong where it matters. All three paths now use the same function; `npm test` keeps it that way.
