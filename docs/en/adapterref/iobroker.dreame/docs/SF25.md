# Dreame SF25 WiFi (experimental)

Support for `dreame.fwd.u2527`, the SF25 food waste disposer. Property definitions
and protocol behavior are based on
[maestrea76/HA-Dreame-SF25-WiFi-Integration](https://github.com/maestrea76/HA-Dreame-SF25-WiFi-Integration)
at commit `6dfb9aaa4f77088731ac97c526d56584612c3ac7` (MIT; notice in
`lib/sf25-source-LICENSE.txt`). Related discussion: [#154](https://github.com/TA2k/ioBroker.dreame/issues/154).

This implementation has automated protocol/adapter tests and initial physical
SF25 testing on 8–9 October 2026. It remains experimental, not a confirmed release.

## Using it

Use the existing Dreamehome login with the device bound to the account. The
adapter's current cloud configuration uses the EU region. The SF25 appears under
its device ID in the Objects view. States are created as valid property values
arrive. It is intentionally excluded from robot/map widgets.

### Dreame tab

The Dreame admin tab now includes a separate SF25 page, automatically selected on
SF25-only accounts. Mixed accounts can switch between the existing robot view
and the SF25 page. No robot/map commands are used for the SF25.

The page shows operation, lid state, remaining time, temperature, humidity, cycle
energy and filter values with their update times. Standby/sleep takes precedence
over retained program/running flags. Missing readings appear as dashes; readings
older than five minutes are marked, and controls require fresh device status and
reachability. The online flag is written only on transitions, so its timestamp
is not treated as a heartbeat. Wake and Refresh remain available for recovery
when readings are stale or reachability is unconfirmed. This is a fixed UI freshness threshold, independent of the adapter's
configured polling interval. Refresh requests a new device poll.

Controls use the existing SF25 remote states: processing, self-cleaning, pause,
resume, stop, wake, lid opening, silent mode and child lock. Starting/stopping a
program requires confirmation. Self-cleaning also asks the user to confirm bucket
preparation. The page reports that a command was sent to the adapter, not that the
device executed it; check the resulting status and adapter log for rejections.
The adapter remains authoritative for the lid-opening preflight described below.

Device discovery publishes `info.sf25Devices` separately. `info.devices` remains
robot-only for compatibility with existing map widgets. The page also works in
the standalone web interface; the existing robot widget choices are unchanged.

| State under `<did>` | Meaning |
|---|---|
| `status.state` | 1 working, 2 standby, 3 sleeping |
| `status.activity` | Derived operation: -1 unknown, 0 standby, 1 running, 2 paused, 3 sleeping |
| `remote.program` | -1 idle/stop, 0 processing, 1 extra drying, 2 self-cleaning |
| `status.running-state` | Raw flag: -1 off, 0 paused, 1 running; can remain 1 in standby |
| `status.remaining-time` | Minutes remaining |
| `status.temperature`, `status.humidity` | Chamber temperature (°C), humidity (%) |
| `status.energy` | Raw cycle energy in Wh; not a lifetime total |
| `status.carbon-filter-life`, `status.carbon-filter-days` | Filter life (%) and days until cleaning |
| `status.lid-open` | Lid state, nonzero means open according to HA mapping |
| `remote.child-lock`, `remote.silent-mode` | Boolean settings, encoded as 0/1 |
| `remote.wake`, `remote.pause`, `remote.resume`, `remote.Refresh` | Buttons |
| `remote.open-lid` | Guarded lid-opening button; hardware validation pending |
| `status.2-2`, `status.4-6` | Unmapped read-only numeric properties |

Write command states with `ack: false`; buttons need `true`. Program writes accept
only -1, 0 and 2. Value 1 remains visible as an automatic phase but cannot be
started directly until validated. Stir/Compact, automatic schedules
and the HA temperature-stop automation are outside this initial implementation.

Use `status.activity` for current operation. Standby and sleeping take precedence
over retained running/program flags. Raw properties stay unchanged for diagnosis.
Standby does not prove successful cycle completion or that the bucket is cool
enough to remove; follow the device/app cooling notification. Program value 1
was retained in standby after processing; its exact phase meaning is unresolved.
The app's silent setting mutes tones/voice prompts, not necessarily motor noise.

### Remote lid opening

Write `true` with `ack: false` to `remote.open-lid` (Deckel öffnen). The controller
first reads status, program, running flag and temperature directly from the device.
It only sends `6.26 = 1` when all readings explicitly succeed and confirm standby
(`2.1 = 2`), stopped program (`2.3 = -1`), stopped running flag (`2.10 = -1`) and
a finite temperature at most 40 °C. Missing, invalid or ambiguous values block
the command. The 40 °C threshold is a conservative integration-side guard, not a
Dreame-specified cooling clearance. Follow the app/device instructions.

The lid sensor remains read-only. The button resets after completion or failure;
opening is checked by readback. A rejected or uncertain opening is never retried,
and the lid command does not automatically wake the device. Retained program=1
or running=1 after a completed cycle also blocks this conservative guard. Do not
change or spoof status values to bypass it. Closing remotely is not implemented.

Command and guard reference: HA integration commit
[`9e791edd21dfff121388314f3708f8229ec2b91c`](https://github.com/maestrea76/HA-Dreame-SF25-WiFi-Integration/tree/9e791edd21dfff121388314f3708f8229ec2b91c),
`button.py` and `control_guard.py` (MIT). Protocol tests cover opening and rejection
paths; the new lid button has not yet been tested on the physical SF25.

## Implementation choices

- A separate SF25 lookup follows the adapter's existing spec-module pattern.
  No robot properties or map commands are inherited.
- Status uses device RPC `get_properties` with property-address DIDs and batches
  of at most 15; no cloud summary/cache is treated as authoritative SF25 status.
- The RPC path is derived from the device's `bindDomain`, matching the HA client.
- MQTT uses `masterUid` in the topic. If it differs from the broker of the existing
  connection, this first implementation falls back to polling for the SF25.
- Polling follows the configured adapter update interval. MQTT is preferred for
  brief lid changes; this patch does not add an adaptive per-device poll timer.
- A push received during an in-flight poll is preserved. Invalid property results
  do not overwrite valid state values.
- Writes require explicit property success and a matching numeric readback.
  Readback waits 1.5 seconds and allows up to three reads for delayed updates;
  an accepted write is never repeated because of a mismatch. Transport retries
  are disabled for writes and actions. A property rejection with code 1 is
  retried once only after sleep and subsequent awake status have been confirmed.
  Wake cloud code 80001 was observed alongside the device's standby announcement;
  it is tolerated only if subsequent status reads confirm the device is awake.
  Other action errors still fail. The wake action itself is never repeated.
- Existing MQTT TLS behavior is unchanged. Certificate validation should be
  reviewed separately; this patch does not claim to add the HA client's pinning.

## Physical testing and remaining validation

Confirmed with the initial implementation and subsequent fixes: Dreamehome login,
device discovery, binding-derived RPC route, property reads, MQTT changes,
lid polarity (1 open/0 closed), silent mode on/off (also checked in the app),
sleep-to-standby wake, processing start/pause/resume/stop, and reconnect after
adapter restart with fresh readings. A processing run started at 06:21 on
9 October; the app later confirmed standby and that the bucket had cooled.
No stop command was sent during this run. Its precise completion event was not
captured, so standby alone is not treated as proof of a successful cycle.

Remaining time was observed at 360, 329, 299 and then 0 minutes. Energy increased
from 0 to 59 and 90 Wh, then reset to 0 at the standby transition. These samples
do not establish total cycle consumption. Temperature scaling/units still need
independent comparison. A network/broker interruption while the
adapter keeps running, and a mixed SF25/robot account remain untested.
Self-cleaning was started through ioBroker at 07:59:56 on 9 October after user
preparation. The app explicitly reported the inner drum clean at 09:30, matching
the initial 90-minute estimate. Remaining-time samples decreased through 72, 59,
44, 29 and 14 minutes to 0; sampled energy rose to 112 Wh before resetting to 0.
This is not a measured total. Device status changed to standby (2), and derived
activity correctly changed to standby (0), although raw running-state stayed 1
and program changed to 1. These retained flags do not mean drying is active.
The cleaning notification is not an explicit cooling clearance. Follow the
app/device cooling indication before removing the bucket. The user subsequently
confirmed emptying/cleaning the bucket. Reconnection after another adapter restart
was checked with fresh standby values after this completed cleaning run.
Unknown properties remain read-only; do not assign guessed fault meanings.

If this account has already used the unmodified adapter with the SF25, old vacuum
objects may remain in ioBroker. This patch does not delete user objects. Verify
the new SF25 states and remove obsolete device objects manually only after backup.
